# 登录首屏代码分包

## 本次范围与测试基线

先处理启动，运行时 CPU、卡顿和内存优化另做。本次不修改比赛模拟、HUD 更新频率或联机协议。

微信云测截图中的 iOS 高档机：总启动 3563 ms，其中环境加载 1301 ms、代码包下载 1792 ms、框架加载 499 ms、游戏代码注入 9 ms、首屏渲染准备 69 ms。各阶段存在重叠，不能简单相加。该设备主要应减少启动下载依赖，不能仅凭报告总览的“注入较慢”标签认定这台设备注入耗时很高。

原登录入口静态引用大厅、角色管理、房间和完整 UI 构建器，账号栏与字体会提前触发比赛资源包加载。页面控件少，并不代表启动依赖少。

## 加载顺序

| 阶段 | 加载与创建内容 |
| --- | --- |
| 微信普通冷启动 | `StartupManager`、四张原登录图片、背景/Logo/开游按钮；并行请求登录音乐和首屏小字库 |
| 点击开游 | 合并连续点击请求，加载 `gameplay` 代码分包，创建原 `LoginManager` 并直接进入大厅 |
| 进入大厅 | 原账号、头像、金币栏与完整业务系统开始初始化；大厅资源继续使用原 `race` 加载器 |
| 分享邀请启动/唤起 | 立即请求业务分包，交接最新房号，进入原房间流程 |
| 比赛返回 | 使用已加载的业务入口，保持返回大厅/房间与 keep-alive 重赛逻辑 |
| 编辑器/非微信 | 使用原登录入口，保留已有调试入口 |

音乐在登录页保留。音乐实现移到 `assets/startup/MusicManager.ts`，原 `assets/scripts/app/MusicManager.ts` 仅重导出同一类，避免两个播放器或切大厅重播音乐。首屏只读取已存的音乐音量；完整设置和音效系统在业务包加载后接管。

首屏沿用原图、1280×720 设计坐标与宽屏 cover 规则。按钮文字仍为运行时 Label。首屏不实例化随后再销毁比赛 HUD。

## 分包与依赖约束

| 位置 | 构建位置 | 用途 |
| --- | --- | --- |
| `assets/startup` | 主包 | 8 个小入口模块，包含登录视图和共用音乐播放器 |
| `assets/scripts` | `subpackages/gameplay` | 大厅、联机、比赛等完整业务代码 |
| `assets/race` | `subpackages/race` | 原比赛/大厅场景和资源 |
| `assets/music` | `subpackages/music` | 原音乐分包 |
| `assets/race/fonts/startup` | `subpackages/startup-ui` | 登录专用字体，优先级高于父级 race |

首屏 TypeScript 源码约 23 KiB，业务目录约 2.53 MiB；这只是源码量，不是生成的 JavaScript 包体，也不是性能收益。实际构建大小由构建守卫输出。

`StartupManager` 先用 `assetManager.loadBundle` 加载业务，再通过 Cocos 类注册表挂载 `LoginManager`；主包禁止静态导入业务目录。业务包只可引用已经加载的主包公共模块。Cocos 支持按 Bundle 加载脚本，但跨包依赖必须保证加载顺序，参见 [Cocos 3.8 Asset Bundle 文档](https://docs.cocos.com/creator/3.8/manual/zh/asset/bundle.html)。

`StartupManager` 与 `LoginManager` 必须各自持有独立、稳定的 UUID；`Login.scene` 的 Canvas 明确绑定 `StartupManager.ts.meta` 对应的脚本类 ID。不要把旧脚本 UUID 移交给新文件：运行中的 Creator 可能先识别出两个文件共用 UUID，自动重编号新文件，从而让场景引用失效。

2026-09-24 编辑器预览回归：日志确认 UUID 冲突后，Creator 将 `StartupManager` 编号改为 `250e5bfe-7ba4-472d-81d1-2fd5bdd7bc2a`，场景仍引用旧 `9decb106-7785-4f29-96ec-a5a56c9cee87`，导致 Canvas 启动脚本丢失。已保留 Creator 的独立编号，并修正场景绑定。源文件检查与微信构建前检查现在验证实际场景绑定及脚本 UUID 唯一性；还可用 `assertStartupPreviewEntry` 对照现有 Creator 编译产物中的 `_RF.push` 注册 ID。此检查不等同于实际画面验收。

资源路径的小表在 `StartupResources.ts`，完整 `ResourcePaths.ts` 复用它。业务存档、房间会话不复制到首屏；交接仅有当前首屏节点与邀请房号。

## 字体与异常处理

登录字库从 `StartupCopy.ts` 自动提取，使用真实 600 字重，生成文件约 72.8 KiB。整套大厅/比赛字库仍位于 race，首屏不必为“开游”下载完整字库。修改首屏文案必须修改该文件并运行 `pnpm fonts:build`、`pnpm fonts:check`；不能手改 TTF 或字符清单。

业务下载失败保留按钮，显示“点击重试”；连续点击复用一次请求。字体/图片也失败时转入原入口，业务同样失败则给出微信原生重试提示。场景销毁后的资源回调不再创建节点或组件。下载期间的新邀请覆盖旧邀请；启动监听在业务入口接管时解绑。

## 构建与验收

1. 让现有 Creator 会话导入新增脚本、分包目录以及 `ShuiMasterUI-Startup.ttf`；新字体的 `.meta` 需由 Creator 生成并保留。本次没有启动/重启 Creator。
2. 重新构建微信小游戏；共享 `config/build/wechatgame.json` 默认使用非调试模式，构建面板手动选择的调试开关仍会保留，做性能复测时应关闭。
3. 构建扩展检查四个分包，并核验实际 `System.register` 模块：`LoginManager`、`GameManager`、`PrepareRaceFlow`、`RoomFlow` 必须只存在于 gameplay；首屏必须留在主包；gameplay/race 不得列入启动预加载。
4. 运行 `pnpm wechat:check -- --build`，查看实际主包大小、主包脚本和业务分包脚本字节数。如果旧扩展缓存未生效，检查会拒绝通过；不要仅凭 `game.json` 中存在分包声明判断优化成功。
5. 同机、同网络、同构建模式分别复测清缓存冷启动和有缓存热启动。记录“登录页可见/可点击”“点击开游到大厅可操作”“大厅到首局可操作”三个耗时。业务延迟到开游后首次加载会产生等待，不能仅用首屏变快替代整个路径体验验收。
6. iOS、Android 检查登录音乐与静音存档、宽屏布局、断网重试、连续点击、邀请冷启动/热唤起、联机比赛返回房间和重赛。音乐仍按需下载，缓存首次为空时可能晚于背景出现。

离线检查：启动专项 13 项，以及音乐、联机、包体、UI 资源与微信配置共 55 项通过；游戏 `assets` 范围使用 TypeScript 5.4.5 类型检查通过。全仓类型检查仍有两个本地历史工具脚本 `tools/freestyle-shoulder-repair/history-*.ts` 的既有缺失引用，未修改这些工具文件。
