# 比赛 HUD 交互学习与设计纠偏

本轮暂停出图，只研究HUD如何服务比赛。用户已明确：机甲是皮肤，游戏不是科幻；先验证一张典型比赛界面，不能批量铺开。

## 阅读依据
- Microsoft XAG 102，对比度：https://learn.microsoft.com/en-us/gaming/accessibility/xbox-accessibility-guidelines/102
  关键HUD要在不同背景中持续可辨认；一般关键文本建议至少4.5:1，大文本/图形按其适用条件至少3:1。数字不是“所有字号一律通用”的规则，应结合实际呈现尺寸。提高可读性不等于扩大整块面板。
- Microsoft XAG 103，视觉与音频线索的补充通道：https://learn.microsoft.com/en-us/gaming/accessibility/xbox-accessibility-guidelines/103
  关键状态不能只靠颜色；图标、文字、声音/触觉可相互补充。静音或关闭震动时仍需可用。声音与震动不是本轮已授权的新实现。
- Microsoft XAG 109，目标清晰度：https://learn.microsoft.com/en-us/gaming/accessibility/xbox-accessibility-guidelines/109
  让玩家能查看目标/进度；与当前目标无关的打断可推迟或抑制。不是鼓励把所有信息常驻放大。
- NN/g，减少认知负担：https://www.nngroup.com/articles/minimize-cognitive-load/
  删除不帮助任务的视觉杂乱和无意义字形变化；减少需要阅读、记忆、判断的额外工作。这是通用交互资料，本项目的具体布局是应用推断，不是其直接研究结论。

以上已读取网页正文。另一次Game Accessibility Guidelines链接返回404，未将它作为证据。未进行玩家眼动研究、真机测试或元梦之星逐帧交互分析。

## 本项目事实
- SpeedStarsUiPrefabBuilder.beginTouchStroke根据触点横坐标区分LEFT/RIGHT；按住与松开驱动划水。全屏触控不是背景装饰，叠加UI会影响热区和触点生命周期。
- InputTuning.STROKE_QUALITY_TUNING按手臂周期进度定义GOOD/PERFECT窗口；速度改变动作周期。可见动作与松手判断密切相关，不能只顾读数好看。
- 截图显示追拍、水下、侧拍、俯视镜头并存。同一屏幕位置在不同镜头下可能遮住手臂、前方泳道或对手。
- 心率、体能、蓄气关系到操作选择，不能未验证就删掉。精确小数速度与长英文赞词是否必要，要另行判断。
- 现有赛中UI与联机/游戏更新解耦要求继续有效；视觉流畅不能以增加逐帧Graphics或Label重建换取。

## 对前两版的纠偏
1. 科幻边框改为圆角白卡只是换皮；白卡大面积高亮同样抢注意力。
2. 未验证就把速度移到左下不成立：它可能增加视线往返，也可能落在手指遮挡区。撤销“固定左下已经定稿”的假定。
3. 将心率、体能、蓄气、进度、名次做成同等重量，缺乏信息优先级。
4. 每次连击的大贴纸与动作观察竞争；不能用更大、更亮、更频繁证明有游戏感。
5. 生成图不能证明触控热区、读数时间、镜头适配或帧率表现；之前批量生成没有完成这些验证。

## 下一张典型画面的设计假设（待验证）
| 信息 | 玩家用它做什么 | 呈现假设 |
|---|---|---|
| 手臂动作/节奏反馈 | 决定何时松手 | 优先保护角色与动作周围视野；反馈靠近但不压住动作 |
| 体能 | 调整消耗与恢复 | 紧凑可扫读条；低体能时局部加强，避免始终强亮 |
| 心率 | 判断当前节奏区间 | 保留区间可读性；精确数值权重低于区间，但不擅自移除 |
| 蓄气 | 判断能否释放 | 清楚的就绪标记；就绪状态持续可查，出现瞬间可轻提示 |
| 进度/名次 | 判断赛事位置 | 边缘紧凑常驻，不反复抢视线 |
| 速度 | 了解运动变化 | 暂不定位置；对比靠近主视区与固定位置的扫视成本 |
| 评价/连击 | 确认操作质量和获得奖励感 | 短促、小幅、统一位置；不排队播放过时评价 |
| 完整排名 | 主动查看整体赛事 | 默认收起；展开区热区独立，收起后不留透明阻挡 |
| 赛事介绍/名单 | 赛前了解规则与选手 | 在非操作阶段可更充分展示，不把赛前卡片语言等比例搬进HUD |

“周边视觉能否读懂具体数字”不能预设；条长度、形状变化可作粗提示，精确数字依然需要注视。不能为了极简把信息藏得不可发现，也不能让UI频繁显隐导致位置记忆失效。固定槽位，变化的是强调程度。

## 单张原型的验证方式
- 用实际手机显示尺寸看，不以桌面大图清晰代替可读性。
- 在原图16上先标注角色手臂活动范围、前方泳道、双手握持可能遮挡区、微信系统安全区。区域来自实际画面和握持测试，不能臆造一个万能“中心禁区百分比”。
- 对比当前HUD与一张新灰度布局：同一角色/背景/动作，排除背景变亮带来的虚假改善。
- 用任务提问：当前能否释放？是否该恢复体能？目前第几？前方还剩多少？确认能读到所需信息又不丢失动作节奏。
- 观察漏松手、节奏中断、误点排名、界面挡手/挡人等现象。没有测试数据，不宣称“不影响操作”。
- 验证追拍、水下、侧拍、冲刺等相同组件的压力状态；这不是重新出多页美术稿。
- 触控必须测试按下在游戏区后滑入控件、松开/取消、双指、面板展开收起，避免卡住长按或把看排名算作划水。
- 最后再检查真机iOS微信小游戏帧率、UI更新频率与透明叠加成本。
