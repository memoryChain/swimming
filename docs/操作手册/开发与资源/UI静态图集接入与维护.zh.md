## 加载与性能

合图资源路径使用 `/spriteFrame`。`AvatarUiAssets.ts` 根据所属目录加载一次 `SpriteAtlas`，共用正在进行的请求和已加载缓存，再以文件名取子帧。生产构建缺图集或子帧直接报告失败，不回退为大量 CDN 散图下载；Creator 编辑器预览允许读取原 SpriteFrame，因为自动图集只在构建时生成。

进入页面时先准备所需图集。原有大厅／比赛资源屏障继续生效，首次角色页、头像弹窗和联机房间补齐页面门禁：冷加载期间使用不透明加载页，挂载和嵌套请求完成并经过两个渲染提交帧后展示。失败显示整页重试；取消后迟到回调只补缓存。热缓存且页面已准备好时同步展示，不重新创建加载页。

房间网络连接与美术加载并行。美术重试保留当前房间、成员与准备状态；不调用 `endGame`，不修改玩法、输入、随机种子或比赛同步格式。进入比赛、退出和房间失效会取消旧页面门禁。

合图减少纹理切换，实际 drawcall 仍取决于连续绘制顺序、材质、Mask、文字纹理和渲染层。HUD 状态底图集中放在文字之前，减少逐控件的纹理交错。图集数量不等于 drawcall 数；一次图集加载也可能包含配置、序列化元数据和一到多张纹理页请求。

共享图集／帧由资源缓存持有，节点不能销毁它们。九宫格和肖像局部裁切用 `source.clone()`，保留图集纹理、rect 和 UV，仅释放自己的克隆帧。裁切坐标要加上原子图的 rect 原点；不要用整张图集的宽高当子图尺寸。静态图集帧禁止再次进入动态图集。

### Creator 浏览器预览与角色列表

`.pac` 只在构建时生成纹理页，重开 Creator 不会让浏览器预览自动使用静态图集。预览回退的原 SpriteFrame 必须保留 `packable=true`，使用引擎默认动态合图；实际构建图集帧仍为 `false`。不能把构建帧的禁合图规则套到原图，也不强制打开微信包的动态合图或关闭图片缓存清理，避免 ASTC／内存策略失效。

角色列表的外层 stencil 只裁像素，无法停止视口外卡片提交绘制。列表在创建、滚动事件和重新显示时计算卡片与视口的交集，仅在变化时切换卡片 root 的 `active`，节点、选中状态、滚动位置和资源全部保留。初始 12 张卡片中显示 6 张，行间滚动最多 8 张；隐藏页面与暂存状态不做处理，不接入比赛逐帧更新。每张卡片仍保留圆角遮罩，避免性能修改导致肖像漏角。

角色页的状态驱动文字局部使用 `CacheMode.BITMAP`，缓存整段文本；动态合图启用且有容量时可合批，关闭或装不下时保留完整独立文字纹理。不能改成全项目 `CHAR`，其共享字符图集曾在多字体／字号／颜色组合下耗尽并漏字。微信构建的默认动态合图关闭，因此这一文字优化不能冒充微信真机收益。

已动态合图的源帧做局部裁切时，还须给克隆帧的 `original._x/_y` 加上局部裁切偏移，保留引擎恢复原纹理所需的原点；只能修改克隆，不改共用源帧。回归使用本机 3.8.8 的 `_resetDynamicAtlasFrame()`，覆盖冷帧、动态热缓存和构建图集帧。

### 比赛 HUD 的拆批与字符缓存

2026-10-01 对现有预览服务进行独立无界面 Chrome 测量，不截图、不保存临时比赛成绩。进入正式比赛后暂停模拟，渲染继续运行；在 `batcher2D.update()` 内、引擎清空批次之前读取 UI 批次数，在 `EVENT_AFTER_DRAW` 读取总 drawcall，每项取 30 帧。直接在 `AFTER_DRAW` 读 `batches.length` 会得到已清空的零，不能用于判定是否合图。

图片合批已生效：等待排行头像就绪后，主体 HUD 的 42 个有帧 Sprite 都进入同一动态图集；另外两个尚无评价图片的 Praise Sprite 不提交绘制。真实提交中圆环、直线填充、手掌和头像使用相同纹理、材质、buffer 与 stencil 状态，颜色和 FILLED 类型未额外拆批。主要问题是 24 个活跃 Label 使用 NONE 独立纹理，以及排行榜逐行「底圈→头像→数字」交错。

### 微信赛中头顶姓名／名次的名单纹理缓存

`SwimmerNameOverlay` 显示其他选手，本人沿用独立头顶指示。优化前每个名牌由一个静态 Graphics 圆底、一个 NONE 名次 Label、一个 NONE 昵称 Label 组成。圆底只在创建时绘制，没有逐帧重画，但 Graphics 自有模型会独立提交，数字与昵称也有独立纹理，所以每个完整名牌为 3 批。赛前没有名次时只提交昵称，每人 1 批。

独立临时比赛的最新冻结镜头中，投影／遮挡规则恰好没有可见对手名牌；正常为 66 次总提交、18 个 UI 批次，隐藏姓名层保持相同。仅在该临时实例强制七个名牌 root 提交后为 87 次、39 批，隐藏姓名层回到 66／18，证明七个完整名牌增加 21 批。这是强制提交的上界对照，不代表正常镜头始终显示七个；前述自然镜头只显示一个名牌时占 3 批。实际成本随镜头可见人数变化。

现已接入 `RosterNameAtlas`：每份比赛名单生成一次自己持有的纹理页，将完整昵称和 1–8 名次圆标放在同页，再以 Sprite 呈现。昵称仍用全覆盖系统字体，复制 Cocos Label 已生成的真实字形，不加入共享 CHAR；数字等待随包 SemiBold 字体加载完成再缓存。原 22px 紫色正圆在名单事件中绘制一次。子帧保留 Label 的实际几何、中心偏移和明确的 `originalSize`，防止把整页尺寸当成子图尺寸。投影、避让、缩放和显隐仍沿用原行为。

该页不依赖静态 UI 图集、CDN 或全局动态图集，适用于运行时才能确定的联机昵称。相同身份及展示名的名单复用页和节点；5Hz 权威名次更新只切 SpriteFrame，不绘图、不上传纹理、不写 Label。名单变化释放旧帧、Texture2D、ImageAsset 和 Canvas；所属根节点销毁也释放资源，字体的迟到回调核对名单版本。字体、画布或容量失败时保留完整原 Label，同名单可再次尝试。此层只消费既有名单与权威名次，不增加网络字段，不改变单机／联机比赛逻辑。

页面按 2px 透明留白排布，宽高为 2 的幂，最多 1024²；LINEAR、CLAMP、无 mip，所有帧 `packable=false`。当前七人名单通常为 64×512 或 128×256，RGBA GPU 数据约 128KiB，保留的 Canvas 像素约另 128KiB，不含对象及驱动开销；极限页单份像素数据为 4MiB。只在名单变化时构造，不在比赛更新路径复制像素。用户更名仍沿用 8 个 UTF-16 code unit 的截断预算，同时避免切开代理对。

## 日常维护

大厅内角色培养、联机房间和头像弹窗的共用 `UiPageLoadGate` 使用与联赛一致的透明居中转圈。`StartupLoadingCover` 的透明模式忽略数值进度，避免资源回调将转圈替换成底部进度条；失败显示点击重试，重新加载恢复转圈。启动模式仍保留原进度条。资源、嵌套绑定和布局等待、取消保护、热缓存直达以及房间网络并行均沿用原逻辑。

**替换已有图：** 继续修改原 PSD，通过对应导出脚本写入新目录，保留原 `.meta`；无需手工维护合成大图。PS 导出路径已通过共享映射更新，废弃金杯等旧资产不再恢复到运行时目录。

**新增图：** 放入实际共同展示的组，文件名必须唯一；跨页复用素材优先放 `common` 或现有专用公共组。大背景／大插画放独立目录。等待 Creator 生成 `.meta`，在 `ResourcePaths.ts` 登记调用路径，更新分组清单和页面测试。`config/ui-atlases.json.assets` 记录迁移身份，已有记录不得重新分配 UUID；新增素材不需要伪装成旧素材。

**改分组：** 同步图片及 `.meta`、`ResourcePaths.ts`、清单和相关导出入口。运行 `pnpm ui:atlases:sync` 重新生成 PS 路径映射，再检查资源完整性。不要按文件名在旧目录之间猜对应关系，同名 `panel`、`arrow`、`background` 必须根据原路径及 UUID 区分。

日常流程：

1. 在现有 Creator 会话等待新增／替换图片导入完成。
2. 执行 `pnpm textures:fix`，统一修复纹理压缩、图集配置、SpriteFrame 无裁切策略和 PS 映射。也可只运行 `pnpm ui:atlases:fix`。
3. 等待修改后的 `.meta` 再次导入，执行 `pnpm textures:check` 和对应页面测试；图集专项为 `pnpm test:ui-atlases`。
4. 用现有微信构建任务打包。当前任务须开启「合并自动图集」和「MD5 Cache」；共享配置 `config/build/wechatgame.json` 已开启，但旧任务需要自行导入共享配置或更新选项。

只改原图时无需另行运行手工图集生成命令，后续构建会自动重打受影响图集。构建钩子只做审计，缺 SpriteFrame、过期配置或错误采样会拒绝构建，不在构建过程中改资源或伪造导入元数据。图集采用 4px padding、双 bleed、禁止旋转、保留透明画布、不删除代码动态取用的帧、clamp 和无 mip，输出使用 UI ASTC 5×5 与 PNG 回退。
