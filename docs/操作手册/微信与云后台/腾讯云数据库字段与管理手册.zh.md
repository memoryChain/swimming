# 腾讯云数据库字段与管理手册

更新日期：2026-09-27。本次角色独立外观实现将玩家档案升级为 `schema = 7`，生涯结构仍为 `version = 1`。**此更新尚未部署；此前已部署的云函数使用 schema 6。** 以下新增外观字段在客户端和两套云函数同步更新后生效。

本文根据当前云函数实际读写和客户端数据定义编写，说明现有四个业务集合的全部字段及嵌套结构。不是未来赛季/排行榜设计，也不表示本次重新检查了线上每一条玩家记录。示例值只用于解释，除公开短 ID 示例外不引用完整玩家私有档案。

**日常查玩家先看 `players`，用顶层数字字段 `uid` 筛选。需要改的昵称、金币、角色等级都在 `profile` 里面。**

## 1. 先认识后台里的名词

| 后台名词 | 可以这样理解 |
|---|---|
| 集合（Collection） | 一类数据的文件夹，类似一张表，例如 `players` |
| 文档（Document） | 一份记录，例如一名玩家的整个档案 |
| 字段（Field） | 记录中的一项，例如金币 `coins` |
| 对象（Object） | 一组嵌套字段，例如展开 `profile` 才看到昵称、金币 |
| 数组（Array） | 一个列表，例如 `[0, 1]`、回执列表 |
| 字符串（String） | 文字，例如 `小虾2637`、`cartonSwimmer6` |
| 数字（Number） | 数量或编号，例如金币 `500`、短 ID `10000` |
| 布尔值（Boolean） | `true`/`false`，表示是/否 |
| `null` | 明确表示“没有”，例如当前没有待结算比赛 |
| `{}` / `[]` | 空对象/空列表，不等于档案损坏 |

`profile.characters.cartonSwimmer6.level` 表示：展开 `profile` → 展开 `characters` → 展开 `cartonSwimmer6` → 找到 `level`。不是新建一个名字带很多点的平级字段。

表中 `{角色ID}`、`[i]` 是说明用占位符：前者替换为角色实际 ID，后者代表数组中某一项。数组下标与赛事档位/轮次均从 **0** 开始。

操作建议标记：

- **可维护**：业务数据，按说明维护；不代表任何时候直接改都没有关联影响。
- **走管理操作**：需要同时处理版本、比赛状态或审计，优先使用已有管理云函数。
- **系统维护**：可以查看定位问题，不手动修改、复制、重置或删除。
- **兼容/预留**：当前玩法不使用，不靠修改它来开启功能。

## 2. 四个集合分别干什么

| 集合 | 中文含义 | 一条记录代表什么 | 平时需要看吗 |
|---|---|---|---|
| `players` | 玩家档案 | 一个微信游戏账号 | 主要查看这里 |
| `operations` | 玩家操作回执 | 一次成功提交的玩家写操作 | 排查重复请求、未到账时查看 |
| `adminAudit` | 管理修改记录 | 一次成功执行的管理写操作 | 查看谁改了什么、为什么改、前后数据 |
| `counters` | 发号计数器 | 当前只有 `playerUid` 这一条发号进度 | 通常不用操作 |

四个集合均拒绝普通客户端直接读写。云函数验证身份后访问；腾讯云控制台管理员可直接编辑，所以控制台并不会替你执行所有游戏规则。

这里没有独立的“角色表”：每个玩家的各角色等级存在其 `players.profile.characters` 下。这里也没有已上线的排行榜、赛季或成就集合；相关文档仍是设计。

## 3. `players` 顶层：账号与存档管理信息

| 字段 | 类型/示例 | 含义 | 操作建议 |
|---|---|---|---|
| `_id` | 字符串，64 位十六进制 | 数据库文档主键；当前与 `playerId` 相同 | 系统维护 |
| `playerId` | 字符串，64 位十六进制 | 内部账号标识，由 AppID 和可信微信 OPENID 计算得到；关联操作及管理记录 | 系统维护，不是玩家微信号 |
| `uid` | 数字，`10000` | 游戏给玩家展示的短 ID；当前环境内唯一，从 10000 起分配 | 系统维护；查人用它，不手动换号 |
| `profile` | 对象 | 玩家真正的昵称、金币、角色、生涯等资料，见后续章节 | 展开看具体字段，不整档覆盖 |
| `revision` | 非负整数，`1` | 存档写入版本；成功的新玩家写操作/管理写操作递增，用来防止旧请求覆盖新数据 | 系统维护，不是客户端版本或登录次数 |
| `createdAt` | 数字，毫秒时间戳 | 云端首次建档时间 | 系统维护 |
| `updatedAt` | 数字，毫秒时间戳 | 最近一次通过当前业务写入流程更新档案的时间 | 系统维护，不是最后登录时间 |
| `pendingWriter` | 字符串，空闲时 `""` | 当前待结算比赛所属的客户端写入标识，用于多设备冲突检查 | 系统维护；不是手机型号或账号 ID |
| `pendingAt` | 数字，空闲时 `0` | 当前赛事凭据签发时刻；用于 24 小时有效期与设备占用判断 | 系统维护；不是实际发令或完赛时刻 |

### 3.1 几种“ID”不要混淆

- **`uid`**：玩家给客服报的短 ID，如 `10000`。
- **`playerId` / `_id`**：内部长 ID，查回执、审计或调用现有管理函数时使用。
- **CloudBase 管理应用用户 UID**：此前创建/扫码授权的管理账号编号，和玩家短 ID 不是同一套。
- **`pendingWriter`**：客户端生成并保存在本地的写入标识，用于识别待结算比赛来源，不是不可伪造的硬件编号。
- **`race-…` / `cup-…`**：一场比赛/一届杯赛标识，不是用户 ID。

短 ID 是找人用的，不是登录口令。改昵称不会换 ID。直接删除玩家再建档可能领到新号，所以不能把删文档当成正常“重置养成”。

### 3.2 时间怎么看

`createdAt`、`updatedAt`、`pendingAt` 以及后文回执/审计中的 `createdAt`，都是从 1970-01-01 UTC 起累计的**毫秒**，通常为 13 位数字。例如 `1790427700289` 是一个时刻，不是等级或版本。换算成人类日期时选北京时间 UTC+8；不要把“秒”的 10 位值直接填进去。

`pendingAt = 0` 是没有待结算赛事的约定值，不表示玩家在 1970 年注册。`daily.date` 则是另一种格式的日期字符串，见第 8 节。

### 3.3 哪些操作不会改变 `revision` / `updatedAt`

普通读取、同一请求的重复重试、给旧档补分配短 ID，都不会按新业务修改再加一次版本。控制台直接编辑字段也不会自动递增它们。因此不能通过 `revision` 算比赛场数，也不能通过 `updatedAt` 判断最后登录时间或完整管理修改历史。

反过来，一次业务写请求成功受理但没有实际升级（例如金币不足），当前实现仍可能记录回执并递增版本。它表示处理次序，不是奖励次数。

## 4. `profile` 第一层：常用玩家资料

| 完整路径 | 类型/示例 | 含义 | 操作建议 |
|---|---|---|---|
| `profile.schema` | 整数，新版 `7` | 整份玩家档案的数据结构版本 | 系统将旧版 `6` 定向迁移；不要手动修改 |
| `profile.nickName` | 字符串，`小虾2637` | 游戏内昵称，不是微信真实昵称；不保证唯一 | 可维护，见昵称说明 |
| `profile.avatarId` | 字符串，`rose` | 游戏头像资源的稳定编号 | 可维护，只用第 7 节合法值 |
| `profile.coins` | 整数，`0`、`500` | 全账号共用金币余额；不是累计获得量 | 走管理操作；范围 0～1,000,000,000 |
| `profile.characterSelection` | 对象 | 最后确认使用的角色和外观 | 可维护其合法子字段，见第 6 节 |
| `profile.characterAppearances` | 对象，新版新增 | 以角色 ID 为键，分别保存每名角色的肤色和配色 | 外观真值，见第 6 节；不要整表覆盖 |
| `profile.characters` | 对象 | 以角色 ID 为键的培养档案 | 走管理操作修改等级；不要删除角色项 |
| `profile.career` | 对象 | 联赛、杯赛、待结算比赛和回执 | 见第 9～12 节，通常由规则维护 |
| `profile.daily` | 对象 | 预留的每日广告奖励日期/次数 | 当前不启用，保留即可 |

### 4.1 直接改名为什么有效

你在控制台改 `profile.nickName` 后，客户端下次成功拉取档案，就会显示新值。当前云端读档没有把自定义昵称强制重新改成随机名。

但当前游戏内的改名接口只接受“`小`＋指定动物＋1000～9999”这种随机昵称形式；后台自由编辑绕过了这个接口限制，不等于已经开放玩家自由输入昵称。游戏内后续随机改名会替换后台设置的名字。保持昵称为非空、简短文字，不填数字类型、对象或 `null`。

### 4.2 金币“设置”和“增加”的区别

直接编辑 `profile.coins = 500`，意思是**最终余额为 500**。原来 2000 会变成 500，不是变成 2500。

已有管理函数 `coins` 操作的 `delta = 500`，才是**在当前余额上加 500**；`delta = -500` 为扣 500。单次管理增减范围为正负 100 万且不能为 0，最终余额不得低于 0 或超过 10 亿。

### 5.1 角色 ID 对照

这些 ID 出现在等级、角色选择、杯赛、夺冠记录、赛事凭据和回执中，含义相同。英文 ID 是稳定存档键，不要替换成中文角色名。

|---|---|
| `cartonSwimmer6` | 蛙妹 |
| `cartonSwimmer8` | 蛙少 |
| `cartonSwimmer5` | 超级腿 |
| `cartonSwimmer9` | 猫姐 |
| `cartonSwimmer10` | 忍者哥 |
| `cartonSwimmer11` | 健身教练 |
| `cartonSwimmer12` | 飞毛腿 |
| `cartonSwimmer13` | 潜水哥 |
| `cartonSwimmer14` | 风火轮 |

### 5.2 每个角色下面的字段

下表中的 `{角色ID}` 例如 `cartonSwimmer6`。

| 路径 | 类型/示例 | 含义 | 操作建议 |
|---|---|---|---|
| `profile.characters.{角色ID}.level` | 整数，`1`～`30` | 该角色当前等级 | 走管理操作；不是账号等级 |
| `profile.characters.{角色ID}.signed` | 布尔值，默认 `false` | 旧签约兼容标记 | 兼容；当前 `false` 也能使用角色并金币升级 |
| `profile.characters.{角色ID}.signAds` | 整数，默认 `0` | 旧签约广告次数 | 兼容；旧档规范化范围 0～3，当前不消费 |
| `profile.characters.{角色ID}.adTokens` | 字符串数组，默认 `[]` | 旧签约广告凭据列表 | 兼容；本地旧档规范化最多保留 3 条；当前不发奖 |

例如要把蛙妹设为 10 级，目标是 `profile.characters.cartonSwimmer6.level`，不是把所有角色都改成 10。

等级为当前唯一培养数值；体力、技巧、爆发、技能效果等由角色配置与等级计算，不在每名玩家的数据库里分别存一套。这里没有当前经验值 `xp`，也不需要同时修改 `signed`。不要给档案凭空添加 `speed`、`stamina` 期待游戏生效。

## 6. 角色独立外观与当前出场快照

| 路径 | 类型/默认值 | 含义 | 操作建议 |
|---|---|---|---|
| `profile.characterSelection.characterId` | 字符串，默认 `cartonSwimmer6` | 最后确认选择的角色 | 使用第 5 节角色 ID |
| `profile.characterSelection.skinToneId` | 字符串，默认 `warm` | 肤色选项 | `warm`＝黄，`deep`＝黑 |
| `profile.characterSelection.colorSchemeId` | 字符串，默认 `red` | 服装/泳帽等模型支持的配色方案 | 使用下表 ID |

`characterSelection` 保留当前出场角色的快照，供比赛和联机使用。独立配色的真值新增在同一份玩家文档中：

```json
{
  "characterAppearances": {
    "cartonSwimmer14": { "skinToneId": "deep", "colorSchemeId": "blue" },
    "cartonSwimmer16": { "skinToneId": "warm", "colorSchemeId": "purple" }
  }
}
```

完整路径为 `profile.characterAppearances.{角色ID}.skinToneId` 和 `profile.characterAppearances.{角色ID}.colorSchemeId`。只存稳定 ID，不保存 RGB、纹理或材质副本；具体效果由客户端资源解释。选角色不会改变其他角色等级或接替它的杯赛。机甲coser 当前不支持换肤色，其肤色值固定为 `warm`。

- 色块点击只做本地预览，连续选择共用一个 1.2 秒计时器；停止改色后按角色合并提交最终肤色和配色，不逐次发送。回到已保存的外观无需写请求；切换角色仍保留各自草稿，试穿别的角色不会改变 `characterSelection.characterId`。
- 返回大厅或销毁角色页时立即提交剩余草稿并取消计时器。点击确认出场先调用 `selection`，同时保存该角色外观，再提交其他角色未保存的改动；已由 `selection` 保存的颜色不会重复提交。修改当前出场角色的颜色时，`appearance` 也会同步快照。
- 两个操作都只接收 `{ characterId, skinToneId, colorSchemeId }`，由服务器验证合法角色、肤色、配色；沿用事务、`revision` 冲突检查和 `operations` 幂等回执。客户端不能整表上传或顺带修改金币。
- 保存过程中仍可继续试色，服务器旧响应不能覆盖更新的本地草稿。失败会提示并保留草稿，后续换色、离开角色页或确认出场时重试；超时或响应丢失仍保留原请求 ID，在下一次读档时恢复。两设备冲突后重新读档再重试，不用旧整档覆盖另一个角色。尚未提交的草稿仅在本次进程中保留，强制关闭游戏前未发送的试选不保证恢复。
- 旧 schema 6 仅把最后选中角色的肤色和配色迁移到对应项；其他角色默认 `warm/red`。迁移到 7 时保留金币、已有等级、生涯、未结算票据和公开编号，补齐新增角色，业务版本递增一次。
- 官方控制台手动修改时，以独立外观表为准；若改的是当前出场角色，必须同时保持 `characterSelection` 中两项外观一致。只改旧快照会在客户端读取独立表时被覆盖。直接编辑仍须遵循第 3 节的停用账号和版本管理要求。

不增加集合、索引或客户端数据库权限，也不向联机房间发送整张配色表。

| 配色 ID | 名称 | 配色 ID | 名称 |
|---|---|---|---|
| `red` | 红 | `blue` | 蓝 |
| `yellow` | 黄 | `purple` | 紫 |
| `green` | 绿 | `orange` | 橙 |
| `cyan` | 青 | `black` | 黑 |
| `soft-lilac` | 柔藤紫 | `lime` | 青柠绿 |
| `lake-teal` | 湖水青 | `deep-ocean` | 深海蓝 |
| `cherry-red` | 樱桃红 | `strawberry-pink` | 草莓粉 |

外观接口会校验合法值，读入时部分错误选择会被规范化为默认值。不要依赖这种回退来修复错误，也不要用中文标签替代英文 ID。

## 7. `profile.avatarId`：头像编号

当前合法值，按头像选择面板的数据顺序排列：

| 顺序 | ID | 顺序 | ID |
|---|---|---|---|
| 1 | `aqua` | 6 | `rose` |
| 2 | `coral` | 7 | `teal` |
| 3 | `lime` | 8 | `sky` |
| 4 | `gold` | 9 | `frog-lime` |
| 5 | `violet` | 10 | `lifeguard` |

新档从合法头像中随机选一个，不是固定第一项。这些是历史保留的资源 ID，名字不能直接用来推断现在画面里的颜色或人物。改头像不会改变当前比赛角色或角色等级。

## 8. `profile.daily`：广告预留信息

| 路径 | 类型/示例 | 含义 | 当前状态 |
|---|---|---|---|
| `profile.daily.date` | 字符串，`2026-09-27` | 日广告计数对应的日期 | 预留，不是登录日志 |
| `profile.daily.adCount` | 非负整数，默认 `0` | 该日期内记录的广告奖励次数 | 微信正式广告发奖未启用 |

本地模拟后端曾有每日最多 10 次、每次 100 金币的规则，但微信云后端目前拒绝凭客户端广告回调发币。不要修改广告次数来测试发奖。

`todayString()` 使用执行环境本地日历日期；云端创建新档时会初始化这个值，当前云端普通 `load` 不走本地模拟的每日重置流程。因此看到旧日期或一直为 0 是可能的，不代表用户没登录或存档不同步，也不能据此宣称已有按北京时间运行的云端每日任务。

## 9. `profile.career`：账号生涯总览

| 路径 | 类型/默认值 | 含义 | 操作建议 |
|---|---|---|---|
| `profile.career.version` | 整数，当前 `1` | 生涯数据结构的内部版本 | 系统维护，**不是养成榜版本** |
| `profile.career.league` | 整数，默认 `0` | 账号当前最高已解锁的联赛档位，0～5 | 关联积分和杯赛，不孤立修改 |
| `profile.career.points` | 整数，默认 `0` | 当前联赛的晋级积分，0～100 | 满 100 开放本级杯赛；不是全服榜分数 |
| `profile.career.freeSigningUsed` | 布尔值，默认 `false` | 旧首次免费签约是否使用 | 兼容/预留，当前不参与培养资格 |
| `profile.career.cups` | 对象，默认 `{}` | 每角色当前/最近一届杯赛 | 第 10 节 |
| `profile.career.wins` | 对象，默认 `{}` | 各角色曾经赢过的杯赛档位列表 | 第 10 节；不是总胜场 |
| `profile.career.firstPrizes` | 数字数组，默认 `[]` | 历史设计中的首奖档位标记 | 兼容/预留，当前规则不填充发奖 |
| `profile.career.serial` | 非负整数，默认 `0` | 生涯内部创建赛事/杯赛用的流水计数 | 系统维护，不是比赛总场次 |
| `profile.career.pending` | `null` 或对象 | 当前账号唯一一场未结算比赛凭据 | 第 11 节；系统维护 |
| `profile.career.receipts` | 数组，默认 `[]` | 最近最多 32 条比赛结算摘要 | 第 12 节；不是完整战绩 |
| `profile.career.quick` | 对象 | 最近快速比赛的距离与规则偏好 | 合法值可维护 |
| `profile.career.quick.distance` | 数字，默认 `200` | 快速比赛距离，`200` 或 `400` 米 | 不改变已经签发的比赛 |
| `profile.career.quick.rule` | 字符串，默认 `wild` | `wild`＝狂野，`standard`＝标准 | 不改变正式生涯固定规则 |

### 9.1 联赛/杯赛档位对照

| 数据值 | 玩家看到的级别 | 杯赛轮数 | 距离顺序 |
|---:|---|---:|---|
| 0 | 泳馆新秀 | 2 | 200、200 米 |
| 1 | 俱乐部选手 | 2 | 200、200 米 |
| 2 | 城市精英 | 2 | 200、200 米 |
| 3 | 区域强者 | 3 | 200、200、400 米 |
| 4 | 全国大师 | 3 | 200、200、400 米 |
| 5 | 冠军级 | 3 | 200、200、400 米 |

联赛与积分属于账号，换角色仍共用；杯赛轮次和夺冠档位属于各角色。当前级别联赛完赛前四名积分为 20/14/10/6，100 封顶；回打低级联赛不增加当前积分。当前级别杯赛夺冠晋级时，`league` 加 1、`points` 归 0；最高级不再升到 6。

将 `league` 改为 5 不会自动补齐所有角色奖杯，将 `points` 改为 100 也不是“已经夺冠”。目前没有专门修复生涯的管理命令，需要具体设计关联修复，不能把改两行视作完整通关操作。

`serial` 在创建单场凭据时会增加，新建杯赛也增加；云端的单场 ID 又会被替换为随机 `race-UUID`。所以它既不是玩家数量，也不是简单累计局数。

## 10. `cups` 与 `wins`：角色杯赛

### 10.1 `profile.career.cups.{角色ID}`

没参加过杯赛的角色可以没有这一项；参赛后才建立。每个角色最多保存一届当前/最近杯赛，重新报名会替换这份杯赛状态，不是所有历史届次的列表。

| 子字段 | 类型/示例 | 含义 |
|---|---|---|
| `id` | 字符串，`cup-3` | 该账号内这一届杯赛标识；不是全服唯一玩家标识 |
| `tier` | 整数，0～5 | 这届杯赛所属档位，见上表 |
| `round` | 整数，0/1/2 | 当前待赛轮次；结束时保留最终所处轮次 |
| `seed` | 非负整数 | 本届杯赛的随机种子，供各轮派生比赛种子 |
| `state` | 字符串 | `active`＝进行中；`won`＝已夺冠；`lost`＝已淘汰/放弃 |
| `coins` | 非负整数 | 本届已经通过结算获得的金币累计，不是账号余额 |

以上全部由杯赛规则维护。`coins` 是记录，手改它不会给 `profile.coins` 发钱；把 `state` 改成 `won` 也不会自动执行金币、晋级和 `wins` 更新。

| `round` | 两轮杯（tier 0～2） | 三轮杯（tier 3～5） |
|---:|---|---|
| 0 | 预赛 | 预赛 |
| 1 | 决赛 | 半决赛 |
| 2 | 不合法 | 决赛 |

`active + round:1`：表示下一场应参加两轮杯的决赛，或三轮杯的半决赛。`lost + round:1`：表示本届在该轮结束，不是仍有资格续赛。预赛前四晋级，三轮杯半决赛前三晋级，决赛第一才夺冠。

当前冠军金币按档位为 60/70/80/90/100/120；预赛和半决赛没有常规金币。轮间可以培养该角色，但其他角色不能替赛。

### 10.2 `profile.career.wins.{角色ID}`

类型为数字数组。例如 `wins.cartonSwimmer6 = [0, 2]`，表示蛙妹曾赢过泳馆新秀和城市精英两档杯赛。**不表示第 0 名和第 2 名，也不表示赢了 2 场所有比赛。**

同一档赢多次只保留一个档位值；各角色分别记录。它不保存夺冠日期、当时等级、用时或重复次数。不能拿它直接生成精确历史排行榜。

## 11. `profile.career.pending`：未结算赛事凭据

空闲时为 `null`；开赛前云端建立对象，正常结算后清为 `null`。杯赛轮间可以是 `cups.{角色ID}.state = active` 同时 `pending = null`：说明杯赛还没结束，但当前没有正在等待结算的一轮，完全正常。

### 11.1 凭据本体

| 子字段 | 类型/示例 | 含义 |
|---|---|---|
| `id` | 字符串，`race-…` | 服务器生成的单场唯一凭据；结算必须匹配 |
| `source` | 字符串 | `quick` 快速比赛、`league` 联赛、`cup` 杯赛 |
| `characterId` | 字符串 | 本场参赛角色 ID |
| `level` | 整数，1～30 | 本场开赛时角色等级快照，之后升级不应改它 |
| `distance` | 数字，200/400 | 本场距离（米） |
| `rule` | 字符串，standard/wild | 本场标准/狂野规则；联赛杯赛当前固定狂野 |
| `tier` | 整数，0～5 | 凭据携带的赛事档位；快速比赛仍有此字段，但不代表它是晋级联赛 |
| `round` | 整数 | 杯赛本轮下标；非杯赛通常为 0 |
| `cupId` | 可选字符串 | 杯赛关联哪一届，匹配该角色 `cups` 中的 `id`；非杯赛通常省略 |
| `seed` | 非负整数 | 这一场的随机种子；杯赛由本届种子与轮次派生 |
| `ai` | 对象 | 服务器给本场确定的 AI 配置，见下表 |
| `championCoins` | 可选整数 | 杯赛凭据带的冠军金币数快照；非杯赛不使用，未夺冠不会发 |

这不是待发奖励清单，也不是完整对局录像。不要改凭据的等级、种子、距离、ID 或 AI 来替玩家加强角色/降低对手；结算会关联它判断结果。

### 11.2 `pending.ai` 的全部字段

| 子字段 | 类型 | 含义 |
|---|---|---|
| `minLevel` | 整数，1～30 | 本场 AI 等级下限 |
| `maxLevel` | 整数，1～30 | AI 等级上限，不小于下限 |
| `intelligence` | 字符串数组 | 每名 AI 的行为难度名额；当前支持 1～7 名对手 |
| `opponentCount` | 可选整数 | AI 人数，不含玩家本人；填写时与 `intelligence` 长度一致 |
| `characterWeights` | 可选对象数组 | AI 角色抽选池；正式生涯配置中可出现，快速比赛可能没有 |
| `characterWeights[i].characterId` | 字符串 | 候选角色 ID，与第 5 节一致 |
| `characterWeights[i].weight` | 非负数字 | 相对抽取权重，0 表示不出现；不是百分比，总和不要求 100 |

`intelligence[i]`：`rookie`＝新手，`normal`＝普通，`skilled`＝高手，`expert`＝专家，`extreme`＝极限测试档（界面“变态（测试）”），不是正式生涯推荐配置。

例如 `['rookie','normal','expert']` 是三名 AI 加一名玩家，不是同一个 AI 的三个属性。AI 角色按池独立抽选，可以出现重复角色。`ai` 中保存的是配置范围/名额，不是每位最终泳者的完整已实例化数据。

### 11.3 卡在未结算时怎么处理

`pending`、顶层 `pendingWriter` 和 `pendingAt` 是一组关联状态；只清掉其中一个可能让后续请求异常。正常清理由结算流程完成；确实需要运营处理时使用已有 `clearPending` 管理操作，它会同时处理这些字段、递增版本并留审计。

该操作会令原比赛凭据失效；杯赛本身的 `cups` 轮次保留，可重新开始该轮。`pending` 不等于断线可跨设备接管比赛进度；另一设备在占用有效期内开赛可能收到 `BUSY`。

## 12. `profile.career.receipts`：最近结算摘要

每一项结构如下，最多保留最近 32 条：

| `receipts[i]` 子字段 | 类型 | 含义 |
|---|---|---|
| `id` | 字符串 | 已结算的单场比赛凭据 ID |
| `characterId` | 字符串 | 本场角色 ID |
| `coinsGained` | 非负整数 | 本次结算实际增加的金币总数 |
| `regular` | 非负整数 | 常规金币部分；杯赛夺冠时这里也承载冠军金币 |
| `podium` | 数字，当前通常 `0` | 历史设计中的额外领奖台奖励分项，当前结算初始化为 0 |
| `first` | 数字，当前通常 `0` | 历史设计中的首次奖励分项，当前结算初始化为 0 |
| `points` | 非负整数 | 本场实际增加的联赛积分，不是当前积分总额 |
| `message` | 字符串 | 结算说明，如“已晋级决赛，可稍后继续” |

当前金币合计为 `regular + podium + first`。普通比赛名次奖励已经计入 `regular`，不能因为 `podium = 0` 就说前三名没奖励。

回执不是钱包：修改 `coinsGained` 不会补发金币，修改 `points` 不会自动修复联赛积分。回执也没有持久保存完赛用时、名次、距离、判定统计或完整日期，不应当成全量战绩/排行榜数据。不要删除回执来“再领一次”。

## 13. `operations`：玩家写操作回执

这是防重复扣币/发奖的系统账本，区别于只保留 32 条的生涯展示摘要。成功的玩家写操作生成记录；普通 `load` 读取不生成。明确拒绝的请求通常不生成，但业务成功受理后报告“金币不足”等结果仍可能有回执。

### 13.1 顶层全部字段

| 字段 | 类型 | 含义 |
|---|---|---|
| `_id` | 64 位十六进制字符串 | 根据 `playerId + requestId` 计算的操作文档 ID |
| `playerId` | 字符串 | 所属玩家内部长 ID；查短 ID 后用这个关联 |
| `requestId` | 字符串 | 客户端为一次操作生成的唯一请求号；网络重试沿用 |
| `fingerprint` | 64 位十六进制字符串 | 请求内容摘要，防止同一个请求号被换内容重用；不是可还原请求的明文 |
| `result` | 对象 | 当时操作的返回结果，类型见下节 |
| `revision` | 非负整数 | 此操作处理后写入的玩家版本；可能早于玩家当前版本 |
| `createdAt` | 毫秒时间戳 | 这条操作首次成功写入的时间 |

全部系统维护。删除这些记录可能破坏去重保障；不能为了后台“看着清爽”清空。

**这里当前没有独立保存 `action`、完整 `data`、`writerId` 或完整原始结算参数。** 不能仅凭回执证明每笔完整业务输入；昵称/外观操作 `result = {}` 时也不能仅从此对象精确区分是哪种操作。

### 13.2 `result` 可能有哪些子字段

| 操作类型 | `result` 内容 |
|---|---|
| 保存昵称/头像 | `{}`，档案改动存在 `players` |
| 保存角色/外观 | `{}` |
| 金币升级 | `ok`、`levelsGained`、`coinsSpent`，可能有 `reason` |
| 生涯开始 | `ok`、`message`、`ticket` |
| 生涯结算 | `ok`、`message`、`receipt` |
| 放弃杯赛 | `ok`、`message` |

| 子字段 | 类型/值 | 解释 |
|---|---|---|
| `result.ok` | 布尔值 | 业务动作是否达成；升级金币不足时可为 false，但请求已受理留回执 |
| `result.levelsGained` | 非负整数 | 这次升了几级，不是角色最终等级 |
| `result.coinsSpent` | 非负整数 | 这次实际扣了多少金币，不是当前余额 |
| `result.reason` | 可选字符串 | `maxed` 已到等级上限；`insufficient` 金币不足 |
| `result.message` | 可选字符串 | 生涯动作的中文说明 |
| `result.ticket` | 可选对象 | 当时签发的赛事凭据，全部子字段同第 11 节 |
| `result.receipt` | 可选对象 | 当时结算的奖励摘要，全部子字段同第 12 节 |

`result` 不再包含整份 `profile`。`operations.result.ticket` 中的凭据是历史回执，不代表玩家现在仍在这场比赛；是否待结算应看最新 `players.profile.career.pending`。

客户端 API 外层也有一个 `ok`，表达请求是否被云端正常处理；它不等于 `result.ok` 的升级是否成功。金币不足时可能外层成功、内层 false、没有扣币。

## 14. `adminAudit`：管理员修改历史

| 字段 | 类型 | 含义 |
|---|---|---|
| `_id` | 64 位十六进制字符串 | 管理审计 ID，根据操作者与请求号生成 |
| `playerId` | 字符串 | 被修改玩家的内部长 ID |
| `actor` | 字符串 | 操作者；小游戏管理员为其内部玩家 ID，管理应用账号为 `web:用户UID` |
| `fingerprint` | 字符串 | 管理请求内容摘要，防同请求号换内容重复执行 |
| `requestId` | 字符串 | 这一次管理操作的请求号 |
| `action` | 字符串 | 管理操作种类，见下表 |
| `reason` | 字符串 | 管理员填写的修改原因；当前要求 2～200 字符且非全空白 |
| `before` | 对象 | 修改前完整 `profile` 快照，子字段同第 4～12 节 |
| `after` | 对象 | 修改后完整 `profile` 快照，子字段同第 4～12 节 |
| `revision` | 非负整数 | 此次管理修改后的存档版本 |
| `createdAt` | 毫秒时间戳 | 此次管理修改时间 |

| `action` | 含义 | 具体效果 |
|---|---|---|
| `coins` | 增减金币 | 在当前余额上加减，不是把总额设置为 delta |
| `level` | 修改角色等级 | 将指定角色设为目标等级，不自动扣升级金币 |
| `clearPending` | 清理未结算赛事 | 原凭据失效，保留杯赛进度供重开 |
| `restore` | 恢复某条管理审计的修改前档案 | 恢复该玩家的 `before`，不是任意日期回档 |

`inspect`、`search`、`history`、`me` 等读取操作不创建管理写审计。集合为空可能只是还没执行过管理函数写入。

**你在腾讯云数据库页面直接修改昵称或金币，不会自动生成这里的记录。** 腾讯云自身如有平台审计，也不等于游戏 `adminAudit` 的业务快照。

`before`/`after` 只有 `profile`，不包含顶层 `uid`、`playerId`、`pendingWriter`、`pendingAt` 或原始顶层版本。因此管理恢复不会回滚短 ID；恢复时还会保留不倒退的生涯 `serial`，并统一清理待结算。

所有现有管理写操作都会清空当前比赛凭据及对应占用信息、递增版本、保存审计。处理前让玩家结束比赛并退出游戏，避免其正在玩的场次结算失效。

`delta`、目标等级和用于恢复的源审计 ID 当前不作为独立顶层字段保存，主要通过 `before/after` 对比看变化；`fingerprint` 不能反解这些原始参数。`restore` 的快照可能同时覆盖其后的正常游戏进度，不是只“反向撤销一次加币”，需要先核对。

## 15. `counters`：短 ID 发号器

当前业务只使用这一条记录：

| 字段 | 值/类型 | 含义 |
|---|---|---|
| `_id` | 字符串，固定 `playerUid` | 玩家短 ID 计数器的文档名字 |
| `lastUid` | 数字，例如 `10000` | 已分配到的最后一个短 ID，下一位尝试分配 `lastUid + 1` |

首次初始化是 `9999`，所以首位玩家获得 `10000`。**9999 是建库时的初值，不是维护时应该恢复的值。已有玩家后绝不能重置为 9999、调小或删除。**

系统在同一事务里更新计数器和玩家 `uid`，避免两人领同一号。计数器丢失会拒绝新建/补号，不会自动从头发号。`lastUid` 不是当前玩家人数，删除过玩家、环境迁移等情况都会让这种人数推算不可靠。

## 16. 哪些东西不在这些表里

| 你可能想找的东西 | 当前在哪里/当前状态 |
|---|---|
| 管理员名单 | `swimming-admin` 云函数环境变量 `ADMIN_PLAYER_IDS`、`ADMIN_WEB_USER_IDS`；不是给 players 加 `isAdmin` |
| 腾讯云账号密码/扫码登录权限 | 腾讯云或 CloudBase 身份系统；不在玩家 profile 中 |
| 角色基础体力、技巧、爆发、能力配置 | 游戏/云规则源码配置；玩家表主要保存等级 |
| 音量 | 客户端本地设置，不是云端玩家档案字段 |
| 完整比赛成绩、历年纪录 | 当前没有完整持久战绩模型，32 条奖励回执不能代替 |
| 统一配置 `clientVersion`、`quickRankVersion`、`seasonVersion` | 还在设计阶段，当前数据库未接入；不是 `schema`、`revision` 或 `career.version`，详见[统一版本配置设计](../../游戏设计/后续提案/统一版本配置与生涯赛季数据设计.zh.md) |
| 赛季、成就、排名 | 设计阶段，本文不把拟建字段冒充已存在字段 |
| 最后登录时间/在线状态 | 当前没有专门字段；不要用 updatedAt 或 daily.date 代替 |

上述只是位置说明，不需要把密码或密钥写进玩家表。现有函数响应里的 `auditId`、`nextOffset`、`items`、`code` 等是 API 返回字段，不能据此在数据库文档里新建同名字段。

若控制台还显示本手册未列出的 `_openid` 或其他系统字段，先辨别是否平台自动字段、历史导入或其他功能集合；当前这四个集合的业务写入不主动创建 `_openid`，不要套用为本项目的登录关联字段。

## 17. 按操作查字段

### 17.1 找到一个玩家

打开 [players 玩家存档](https://tcb.cloud.tencent.com/dev?envId=cloud1-d5gn11660fac3375c#/db/doc/collection/flexdb/tnt-9cyjcvd8c/players) →「筛选」→ 字段 `uid` → 类型“数字”→ 等于 `10000`。

不要搜 `profile.uid`，也不要把数字写成字符串。核对昵称及短 ID；昵称可能重复。查 `operations` 或 `adminAudit` 时，再使用该档案的内部 `playerId` 筛选，因为这两个集合当前不冗余存短 ID。

### 17.2 改昵称

1. 让玩家先退出游戏，避免旧界面的编辑草稿随后覆盖昵称。
2. 在 `players` 中展开 `profile`，编辑 `nickName`，类型保持字符串。
3. 保存后让玩家重新进入；或在已加载成功的大厅切后台再回来，等待云端刷新。
4. 这是数据库直接编辑，不会生成 `adminAudit`。需要改前/改后记录时单独保存原值。

### 17.3 改金币、改角色等级

金币字段 `profile.coins`；蛙妹等级字段 `profile.characters.cartonSwimmer6.level`。金币填非负整数，等级填 1～30 的整数。控制台字段编辑是目标总值，不是增加量。

正式补偿优先走已有管理函数，留原因、版本检查和前后审计，步骤见[微信云存档部署与后台操作](微信云存档部署与后台操作.zh.md)。不要自己再手动补改 `revision` 来模拟事务；多字段逐个保存仍可能被并发请求插入。

直接编辑不自动撤销旧比赛，不自动扣升级费，不自动改杯赛/回执。玩家应先结束比赛并退出；修改后读回确认，再让玩家重新进入。若没有待结算比赛，预期同时看到 `pending = null`、`pendingWriter = ""`、`pendingAt = 0`，有不一致先排查，不靠单独改一个字段消除。

### 17.4 看某角色生涯进度

先看账号 `career.league/points`，再看 `career.cups.{角色ID}` 的档位、状态和轮次，最后看 `career.wins.{角色ID}` 的永久通关列表。三者含义不同，不能只看其中一个判断“这个账号全部通关”。

### 17.5 想清档、回档或批量改

目前没有通用清档、批量任务或任意时点回档功能。不要删除 `players`、清空 `operations` 或回退 `counters` 来实现。已有 `restore` 仅基于管理快照；批量修改、全服补偿另做带目标名单与防重复机制的业务操作，不能通过批量导入覆盖整档当作补偿。

## 18. 修改后什么时候同步到游戏

| 场景 | 当前行为 |
|---|---|
| 新启动游戏、准备进入大厅 | 拉取云端存档 |
| 已加载成功的大厅切后台再回来 | 拉取云端；加载中/已进入房间等状态有门控 |
| 进入好友房间 | 先刷新角色资料 |
| 正常升级、修改身份/选择、开始或结算生涯 | 成功后取得云端返回的最新档案 |
| 正在比赛中切回前台 | 不通过大厅回调刷新，不中途替换比赛属性 |
| 已在好友房间切回前台 | 不通过大厅回调刷新当前房间快照 |
| 一直停在大厅不操作 | 没有持续推送或轮询，需要下一次触发刷新 |

需要网络成功；当前弱网失败没有持续轮询重试。同步是存档数据同步，不是另一设备半局比赛的接管。代码行为已核对，双设备前后台切换仍应实测验收。

## 19. 最常见的误解

| 看到的情况 | 正确理解 |
|---|---|
| `signed = false` | 当前仍可升级，不需要手动签约 |
| `daily.date` 很旧 | 预留广告日期，不表示存档很久没同步 |
| `wins = [0,1]` | 赢过两种杯级，不是两场总胜场或第 0/1 名 |
| `cups.coins = 120` | 该届杯赛已得金币记录，不是账号余额 |
| `pending = null` 但杯赛 active | 轮间正常状态，没有正在待结算的单场 |
| `operations.result = {}` | 身份/外观操作可以没有额外返回内容，不代表损坏 |
| `adminAudit` 是空的，但后台改过名字 | 控制台直改不会自动产生游戏管理审计 |
| 读档成功但 `updatedAt` 没变 | 正常读取不会写更新时间 |
| 想换养成榜版本 | 目前设计未实现，不改任何现有 version 字段代替 |
| 想发金币而编辑回执金额 | 回执是记录，改它不会执行发奖 |
