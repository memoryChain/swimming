# 云端开发隔离与版本兼容

实施日期：2026-10-03。本项目复用已经购买的云环境 `cloud1-d5gn11660fac3375c`（`ap-shanghai`），没有购买第二套云环境，也没有新增订单。开发和正式共用套餐额度，通过云函数入口、数据库集合、本地缓存和房间握手隔离。套餐容量、调用量与费用仍需合并观察。

云端发布和客户端构建是两个步骤。本次已发布云函数；新客户端的开发/正式分流和房间隔离必须随下一次 Creator 构建生效。源码当前选择 `development`，已有 `build/wechatgame` 属于旧构建，不能直接视为本次可提审包。

## 1. 当前入口与数据归属

公开配置在 `config/cloud-environments.json`，自动生成的客户端配置在 `assets/scripts/backend/WechatCloudConfig.ts`。环境 ID 可以入库，凭据和管理员名单不可以。

| 用途 | 玩家入口 | 管理入口 | 集合前缀 | 客户端构建目录 |
|---|---|---|---|---|
| 日常开发测试 | `swimming-player-dev-v3` | `swimming-admin-dev-v3` | `dev_` | `build/wechatgame-development/` |
| 新正式版及其提审包 | `swimming-player-v3` | `swimming-admin-v3` | 空 | `build/wechatgame/` |
| 已发布旧客户端的兼容入口 | `swimming-player` | `swimming-admin` | 空 | 沿用旧客户端已有配置 |

开发数据库使用 `dev_players`、`dev_operations`、`dev_adminAudit`、`dev_counters`、`dev_gameConfig`；正式继续使用 `players`、`operations`、`adminAudit`、`counters`、`gameConfig`。五个开发集合均为 `ADMINONLY`，客户端不可直接读写。

集合前缀固定在服务端部署包中，客户端传入 `target` 或 `collectionPrefix` 不能切换数据库。事务内也按同一前缀访问。玩家 ID 的计算方式与正式集合名不变，原正式存档无需搬迁。

本地正式缓存继续使用原 `swimming.cloud.<环境ID>` 命名空间，保留历史 outbox。开发缓存追加 `.dev_`，开发和正式各自持有 writer、档案、待发送操作和教学状态。公开短 ID 由各自计数器独立发号，不能用相同 uid 判断两个范围的玩家是同一份存档。

首次开发初始化使用仅在文档不存在时写入的方式：

```json
{"_id":"playerUid","lastUid":9999}
```

写入 `dev_counters/playerUid`；`dev_gameConfig/global` 初始为：

```json
{"_id":"global","tutorialEnabled":false}
```

正式计数器、教学开关和玩家存档未在本次初始化中修改。开始发号后不得重置开发计数器；教学开关也须明确选中开发或正式集合再修改。

## 2. 日常开发流程

在仓库根目录执行：

```sh
pnpm cloud:configure development
pnpm cloud:build development
pnpm cloud:deploy development
pnpm cloud:deploy development --apply
```

`cloud:configure` 更新源码目标，生成 `config/build/wechatgame-development.json` 和本机根目录 `project.config.json`。后者指向开发小游戏输出及 `cloud/functions/development/`。`cloud:build` 只生成两套开发入口；`cloud:deploy` 不带 `--apply` 时只校验发布计划，带参数才实际上传。

使用已有官方 CloudBase CLI 登录态。发布脚本先核对环境、入口白名单、服务端集合前缀和源码摘要，备份所有将被更新的函数，随后上传，最后下载线上包逐文件比对。失败时依据已打印结果和备份核查，不能把部分成功视为整个发布完成。

Creator 导入 `config/build/wechatgame-development.json`，等待配置源码导入后重新构建。构建钩子要求源码目标与输出目录一致，写入包含实际游戏脚本摘要的 `cloud-release.json`。构建完成后执行：

```sh
pnpm cloud:check development build/wechatgame-development
```

微信开发者工具导入仓库根目录项目，确认小游戏目录指向开发输出。开发版本登录后产生 `dev_players` 档案，不会继承正式金币和生涯进度；这是隔离后的正常行为。不要把旧 `build/wechatgame` 内的 JS 手改成开发目标。

## 3. 提审与正式发布

提审包从构建时起就连接正式入口，审核期间与上线后使用同一份正式存档。不能按运行时的体验版/正式版身份自动切数据库，否则审核与发布会改变账号数据归属。

```sh
pnpm cloud:configure production
pnpm cloud:build production
pnpm cloud:deploy production
pnpm cloud:deploy production --apply
```

Creator 导入 `config/build/wechatgame-production.json`，等待源码导入后重新构建。上传提审前检查实际构建：

```sh
pnpm cloud:check production build/wechatgame
```

检查会核对包内实际编译进去的公开目标标识及脚本摘要，拒绝开发包、旧构建和构建后被修改的脚本。仅检查源码不能代替检查上传目录。小游戏提交审核、正式发布和 iOS/Android 验收属于客户端发布流程。

正式输出和开发输出分开保留。完成提审构建后，日常开发恢复：

```sh
pnpm cloud:configure development
```

无需为恢复开发目标覆盖任何正式函数，也不要将生产档案复制到开发集合来省去建档步骤。

## 4. 已发布客户端如何兼容

2026-10-02 的原入口规则 3 更新曾拒绝规则 2 客户端的新操作。本次原入口恢复规则 2/3 兼容，规则 2 继续读档、换装、升级、开赛和结算；已经使用原入口的规则 3 客户端也继续工作。规则 1 不在本次兼容范围内。

规则 2 生涯和升级价格冻结在 `cloud/compat/v2`，来自已备份的真实旧线上包。兼容入口按请求规则选择新操作的执行规则，避免旧客户端展示旧价格、服务端却按新价格扣款。旧客户端继续旧经济规则属于当前兼容策略；调整该策略须单独设计迁移与提示。

新签发赛事票据记录服务端 `rulesVersion`，结算按票据选择规则。历史无标记票据以 `terms` 是否存在区分规则 3/2。规则 2 客户端不能结算规则 3 票据，新版可以补结算仍有效的旧票据，奖金和晋级仍按原票据规则执行。客户端传入的票据版本不能改变奖励。

各正式入口共享原玩家档案、事务版本和幂等回执，同账号跨版本并发仍由 revision 保护。重复原 requestId 不重复扣款或发奖。版本 3 入口拒绝规则 2 的新操作，仅允许恢复已提交回执和补结算有效旧票据。

日常正式打包不包含原入口。只有维护规则 2/3 兼容修复时才显式执行：

```sh
pnpm cloud:build production --compatibility
pnpm cloud:deploy production --compatibility
pnpm cloud:deploy production --compatibility --apply
```

脚本限制兼容包只能在当前规则 3 下生成，未来规则 4 不得覆盖原规则 2/3 入口。普通部署还会拒绝包含额外旧入口的清单；执行过兼容打包后，日常发布须重新运行普通 `cloud:build production`。

后续经济规则升级先建立新的版本入口，完成既有票据和存档迁移兼容测试，再让新客户端连接；旧版本函数继续保留。数据库 schema 的改变也必须兼容仍在使用旧入口的客户端，函数改名本身不能解决共享存档字段的破坏性变更。

### 故障与回退

两套函数依次上传，发布不是数据库事务。失败后先查看输出中哪些入口已完成，再核对 `.cache/cloud-backups/isolation-<目标>-<随机标识>/before`、`after`；全部完成后才会生成 `result.json`。通过修复源码、重新打包和核验后继续发布，不能跳过摘要检查。

回退同一规则版本的故障修复时，使用该入口最近一次已经验证的完整代码包和原依赖安装方式，只更新对应函数代码并重新下载比对。新版本入口尚未有上线客户端时，可让未发布客户端恢复连接既有稳定入口并重新构建。已有新版客户端上线后，必须保留它的入口并做兼容修复，不能删除入口迫使玩家重装。

本次原入口的 `before` 快照正是会拒绝规则 2 客户端的故障版本，不能把整份发布前备份直接恢复为线上。稳定兼容基线是本次 `after/swimming-player`、`after/swimming-admin`。数据库回档与函数代码回退不同，不随代码回退重置玩家档、计数器、revision 或操作回执；需要数据回档时另行设计一致性恢复。

## 5. 联机影响

联机玩法协议从 52 升至 53。大厅 `PV` 声明携带 `环境ID:数据范围:r经济版本`，开赛消息再校验 `cloudScope`。同房成员必须同时满足玩法版本和云数据范围一致，开发档与正式档不能混房；缺少范围的旧客户端也不能与新版共同准备或开赛。

这些校验位于大厅事件，不增加比赛逐帧工作。比赛权威校正、SharedRNG、单机路径和保活重赛沿用原机制。云存档兼容不意味着不同玩法版本可以混跑；旧客户端仍可与同版客户端联机。跨范围提示、邀请进房和双端重赛须在新客户端真机验收中检查。
