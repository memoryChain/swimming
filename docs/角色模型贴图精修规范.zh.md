# 角色模型贴图精修规范

版本：1.1；日期：2026-09-06。

适用范围：已确认设计的带骨骼 GLB／GLTF 角色，导入前源贴图精修，以及任务包含游戏接入时的换色／换肤交付验收。

## 1. 核心标准与优先级

**保留设计，把颜色边界绘制清晰；去掉已确认的污染，不靠删减、扩散模糊或涂成大色块来掩盖问题。**

以用户当前确认的角色设计、原始模型及具体修正要求为依据。本规范补充[现行角色设计规范](蛙蛙男女标准角色设计规范.zh.md)，不改变角色身份、造型或生产预算。

- 精修不是重新设计。领口、接缝、滚边、反光条、拉链、背带、鞋面分色、设备屏幕和挂件图案等，只要属于已确认设计，都应保留位置、宽度关系、形状与可辨识度。
- 设计规范中的小装饰删除／合并建议用于新设计与预算收敛，不能直接作为删除现有已确认细节的依据。若运行预算内无法保真，单独提出调整建议。
- 不把绿色一概判为噪点。已指定为换色标记的绿色块保留其换色语义，固定绿色点缀仍保持固定色；只有结合原稿、模型位置与邻接关系确认的孤立污染才清除。
- 修复只处理已核实区域。不得顺带改变皮肤、五官、发型、配件、点缀色或衣片结构。

## 2. 先分类，再决定修法

| 问题 | 判别依据 | 处理范围 |
| --- | --- | --- |
| 底色脏污／颜色毛边 | 无光照底色仍有杂色、断线、溢色 | 局部重绘与边界校正，保留正常明暗 |
| 跨 UV 错色／采样接缝 | 相邻模型面本应连续，图集边缘、岛间采样或缩图后出现断裂 | 核查配准、岛边扩边、过滤与跨面连续性 |
| 灯光／法线／AO 问题 | 更换中性材质、灯光或视角后明显变化 | 修相应渲染来源，不直接涂掉底色 |
| 真实几何切面／凹口 | 轮廓与网格本身存在转折，如袜褶、发束、鞋底槽 | 保留正常结构；需改网格时另列范围并走模型流程 |

不得把“切面锯齿”统一解释成分辨率不足。整张生成图集与原 UV 的微小错位，也可能让三角面两侧采到不同颜色；只看平面贴图变清晰不能证明模型修好了。

## 3. 执行顺序

1. 保留原始源、最近确认版及新工作版；记录文件名与 SHA-256，不覆盖唯一来源。
2. 审计模型轴向、尺度、网格、三角面、材质、纹理尺寸、UV、骨骼、蒙皮与动画信息。拍摄中性底色及正常光照基线。
3. 按身体部位列出“要修区域／必须保护的设计／本次不改项”，不直接对整张图做无约束处理。
4. 从原始图与已确认版本选择可靠内容，局部恢复设计边界和中性色。修复后的颜色随模型曲面连续，不按 UV 三角块逐块换成不同来源。
5. 将候选贴回同一个模型，以同机位、同材质、同灯光比较。必要时迭代局部边界，不能以整张模糊代替。
6. 打包独立版本，重新导入核验；记录已通过、未验证和残留问题，再交付。

源贴图精修、运行时换色和游戏资源替换是不同任务。只请求清理源模型时，不自动制作新运行时逻辑、替换游戏角色或上传外部平台。

### 游戏角色肤色切换：默认交付项

用户于2026-09-06明确要求：角色需要换肤。今后新增或替换人形角色进入游戏，默认同时交付服装换色与肤色切换，不再等待逐个提出换肤要求；只做源模型精修仍不自动安装到游戏。

- 不能因旧槽位设有 `supportsSkinTone: false` 就照搬关闭，也不能把“保留角色属性”解释为保留缺失的外观功能。身份、数值、动作与大小仍按原授权保持。
- 肤色开关、与当前模型UV匹配的皮肤遮罩、实际材质换肤必须一起完成。现行 `assets/race/effects/SwimmerDynamicColor.effect` 的遮罩模式使用R控制服装／指定装备、G控制帽子、B控制皮肤；B全零时不能宣称支持换肤，单改开关不算完成。
- 皮肤遮罩覆盖脸、耳、颈、手臂、手及其他实际露肤区域，保留五官和正常明暗；头发、眼镜、服装、装备与固定图案不得串色。源肤色保留为可选原色，不能为了换肤直接把源皮肤涂平。
- 若机甲等角色确无可换肤区域，或UV／材质问题使换肤无法安全实现，说明原因并确认例外或调整范围；不得自行关闭换肤、增加材质／分辨率或重排UV来跳过验收。

### 批量精修与授权后自动接入

用户在 2026-09-06 明确授权：所提供批次可以并行精修，完成检查后直接替换进游戏，不再逐个等待外观审核。该授权取消的是人工确认等待，不取消设计保真、身份核对、动作、换色、预算与资源导入检查。

- 批次以用户实际提供的文件为范围，不自动扫描并处理目录内所有模型。每个模型使用独立工作目录、源哈希、候选和报告。
- 可以并行处理独立模型的精修、身份审计和离线核验；运行资源覆盖逐个执行，先冻结备份并重新核对目标哈希，防止并发写入或混用候选。
- 旧角色必须建立“源文件 → 稳定角色 ID／名称 → GLB／遮罩路径 → UUID”的证据链。不能仅凭外观相似、文件排列或上次使用的槽位替换。
- 用户说明为新增的角色不得占用任何旧角色路径；角色名称、解锁与属性等不明确时单独询问，不阻塞其他旧角色的精修。
- 保留现有动作兼容骨架、运行 UV、换色语义、资源 UUID 和可回退备份；不把 2048 源美术图直接当成已验收的 512 运行图。
- 身份有歧义、需要改变结构或质量／动作检查不通过的模型暂不安装。报告具体问题，其余通过检查的模型可以继续。
- 自动接入不包含未经请求的外部上传、提交／推送、购买资源或提高项目运行预算。离线核验不能冒充微信实机验收。

## 4. 分区质量要求

### 4.1 白色与灰白区域

- 白袜、灰白头发应清除不属于设计的黄、绿、棕灰污染，但保留袜褶、发束、体积明暗与合理接触暗部。
- 不用过曝灯光或统一纯白覆盖来宣称“变干净”。无光照看色界，正常光照看结构，两项都要检查。
- 肤色、眼镜、帽带、鞋口与头发邻接区域必须受保护；奶白与浅绿不能只凭单一亮度阈值区分。

### 4.2 分色、缝线与图案

- 服装色块边缘应明确、连续、随形，不出现无设计依据的毛刺、三角裂线、断带或串色。
- 黑／白／主色相接处保留原有层次；滚边不能被吞掉，白条不能被无意加宽，细图案不能以模糊光斑代替。
- 对领口、袖缝、腋下、裆部、裤脚、鞋底、帽口等易出问题区域，补充侧面或低角度检查。
- 本次案例中的紫色镜片与屏幕、黑背带、胸前白条、裤脚绿边和包上白图案属于受保护设计示例，不是所有角色必须具备的装饰。

### 4.3 UV 与图像处理

- 默认保持现有 UV。任何生成／重绘图集都只是候选，逐区贴回模型确认；不接受新增符号、改变图案或岛内设计漂移。
- 判断污染应结合模型空间、拓扑、骨骼权重与原始颜色，不使用全局绿色容差批量改图。
- 对已知连续分色，可沿模型曲面拟合边界再离线烘焙回原 UV；候选面应覆盖所有跨界三角面，不能只用过窄面心范围。
- 分清 sRGB 与线性颜色，检查缩图、岛边 padding 和过滤后的结果。扩边只能修采样空隙，不能破坏真实衣片边界。
- 若 UV 重叠、严重碎片化使保真与边界连续无法兼得，转入 `character-uv-repack-pipeline`；不得以越来越大范围的模糊掩盖结构问题。

## 5. 结构与预算边界

- 纯贴图精修默认不改位置、法线、UV、骨骼层级／名称、关节索引、权重、逆绑定矩阵、动画、节点变换、网格和材质数量。
- 只替换内嵌图片时，逐字节比对所有非图像数据及不应改变的元数据；完整重新导出时，做等价的结构与数值比较，说明允许的重排和差异。
- 只有重新导入成功不代表结构完整；只有结构不变也不代表贴图跨缝连续。两类检查独立进行。
- 运行时沿用现行设计规范：默认一个 512×512 主图集、尽量 1～2 材质、约 5000 三角面的生产方向。源美术版尺寸与面数不能直接当运行预算通过。
- 不因精修擅自升运行分辨率、加材质、拆网格、减面或改 UV。确需结构调整时，先明确范围与成本，再走对应技能流程。
- 制作时的节点、遮罩、超采样和烘焙留在离线环节，不新增逐帧处理、逐角色生成纹理或无必要的渲染批次。

## 6. 验收分层

每项标记为“通过／未通过／未验证／不适用”，没有执行的检查不能记为通过。

### A. 源美术验收

- [ ] 有原图与修正版对照，模型正、背、左、右可检查，重点部位有近景。
- [ ] 中性底色下分界连续，无新增杂色、UV 三角裂线、溢色和图案偏移。
- [ ] 同灯光、同曝光近景仍保留袜褶、发束、衣片和原有设计层次。
- [ ] 普通观察距离与目标游戏显示尺寸下仍可读；未核对游戏尺寸时明确标记未验证。
- [ ] 皮肤、五官、发型、固定色、配件和图案没有未经要求的变化。
- [ ] 新 GLB 重新导入成功，结构对比通过，修改范围与残留问题有记录。

### B. 换色与动作验收（任务涉及这些内容时）

- [ ] 绿色设计区的目标语义完整保留，固定白色、皮肤、头发与主题点缀没有误入主换色。
- [ ] 默认独立遮罩／材质参数；使用白色键前已排除袜子、头发、眼睛、高光等非目标白色。
- [ ] 至少五组高对比换色，覆盖亮、中、深，原色可用；边界不漏底、不染皮肤。
- [ ] 游戏人形角色的肤色开关与实际B通道皮肤遮罩同时有效；原／暖肤色与深肤色分别搭配原服装、红／蓝服装检查，露肤区域连续且不染头发、装备或图案。无可换肤区域的例外已明确确认。
- [ ] 站立、流线、移臂、过头抬臂等相关动作无新增缺陷；纯贴图审计不能代替动作实测。

### C. 游戏交付验收（明确要求导入／替换运行资源时）

- [ ] 确认具体角色、目标资源路径和覆盖范围；保留原资源及其 `.meta`，不把制作源放进 `assets/`。
- [ ] 检查目标分辨率、面数、材质、draw call 与包体成本；源图缩到运行尺寸后重新验收。
- [ ] 换肤选项可见且有效，选角预览与比赛使用相同肤色；切色不重建模型或重启动作，确认选择并重新进入后肤色正确保持。未执行的运行检查标记未验证。
- [ ] Cocos 生成／更新导入元数据后执行 `npm run textures:fix` 与 `npm run textures:check`，不手改压缩设置。
- [ ] 重要变化完成 iOS／Android 微信实机检查；未测压缩外观、动作或实机时明确说明。
- [ ] 若变更运行时代码，执行项目指定类型检查，并核对单机／联机一致性；仅离线贴图替换不应新增联机状态或逐帧工作。

建立本规范本身不授权启动 Cocos、部署、提交／推送或上传。外部上传须先知道目标平台／仓库与文件范围。

## 7. 交付记录

交付应包含版本化 GLB、可编辑制作文件或导入副本（标清是否包含制作过程）、结构审计、修前修后图及简短说明。记录源文件与成品哈希、实际计数、贴图尺寸、修复部位、保护项、未验证环节和残留问题。可复用规范／代码进入共享技能；预览、备份、源美术和模型专用临时脚本不当作运行资源。
