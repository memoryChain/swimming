# 比赛加载就绪与分帧初始化

2026-09-24。进入比赛的 Loading 现在覆盖参赛模型、动作、换色、场馆和必要 UI 的初始化，再启动赛前展示。登录首屏与分包边界保持现有设计。

## 原因

原先 `GameManager.buildScene` 完成只表示泳池、玩家逻辑节点和基础 UI 已建立；回调直接 `startGame` 并关闭 Loading，AI 随后才创建。角色 GLB、专属动作和换色资源各自异步返回，渲染器还会隐藏两帧，造成空泳道、角色逐个出现和展示时间被加载占用。

## 当前流程

1. 建立本场加载作用域和联机会话。Loading 至少显示一帧后，并发读取调参和公共动作。
2. 建立场馆、玩家及界面；起跳 UI 与 HUD 素材并发加载。场馆缺失进入错误出口，不以空场馆进入比赛。
3. 在 Loading 内创建完整阵容，映射远端真人最终身份；模型请求可以并发，GLB 实例化和骨骼绑定每渲染帧最多处理一名选手。同一角色仍在加载时，不重复发起模型请求。
4. 建立观众和计分板。等待全部参赛模型、专属动作、换色材质／遮罩及渲染器就绪；同时等待 `loadRaceAsset`／`loadRaceAssetDir` 和头像 UI 订阅触发的嵌套资源请求完成，包含此前从大厅发出、进入比赛后新订阅的共用请求。
5. 完整阵容准备后设置展示姿态，遮罩下再经过三帧渲染准备。加载期间不推进 `GameManager` 的玩法和镜头计时，随后注册输入、关闭 Loading，再开始可见展示。

分帧仍在主线程执行，不引入 Worker。单个 GLB 的实例化／骨骼绑定、泳池和观众构建仍可能形成长帧；这次只拆开不同选手的初始化，不能据此保证任何设备上 Loading 都完全不卡顿。首帧等待不是 GPU 完成栅栏或完整 shader 预热证明。

## 失败和生命周期

- `RaceLoading` 在 MainGame 初始化阶段设置 60 秒总超时。必要模型、动作、换色、起跳 UI、HUD、赛前卡片加载错误会阻止放行；无回调时由超时退出等待。
- 错误时停止本场初始化和网络控制器、通知退出本局、清理比赛世界及旧 UI，提供“返回”按钮。用户回到入口后可以重新进入。保留联机房间会话，不调用 `endGame`。
- 退出／销毁取消等待、队列和帧监听；模型令牌和节点有效性检查拒绝旧请求。共用资源请求本身仍可完成并清理缓存等待者，不强行取消可能被其他界面共用的下载。
- 非必要装饰资源沿用其现有回退；资源请求完成不代表每项装饰必须成功。音乐保留现有加载策略。
- `RaceLoading` 成功时一次输出分阶段毫秒数和总计；总计从 MainGame 初始化开始，不包含前一场景下载 race 分包的时间，各阶段可能重叠，不能简单求和。

## 联机

- 加载期间继续 `NetRaceController.tick` 上传空输入帧，避免拖住其他设备的帧同步。
- 提前收到 `GO` 时先记录；只有本机完整加载且赛前展示结束、执行 `reportRaceReady` 后才开始倒计时。房主自己未准备时不能因收到其他人的 `CR` 提前发令。
- 保留原有房主 5 秒／访客 7 秒掉线兜底；极慢设备仍可能比其他人晚开始，这次不重做全房时间同步或重同步协议。
- 全体阵容创建提前到了展示之前，共享随机数消费顺序发生变化，因此玩法协议升级为 **47**，两端需同时更新，拒绝与 46 及更早版本混跑。比赛数值和保活重赛方式不变。

## 验证

- `pnpm test:race-loading` 执行真实加载协调器、进场方法、角色就绪判断和倒计时方法，覆盖最后一名角色迟到、嵌套资源等待、模型失败、超时、取消、提前 GO 及重复发令。
- 同时回归启动、赛前展示、起跳和房间测试，并执行 TypeScript 和微信资源审计。
- 仍需在现有 Creator 会话，以及 iOS／Android 微信真机验证冷缓存首次进场、热缓存再次进场、不同角色阵容和双端快慢加载。离线测试不等于实际渲染验收。
