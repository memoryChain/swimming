# 微信得分存档与玩家云档案接入调研

> 实施进展：已编写微信云档案客户端、云函数和管理员操作；已部署至微信云环境并完成基础真实调用，客户端重新构建和真机联调待完成。部署步骤与实际边界见[微信云存档部署与后台操作](微信云存档部署与后台操作.zh.md)。

调研日期：2026-09-26。依据当前项目源码、用户浏览器打开的微信官方「得分存档服务」及其 API、云开发官方文档。

本文记录接入前的调研方案；后续运行时代码已实现，已部署至微信云环境并完成基础真实调用，客户端重新构建和真机联调待完成，具体进度见上方部署文档。官方已确认的能力与项目建议、待验证项分别标明。

## 1. 结论

- 当前玩家档案全部保存在设备本地，微信构建也使用 `MockBackend`，没有账号云端备份。
- 用户打开的「存档服务」具体是 **RankManager 得分存档**：适合成绩、最高关卡等数值记录，不能直接保存本项目整份结构化玩家档案。
- 推荐：**完整玩家档案使用微信云开发（云函数＋数据库）；成绩展示按需使用 RankManager；音量与调试设置保留本地**。无需购买、维护传统服务器，但需要开发和部署少量云端业务逻辑。
- 后台补偿、改等级、回档依托云数据库与管理员操作；不能假设 MP 的玩法配置页就是玩家存档编辑器。
- 微信、抖音、TapTap 首阶段按平台独立账号、独立存档设计。跨平台互通是额外账号绑定需求，不会随平台云存档自动实现。

## 2. 当前项目实际怎么保存

| 内容 | 当前实现 | 影响 |
|---|---|---|
| 后端选择 | `assets/scripts/backend/BackendManager.ts` 始终创建 `MockBackend` | 所有构建都走本地，无微信云端分支 |
| 玩家主档 | `MockBackend.ts` 用 `sys.localStorage`，键为 `swimming.player-profile`，JSON 序列化 | 没有远程备份；换设备无法从项目服务恢复，缓存清理可能丢失 |
| 档案字段 | `PlayerProfile.ts`，schema=6 | 昵称、头像 ID、角色/肤色/配色、金币、每日广告次数、各角色等级，以及完整生涯数据 |
| 生涯数据 | `CareerRules.ts` | 段位、积分、各角色杯赛轮次/种子/状态、夺冠记录、首奖记录、待结算赛事、最近结算回执等 |
| 内存与调用入口 | `PlayerData.ts` | 载入去重、修改队列、变更通知；这些仅约束当前进程，不等于跨设备并发保护 |
| 平台登录 | `PlatformSession.ts` | 缓存 `wx.login`/`tt.login` 返回的临时 code，未把玩家档案绑定稳定账号 |
| 音量 | `SettingsManager.ts`，`SpeedSwimming.Settings.v1` | 独立本地保存，适合继续作为设备设置 |
| 调参 | `TuningDebugControls.ts`，`SpeedSwimming.Tuning.v1` 等项目/原生保存通道 | 开发配置，不应混入正式玩家云档案 |
| 旧养成档 | `ProgressionManager.ts`，`SpeedSwimming.Progression.v2` | 读旧键合并进主档，然后保存并清理 |

当前比赛奖励实际已走 `GameManager → PlayerData.executeCareer(settle) → MockBackend → CareerRules`。`IBackend`、`ProgressionManager` 中关于旧 `awardRace` 的部分注释落后于实现，接入以实际调用为准。

`WechatPlatform.submitScore()` 只是 `wx.setUserCloudStorage` 的好友关系链 KV 写入封装；`getLeaderboard()` 仍返回空数组。源码检索未发现比赛流程调用 `submitScore`，因此不能把这个封装视为已经接入成绩云存档。它也不是 RankManager。

## 3. RankManager：能保存什么、怎么用

### 3.1 官方已确认

来源：[得分存档指南](https://developers.weixin.qq.com/minigame/dev/guide/open-ability/storage-server/storage-score.html)、[管理器入口](https://developers.weixin.qq.com/minigame/dev/api/open-api/game-component/wx.getRankManager.html)、[上报接口](https://developers.weixin.qq.com/minigame/dev/api/open-api/game-component/RankManager.update.html)、[查询接口](https://developers.weixin.qq.com/minigame/dev/api/open-api/game-component/RankManager.getScore.html)。

1. MP 后台进入「运营功能管理 → 基础配置 → 游戏玩法 ID 设置」。
2. 配置玩法 ID 与战绩类型，支持数值型、时间型、枚举型。玩法生效后，除枚举值新增/修改名称外不支持更改，需先确定语义。
3. `wx.getRankManager()` 获取全局单例；`update({scoreKey, score})` 上报当前用户分数。
4. `getScore({scoreKeys, periodType})` 查询当前用户得分，结果示例为 `res.scores[key] = {score, timestamp}`。
5. `periodType`：1 自然日最高、2 自然周最高、3 自然月最高、4 历史最高、5 最新。
6. 文档标注管理器及上述方法自基础库 **3.14.2** 支持；方法不原生返回 Promise，应封装成功/失败回调。
7. `subScoreKey` 可选，正整数 1～1000；查询对应 `subScoreKeys`。页面同时标注子键自 3.12.1 支持，与管理器起始版本有差异，接入按 3.14.2 加运行时能力检测，不据此承诺低版本可用。

示意（仅说明调用，玩法 ID 需先在实际 MP 后台配置）：

```javascript
const manager = wx.getRankManager();
manager.update({
  scoreKey: 'career_highest_tier_v1',
  score: highestTier,
  success: () => { /* 标记此次上报成功 */ },
  fail: error => { /* 保留有限重试任务 */ },
});
manager.getScore({
  scoreKeys: ['career_highest_tier_v1'],
  periodType: 4,
  success: result => { /* 读取对应记录；空记录与请求失败分开处理 */ },
  fail: error => { /* 不能把失败当作新玩家 */ },
});
```

### 3.2 对本游戏的用法建议

| 数据 | 建议 |
|---|---|
| 历史最高生涯段位展示 | 可用数值型得分记录，但完整生涯进度仍以云档案为准 |
| 200m / 400m 最佳成绩 | 可考虑时间型，各距离、规则分开；角色等级影响成绩，应先明确榜单公平性与赛季规则 |
| 最近一局成绩 | 使用 `periodType=5`，不能把它当完整战绩列表 |
| 金币余额、角色等级、杯赛轮次和领奖记录 | 存入云数据库；不能把整个档案拆成多个 scoreKey 充当事务数据库 |

时间型的上报单位、精度、排序方向以及 `periodType=4` 在该类型下的实际最佳值行为，需要结合实际 MP 配置和真机核实。API 参数页仅写 `score:number`，不据此假设毫秒、秒或自动取最小值。

为什么金币不适合：余额会增加也会减少，“历史最高”会恢复已花掉的钱；“最新值”虽然可以表达余额，但多设备覆盖、扣币与升级的一致提交、运营审计、客户端伪造等问题仍未解决。API 没有提供整档 JSON、事务或版本比较能力。

此外，管理器入口目前写着“得分排行榜（开发中）”，不要仅凭 `RankManager` 名称就承诺能直接查询任意全服榜单。`update` 在擂台赛进行中会结束挑战并弹结果页，将来接擂台赛时必须与普通存档上报隔离。

### 3.3 后台能否直接修改 RankManager 数据

本次查阅的指南、RankManager 方法列表与公开服务端目录，**未找到明确的任意玩家分数编辑/删除/回档接口或后台编辑操作说明**。已确认的 MP 入口用于配置玩法；不能承诺其可修改任意玩家分数。

公开服务端目录中的 `set_user_storage` / `remove_user_storage` 属于关系链开放数据 KV，不能当成 RankManager 分数修改接口。若未来有成绩纠错需求，需在实际 MP 账号或官方支持渠道确认能力；在确认前，不把可人工恢复的完整档案建立在 RankManager 上。

## 4. 完整云档案的最小接入方案

### 4.1 使用微信云开发

1. 在微信开发者工具/云开发控制台开通对应 AppID 的云环境，区分测试与正式环境。
2. 建立 `players`（玩家档案）、`operations`（幂等业务回执）、`adminAudit`（管理员审计）等集合；集合名为本项目建议。
3. 客户端初始化一次 `wx.cloud.init({env: environmentId})`，通过 `wx.cloud.callFunction` 请求云函数。显式指定环境，避免默认连错环境。
4. 云函数通过 `cloud.getWXContext()` 获取可信 `APPID`、`OPENID`，缺失时拒绝玩家操作，不信任客户端提供的账号 ID；无需自行搭建 code 换 openid 服务。
5. 云函数运行实际规则、写数据库并返回新档案与版本，客户端更新 `PlayerData` 和账号隔离的本地缓存。

档案建议增加元数据：内部 `playerId`、可信平台身份映射、`schema`、单调递增 `revision`、云端 `updatedAt`。保留现有业务字段结构以降低迁移成本；`playerId` 可用于客服查人，不能作为登录凭据。

客户端禁止直接写经济集合；云函数与控制台具备管理权限，因此**每个云函数也必须自行检查调用者身份、动作参数与权限**，不能只依赖数据库规则。

### 4.2 对现有代码的具体改动

| 位置 | 接入改动 |
|---|---|
| `BackendManager.ts` | 微信正式环境选择 `WechatCloudBackend`；编辑器/浏览器保留 Mock；云端故障不能偷偷切换成本地正式经济档 |
| 新增 `WechatCloudBackend.ts` | 封装初始化、云函数调用、错误分类、版本和请求 ID，隔离微信 API |
| `IBackend.ts` | 保留业务动作语义；增加明确的角色选择保存、档案刷新、迁移接口；收紧任意 `saveProfile` |
| `PlayerData.ts` | 增加可靠刷新和档案状态，不能只用目前“一旦 loaded 永不重拉”的 `load()`；所有变更仍走串行队列 |
| `CareerRules.ts` 与配置 | 抽取可在云端运行的规则依赖，复用版本化配置；云端生成/验证赛事凭据，重试不重复领奖 |
| `ProgressionManager.ts` | 将旧档迁移改为明确、可等待的流程；云端确认迁移成功后再清理旧档 |
| 新增 `cloud/functions/` | 云函数、部署说明与规则打包，不放进 Cocos `assets` |
| 平台成绩接口 | 若接 RankManager，单独定义成绩提交/查询能力，支持玩法、周期与“不支持”状态 |

最小云端动作：载入/建档、修改昵称头像、修改角色外观、金币升级、开始/放弃/结算生涯比赛。广告发奖在正式启用广告时再接入可信凭据和每日限额。现有 `grantDebugCoins` 不得向普通正式账号开放；当前调用在 AI 调试入口，旧注释的“头栏加号”不能作为现状依据。

每个资源变动请求携带唯一 `requestId`，服务端用持久化回执去重；升级的扣币与加级、结算的发奖与杯赛推进，都在同一个事务提交。若上次请求实际成功但响应丢失，重试返回原回执，不能再扣钱/发奖。

现有本地 32 条结算回执不是完整的云端幂等方案。云端应使用账号范围内唯一且不可重新执行的赛事凭据，定义回执保留期限与过期拒绝规则；不能在删除旧回执后又允许同一赛事领奖。

云函数能防止直接篡改数据库、重复领币，并不自动证明客户端上报的比赛时间或广告完成是真的。第一阶段至少验证赛事凭据、配置版本、合法范围、耗时和奖励上限；更强成绩可信度需另做结果校验/回放或平台凭据验证。房主客户端也不是可信支付或经济服务器。

## 5. 后台怎么改玩家数据

### 5.1 开发测试期

官方云开发控制台支持数据库查询与管理，并提供可执行增删查改的高级数据库脚本。不必先开发大型管理网站，就能定位测试玩家记录、备份并修正字段。

这是数据库原始能力，不会自动检查本游戏规则。手工修改金币、杯赛、等级等关联数据要校验一致性，并同步提升版本；正式运营应使用下一节的管理员命令。

### 5.2 正式运营建议

做一个很小的管理员工具，调用独立鉴权的管理云函数，最初可用受控管理脚本，之后再加网页。普通玩家接口不能接受客户端传入 `isAdmin=true`，也不能内置管理员密钥。

建议操作：按玩家 ID 查询、补偿金币、调整指定角色等级、修复特定杯赛状态、导出备份、从选定备份恢复。

一次修改的流程：

1. 读取玩家档案和 `revision`，显示目标玩家与变更预览，填写原因/工单号。
2. 验证管理员身份和操作范围，并携带唯一操作 ID。
3. 事务内校验预期版本，更新受影响字段，`revision + 1`，写入审计记录。冲突时重新读取并重新审阅修改。
4. 审计记录保留操作者、对象、时间、原因、操作 ID、变更前后值和版本。
5. 玩家下一次回到首页/回前台/执行业务操作时拉取新版本。赛中变更涉及角色能力时留待下一局应用。

补偿优先表达成“增加 500 金币”；修正为某个绝对值时必须检查预期版本，避免覆盖同期合法收入。回档是生成一个新的更高版本，不能把版本号一起倒退；经济回执也要保持一致，避免恢复到领奖前后造成再次领奖。

**防止后台修改被覆盖的关键：客户端不上传整份旧档作为最终真值。** 只提交“升级这个角色”“领取这次赛事奖励”等意图；云函数在最新档案上处理。单有 `revision` 字段却不检查它，仍不能解决问题。

## 6. 本地老档、断网与多设备

- 测试档包含可调试加币数据，默认不自动导入正式经济档。需要保留的测试账号可采用一次性白名单导入；是否继承现有测试进度需在切换正式云档前确定。
- 迁移必须先确认账号、明确“云端确实无档”，在云端原子执行仅一次；禁止用本地时间戳比较新旧、字段取最大值或无条件覆盖已有云档。
- 现有 `migrateLegacySave()` 调用 `void PlayerData.persist()` 后立即删旧键，且启动未明确要求 `PlayerData.loaded` 成功后才迁移。接云端前必须修复，不能在云端加载/写入失败时丢掉原档。
- 本地缓存按环境、平台、账号隔离；未确认身份前不启用经济操作，账号变化时清理内存中的旧会话数据。
- 区分“新账号无记录”“网络失败”“数据损坏/不支持的 schema”；云端失败不能创建默认档并覆盖原档。
- 推荐首阶段：断网可玩不计正式奖励的练习模式，经济操作等联网后执行。若要离线推进正式生涯，需另做持久化操作队列和冲突政策，不能整档覆盖合并。
- 升级/结算成功即保存，不依赖退出或 `onHide` 才上传；切后台异步请求不保证完成。缓存/重试记录须落本地，服务端承担幂等。
- 两台设备并发通过事务、版本和赛事凭据处理。当前生涯只有一个 `pending` 赛事，第二台开始比赛时应明确拒绝/提示已有赛事，不隐式覆盖它。

## 7. 多平台与联机影响

- 现有平台工厂只区分微信、抖音、default，尚无 TapTap 实现。扩展时保留 `IBackend`，各平台身份认证与存储适配分别实现。
- 当前源码中抖音存储能力的旧注释不是最新官方能力证明；本次未调研抖音/TapTap具体云服务，不据此承诺其支持或不支持某项云存档。
- 若各平台独立运营，微信 openid、抖音身份、TapTap 身份各自映射档案即可。若未来要跨平台继承角色和金币，需统一账号与显式绑定，不能按昵称、头像或不同平台 openid 自动合并。
- 角色等级会影响联机结果。进入房间和准备开赛前完成云档案读取，使用同一份已确认角色快照生成外观和属性摘要。
- 后台改等级或云端刷新不能在比赛中直接改当前泳者属性；准备阶段失效时应重做准备确认，赛中则下一局生效。
- 云档案请求放在登录、升级、比赛开始/结算、回到前台等事件，不进入 `GameManager.update()`，不增加比赛帧循环成本。
- 保留既有房间保活重赛机制，不因存档接入调用 `endGame`；官方房间服务与云数据库是独立能力。

## 8. 费用与待核实项

截至调研日，[官方计费页](https://developers.weixin.qq.com/minigame/dev/wxcloud/billing/price.html)列出：基础套餐 **19.9 元/月/环境**（页面标注原价 39 元），含 20 万次调用、2GB 容量及对应计算/流量配额，超出配额可选择按量付费。

“调用次数”包括数据库读写、云函数调用、存储上传下载等，因此一次保存并不必然只计一次调用。测试和正式环境分别核算，低频事件保存更适合当前项目。

免费环境活动页面写明符合资格的账号可在未发布阶段使用免费环境，发布后到期时间变为上线后第 15 天；页面概述又保留“六个月体验”的表述。实际资格、到期和支付以该 AppID 控制台显示为准，不能承诺永久免费。正式上线需配置费用与到期提醒、备份，避免停服后数据释放。

接入前还需在实际账号确认：云开发是否已开通、测试/正式环境 ID、套餐资格；MP 玩法 ID 是否已有配置；时间型成绩语义和配额；是否保留本地测试档。此次未操作账号控制台或修改任何线上玩家数据。

## 9. 建议实施顺序与验收

1. **先完整云档案**：测试环境、可信身份、云函数、数据库、载入/升级/生涯结算、版本/幂等、迁移保护。
2. **再管理员操作**：玩家查找、补偿/修正、审计与恢复，让“后台能改而且不会被覆盖”在上线前成立。
3. **然后成绩服务**：确定玩法与时间型语义后接 RankManager；只接它不能解决金币和角色跨设备恢复。
4. **最后正式环境切换**：确定测试档政策、配置费用/备份，体验版真机验证后再发布。

验收覆盖：同账号换设备恢复；账号隔离；并发建档；弱网读取失败不覆盖；成功响应丢失后重试不重复扣币/领奖；并发升级余额正确；迁移失败保留旧键；后台补偿不被旧设备回写；回档后旧凭据不重复领奖；联机准备快照一致且赛中不变；旧基础库成绩能力降级；编辑器本地模式维持可用。
