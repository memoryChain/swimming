## 2. 上线顺序：哪些步骤必须等前一步

TapTap 对普通小游戏提供前置备案服务，整合小游戏备案与 ICP 核准流程。不要照搬抖音的“版本审核后自动申报”顺序，也不要用网站域名备案替代小游戏备案。

```text
确认发布主体并完成认证
  → 创建/核验目标普通小游戏应用，取得 AppID 和测试权限
  → 构建并上传合适包体，完成必要自测
  → 选择包体，提交前置备案资料
  → 电子化核验、提交审核、短信验证、取得核准结果
  → 首发功能与物料验收完成，提交版本审核
  → 审核通过，按发布设置上线
  → 补验线上桌面入口并观察运营数据
```

这是便于执行的依赖顺序。开发打磨、广告与数据联调、宣发制作可在备案等待期间进行；备案包体应与拟上线内容相符，较大内容变化需核对是否影响申报。上传、自测、提审、过审、备案完成、发布是不同状态，逐项记录。

依据：[前置备案流程](https://developer.taptap.cn/minigameapidoc/quick-start/guide/pre-filing/)、[创建小游戏与包体管理](https://developer.taptap.cn/minigameapidoc/quick-start/guide/creation-improvement/)、[版本提审](https://developer.taptap.cn/minigameapidoc/quick-start/guide/game-publish/version/)。

预约/敬请期待页面可先行准备，但页面发布不代表游戏已经可玩。官方对不涉及内购的普通小游戏给出无需提交版号、上线前完成前置备案的口径；有内购须按对应版号、支付及商户要求另走流程，不能直接使用本计划的无内购假设。[创建页资质说明](https://developer.taptap.cn/minigameapidoc/quick-start/guide/creation-improvement/)、[小游戏内购接入](https://developer.taptap.cn/minigameapidoc/quick-start/monetization/IAP-game/)

## 3. 哪些环节最花时间

**优先排查材料补件、转换后的双端资源问题，以及埋点数据通道。**下表区分官方时效与项目工作量判断，不能相加当成承诺上线日期。

| 环节 | 时效依据或工作量判断 | 提前行动 |
| --- | --- | --- |
| 主体认证 | 官方入驻页说明材料提交后 2 个工作日内处理 | 核验资料有效性、申请权限与联系信息 |
| 软著与权属 | 当前未确认本应用证书要求，也不估算办证时间 | 尽早确认必交范围；已有或在办证书核对名称与权利人 |
| 前置备案 | 官方预计材料无问题时全程 20 个工作日内；初审预计 12–16 个工作日 | 先准备主体、负责人、内容介绍和包体；预留补件及节假日余量 |
| 短信核验 | 收到核验短信后 24 小时内操作 | 保持负责人手机号可用，安排及时处理 |
| 游戏资料审核 | 创建页给出新建游戏资料约 1–3 日、更新资料约 1 日的预计值 | 不能把资料审核时间当成包体技术审核或完整上线周期 |
| Cocos 转换与双端测试 | 项目判断：中到高，首次转换后才能估工期 | 首先验证分包、GLB、ASTC 回退、字体、音频和输入 |
| 桌面入口 | 项目判断：中；完整线上验证晚于开发阶段 | 开发阶段测能力判断与失败分支，上线后补完整流程 |
| 自定义数据 | 项目判断：通道未验证前，工期不确定 | 先只上报一个事件，确认应用身份、字段、入库和报表 |
| 联机/真实后端/内购 | 项目判断：若首发必需，可能成为主要开发项 | 单独安排双机弱网、重赛、账号和事务验证 |

时效依据：[开发者入驻](https://developer.taptap.cn/minigameapidoc/quick-start/guide/registration-login/)、[备案时效与核验](https://developer.taptap.cn/minigameapidoc/quick-start/guide/pre-filing/)、[游戏资料审核说明](https://developer.taptap.cn/minigameapidoc/quick-start/guide/creation-improvement/)。不将“预计”写为保证，不给没有公开依据的包体审核、广告审批时长。

预算分别估算适配与测试、美术物料、必要的域名/HTTPS/采集服务/存储、后续维护。平台宣传的零分成不等于项目无服务器或运营成本；实际额度及费用按所选服务核验。

### 4.2 软著证书：公开资料的确定项与边界

区分“软件著作权人信息”“权属或授权材料”“软件著作权登记证书”，三者不能互相替代。

| 官方资料 | 已核实内容 | 不能直接推出的结论 |
| --- | --- | --- |
| 通用快速入门指南 §2.2 | 无内购开放试玩清单未列软著，有内购清单列有软著 | 不能仅由此认定所有普通小游戏都免证书 |
| 小游戏审核规范 §6.5.1 | 要求提供登记号、证书扫描件，以及适用时的授权材料 | 本条没有明确解释与无内购清单的适用关系 |
| 普通小游戏前置备案 §3.3 | 著作权人名称应与权属材料一致 | 该页没有给出所有情况的证书必填条件 |

依据：[通用指南](https://developer.taptap.cn/docs/store/standardies-operation/)、[小游戏审核规范](https://developer.taptap.cn/minigameapidoc/tap-operation/operation-standards/review-standards/)、[备案说明](https://developer.taptap.cn/minigameapidoc/quick-start/guide/pre-filing/)。

**执行口径：**先准备权属材料，证书列为申报/提审前待核实项。针对“普通小游戏、无内购、如采用激励广告”分别确认备案和版本提审的必传附件；公开资料尚不能得出免证书或全部必办的确定结论。未找到自研权属声明可以替代登记证书的官方入口或模板，不将其写成可用方案。TapTap 制造的经验与 PC 测试清单不作为本项目的免交依据。

### 4.3 宣发与商店资料

优先采用小游戏专用物料表；不混用普通 APK/PC 页面上的视频或图片大小上限。

| 物料 | 准备规格 |
| --- | --- |

| 方形宣传图 | 1440×1440，1 张，JPG/PNG，2 MB 内 |

### 4.4 实名、防沉迷、适龄与隐私

仅提供小游戏游玩方式时，创建页说明防沉迷默认依托平台开启；若同时提供 APK 测试或下载，则另有要求。项目仍需验证限制触发后的暂停、退出与恢复行为，不能仅看到登录成功就视作所有合规能力验收完成。[适用说明](https://developer.taptap.cn/minigameapidoc/quick-start/guide/creation-improvement/)

按照真实数据行为配置隐私指引、授权和拒绝处理。用户自定义文字输入需处理内容安全；当前固定头像、自动昵称与未来开放自由输入应分别评估。若使用好友排行等权限能力，按该接口要求在后台声明并处理用户授权。项目已有 8+ 内容调整是准备工作，不能替代平台审核。[内容规范](https://developer.taptap.cn/minigameapidoc/tap-operation/operation-standards/content-standards/)、[隐私审核要求](https://developer.taptap.cn/minigameapidoc/tap-operation/operation-standards/review-standards/)、[排行榜权限](https://developer.taptap.cn/minigameapidoc/dev/api/open-api/leaderboard/tap.getLeaderboardManager/)

### 5.3 登录与稳定身份

`tap.login()` 返回临时 code；服务端通过 `code2Session` 换取身份，再给客户端自己的会话。code 仅可使用一次，不作为稳定用户 ID；`secret`、`session_key` 留在服务端。处理登录态检查、过期、重登和切账号。[小游戏登录态管理](https://developer.taptap.cn/minigameapidoc/dev/tutorial/open-capabilities/login-management/)

本地存档、平台云存档、自有账号系统是不同范围。只有业务需要自有身份、跨设备数据或收集接口时才安排相应服务；不把“接登录”写成必须建设完整游戏服务器。分析身份也不能用当前昵称或微信 openid 直接冒充 TapTap 用户。

| `rewarded_ad_result` | 一次请求终态一次 | 请求 ID、完成/跳过/错误/不可用、错误分类 | 观看流程在哪一步失败 |
| `reward_grant` | 奖励成功写入后一次 | 事务 ID、来源、币种、数量、关联广告请求 | 广告或补给奖励是否实际到账 |
| `progression_change` | 升级、突破或解锁成功后 | 角色、操作、前后等级、消耗 | 养成推进与经济消耗 |
| `online_flow` | 建房、加入、开赛、断线、恢复等状态变化 | 阶段、结果、耗时、错误分类 | 联机成功率与恢复质量 |
| `desktop_guide_click` / `desktop_request_result` | 桌面引导点击、调用结果 | 系统、能力状态、调用结果 | 引导是否有效；不冒充真实添加或复访 |

名称是项目内部约定，不是宿主已存在的 API；接入 TapDB 时按其规则映射名称和属性。共同字段包含事件版本、游戏版本、渠道、系统类型、会话、测试标记；比赛事件带平衡配置版本。仅采集获准且必要的身份信息，不上传昵称、头像 URL、手机号、证件或原始登录凭证。

### 7.4 统计口径与赛中性能

- 采用统一事件定义，区分新用户和已有存档用户；按同一用户群、时间窗口和游戏版本计算漏斗，保留实际开赛与点击再玩的区别。
- 代码执行前的下载或启动失败依靠平台数据，游戏内埋点无法覆盖；拒绝分析授权的人群也可能不进入自定义样本，不强行与全量平台人数相等。
- 未获对应授权时不采集；匿名阶段如需统计，使用应用范围内的标识并明示口径，登录关联按所选服务规则实现，不假定历史自动合并或跨微信/TapTap 自动认同一人。
- 赛中只累计必要计数，局末汇总；不逐帧、逐次划水、逐个 AI 或水花上报，不在 `GameManager.update()` 中格式化事件或创建请求。
- 联机客户端只报本地玩家行为；全局结果如需统计，由指定权威来源产生，按比赛 ID 去重，处理重放和房主迁移。采集不影响随机流、时钟或同步协议。
- 队列、批量、重试、缓存容量与过期时间均有上限，失败退避；切后台尽力发送，不能保证杀进程前发送成功。
- `race_end` 只把可观测主动退出记为退出。超时没有终态的局次标为未知/未完成，不等同主动离开或崩溃。
- 广告完成、奖励提交、统计上报分离；事件接收失败不影响操作或奖励。通过事务 ID 防止重试重复发奖，通过事件 ID 处理重复统计。
- 编辑器、调试模型、托管、测试设备进入独立环境或可过滤范围，不能污染真人留存与完赛率。

### 7.5 后台验收与首批看板

固定执行正常首局、重复点击、主动退出、断网重试、切后台、杀进程、切账号、拒绝授权、广告跳过/失败/完成、奖励重复回调；若首发联机，再测重赛和断线恢复。逐条核对次数、字段、身份与实际行为，不只确认请求返回成功。

首期建立：

1. **首局漏斗：**大厅可操作 → 教学完成 → 首局开赛 → 首局完赛 → 第二局实际开赛。
2. **奖励漏斗：**广告请求 → 观看完成 → 对应奖励到账，保留失败与未观察到终态的分支。
3. **玩法看板：**模式参与、完赛率、耗时、再玩与局末操作汇总，按角色、距离及版本拆分。

留存按实际跨日样本验证，不能当天上报成功就称次留验证完成；阈值由真实样本建立，不写没有依据的行业达标值。桌面添加或复访若没有可靠来源证明，暂只分析引导和调用结果，不搭建伪造的“添加成功率”。

## 8. 执行阶段与验收清单

### 8.1 按交付结果推进

| 阶段 | 交付内容 | 完成标准 |
| --- | --- | --- |
| A：材料与范围 | 主体、AppID、权属、商业模式和首发功能表 | 目标应用明确，材料缺口和待确认规则有处理记录 |
| B：转换可玩版本 | 插件版本、构建产物、资源预算和双端记录 | 两端可登录、加载并完整完成比赛，平台识别正确 |
| C：平台功能 | 桌面、隐私及适用广告/联机/云服务 | 开发阶段可验证项通过，线上限定验证项单独列出 |
| D：数据闭环 | 通道试通、事件登记、真机日志及看板 | 用户与事件可核对，首局、玩法、奖励三类分析可用 |
| E：备案与提审 | 内容资料、物料、自测记录、备案及版本审核状态 | 所需资质齐全、备案完成、版本通过审核 |
| F：上线与观察 | 正式版本、桌面补验、指标和异常处置记录 | 线上专属流程验证完成，首批问题可定位并安排更新 |

阶段 B 后有适合申报的包体即可推进备案，与 C/D 和物料准备并行。若最终首发范围含联机或自定义分析，相关验收必须完成；延期需要明确调整范围，不能默默当作已实现。

### 8.2 提审与发布检查

- [ ] 主体、目标应用、名称、权属与适用软著附件核对完成。
- [ ] 前置备案资料、电子核验与核准状态有实际记录；发布前满足审批条件。

- [ ] ZIP 与版本号符合要求，目标应用的实际包体限制已确认。
- [ ] 登录、过期与换号处理通过；隐私披露、授权和拒绝行为一致。
- [ ] 桌面功能开发阶段可测项完成，线上补验有明确步骤。
- [ ] 首发所有可见玩法和平台入口真实可用。
- [ ] 广告完成、跳过、无填充、失败、重复回调和奖励写入通过验收。
- [ ] 首发包含联机时，双端开赛、结算、重赛、断线与房主变化通过。
- [ ] 首发包含自定义分析时，通道、字段、去重和测试隔离通过。

### 8.3 真机验证方法

官方支持上传开发包自测，也提供 TapTap MiniGame Debugger。使用有测试权限的账号；本地调试要求电脑打开小游戏代码包根目录，手机与电脑处于同一局域网。测试账号可在小游戏包体管理中配置。

Android 可用 Chrome DevTools；iOS 可先看 vConsole，Safari 断点调试按官方步骤使用 macOS。当前 Windows 环境的本地检查不能代替 iOS 真机验证。设备和 TapTap 客户端版本按官方调试页确认。[真机调试指南](https://developer.taptap.cn/minigameapidoc/dev/dev-support/debugging/)

覆盖首装冷启动、缓存启动、更新、分包下载失败、完整比赛、连续再玩、横屏和安全区、全屏左右输入、音频、广告返回、前后台切换与弱网。使用实际上传包验收，记录包版本、基础库、系统、设备及插件版本；不使用 Creator 编辑器截图替代游戏真机证据。

### 8.4 上线后的立即检查

- 从正式游戏页启动，核验发布版本、资源和存档，确认没有测试配置残留。
- 两端补验桌面完整流程，iOS 不以状态查询冒充已经添加。
- 检查平台启动与用户数据；自定义事件及广告收入分别核对各自来源。
- 观察首局加载、完赛、再玩、奖励和联机错误，区分版本问题与样本不足。
- 预备修复包与异常处置步骤；能否灰度或回退需以后台实际能力为准，不假设首次发布支持灰度。

## 9. 待确认事项：已有结论、影响与关闭方式

以下只保留公开资料无法确定的具体问题，不将已经找到的广告/联机 API 继续列为“平台是否支持”。

| 问题 | 已有结论 | 影响哪个阶段 | 如何关闭 |
| --- | --- | --- | --- |
| 无内购普通小游戏是否必须交软著证书 | 通用清单与小游戏专属条款的适用关系未明确；权利人信息需准备 | 备案材料与提审 | 实际表单和人工书面答复分别确认备案/版本环节；如必交，安排证书及授权 |
| Cocos 首包、总包和分包上限 | 官方页面有 20 MB、60M+ 及 Unity 压缩首包不同口径 | 包体预算和上传 | 确认对象、压缩方式与准确上限，保存规则依据，调整资源后再提交 |
