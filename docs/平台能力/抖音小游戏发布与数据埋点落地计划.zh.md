## 2. 上线顺序：哪些步骤必须等前一步

官方提供无版号游戏经小游戏备案后办理 ICP 核准的流程；官方发布指引同时明确，开通内购需要提交版号等完整资质。不能把“广告变现”直接等同于无需审批，也不能把软著、小游戏备案、ICP 核准和版号混为一项。

未上线、无版号项目的主要依赖关系：

```text
主体认证与软著等材料准备
  → 基础信息审核通过＋测试版本审核通过
  → 平台自动申报小游戏备案
  → 小游戏备案通过，开放无版号游戏 ICP 核准入口
  → ICP 核准通过，并满足其余发布条件
  → 发布
```

有版号游戏按官方对应路径处理，不机械套用上面的小游戏备案步骤。参考：[小游戏备案申报](https://developer.open-douyin.com/docs/resource/zh-CN/mini-game/guide/minigame/game-filing-application-works)、[ICP 核准指引](https://developer.open-douyin.com/docs/resource/zh-CN/mini-game/guide/minigame/icp/icp-filings)、[发布与商业能力开通](https://developer.open-douyin.com/docs/resource/zh-CN/mini-game/guide/minigame/release)。

注意：官网最新页面使用“ICP 核准”表述，部分旧链接和后台说明仍保留“ICP备案”。这也不同于自有服务器网站域名的备案，不可用已有网站备案代替小游戏的流程。

## 3. 哪些环节最花时间

**优先防范审批串行等待、反复补件和抖音真机适配。**下表将官方办理口径与项目工作量判断分开列示，不把它们相加当作确定上线日期。

| 环节 | 时效依据或工作量判断 | 提前行动 |
| --- | --- | --- |
| 软著与名称/主体对应 | 以实际申请渠道进度为准，本次未估算软著办理时间 | 申请阶段就核对上线名称、软件简称、权利人与发布主体，减少授权和改名返工 |
| 主体认证 | 官方企业身份约 3 个工作日、个人约 1 个工作日；验证等其他环节另计 | 等软著时先完成账号认证，核查结算主体 |
| 首版 QA | 官方预计 1–3 个工作日；退回修改会增加轮次 | 尽早做完整可提审版本，覆盖实际合作宿主 |
| 小游戏备案 | 主流程文档明确不保证监管处理时间 | 基础信息和版本过审后查看自动申报状态；不可仅拿到软著就认为已进入备案 |
| ICP 核准 | 抖音平台审查 1–3 个工作日；材料齐全准确后，工信部规定管局在 20 个工作日内办理 APP 备案 | 预备负责人、地址、证件及属地附件，收到短信后 24 小时内完成核验 |
| 抖音资源适配与真机排障 | 项目判断：中到高，需先构建验证才能估工期 | 先跑通 iOS/Android 的加载、整局比赛、广告返回及音频/输入恢复 |
| 侧边栏接入 | 项目判断：中；代码外还包括美术、领奖持久化和完整流程测试 | 提前设计入口并申请所需真机测试支持 |
| 联机/实际后端/内购 | 项目判断：若首发必需，可能成为最大的开发工作项 | 明确首发边界，分别估算；云存档不是本次查到的普遍上架必接项 |

时效依据：[主体认证](https://developer.open-douyin.com/docs/resource/zh-CN/developer/join/join-into-developer-platform)、[首版提审](https://developer.open-douyin.com/docs/resource/zh-CN/mini-game/guide/minigame/examineguide)、[小游戏备案 FAQ](https://developer.open-douyin.com/docs/resource/zh-CN/mini-game/guide/minigame/game-filing-application-works)、[ICP 核准步骤](https://developer.open-douyin.com/docs/resource/zh-CN/mini-game/guide/minigame/icp/icp-filings)、[工信部 APP 备案通知第七项](https://www.gov.cn/zhengce/zhengceku/202308/content_6897341.htm?type=mobile-internet)。

20 个工作日指管局收到齐全准确材料后的办理环节，不是从准备软著起计算的整个上线周期；退件、补件、平台审查、前置小游戏备案和节假日另算。抖音个别专项指引对小游戏备案有预估天数，但本项目排期采用主流程的不承诺固定时效口径。

## 4. 材料准备清单

### 4.1 账号、资质与商业资料

| 准备项 | 需要准备什么 | 完成标准 |
| --- | --- | --- |
| 主体认证 | 个人身份证及实名验证；企业/个体户证照、负责人资料及后台要求的验证材料 | 主体认证通过，团队权限设置完成 |
| 游戏名称与软著 | 软著证书、登记信息；主体不一致时补齐运营/发行授权链 | 名称、权利人和授权关系符合审核要求 |
| 基础资料 | 名称、图标、简介、详细介绍、联系人、适龄分段及说明 | 基础信息审核通过 |
| 内容与版权 | 美术、模型、字体、音乐音效的许可依据；游戏内容自审 | 可说明素材权利来源，按真实功能完成后台自审确认 |
| 隐私与用户协议 | 实际采集的数据、用途、第三方服务、联系方式与权利处理方式 | 后台披露与代码行为一致；不强迫非必要授权 |
| 小游戏备案 | 平台要求的作品与资质材料，已审核通过的版本 | 备案通过；已有符合要求版号批文的游戏按官方免重复备案路径处理 |
| ICP 核准 | 主办者、负责人、游戏与前置审批材料，按主体所在地区要求准备 | 取得核准号后才能上架 |
| 广告及结算 | 申请流量主、创建真实广告位，补齐主体对应的结算资料 | 广告真机可用，结算资格和信息已确认 |
| 内购（如采用） | 版号等资质、支付开通、客服、订单与发货校验 | 按当前宿主及操作系统政策完成支付全流程验收 |

官方支持个人主体创建小游戏，但个人与企业的能力和结算条件不能相互套用；应以当前主体后台核验。参考：[入驻常见问题](https://developer.open-douyin.com/docs/resource/zh-CN/developer/join/issues)、[主体认证](https://developer.open-douyin.com/docs/resource/zh-CN/developer/join/join-into-developer-platform)。

软著规则包括：同一软著仅支持一款小游戏在线运营；游戏名称须符合软著名称对应规则；主体不一致须有授权。自审报告当前可在后台确认。参考：[小游戏资质规范](https://developer.open-douyin.com/docs/resource/zh-CN/mini-game/operation1/norms/credential-norms-for-mini-game)。

### 4.2 实名、防沉迷与适龄

按游戏实际情况完善适龄提示、健康游戏忠告及适用资质信息；本项目既有 8+ 内容调整计划只能作为内容准备的一部分，不能替代平台审核。已有版号的在运营游戏需按官方指引办理中宣部实名系统渠道绑定。平台是否代为提供某项技术能力，要在实际应用及宿主中核实，不能仅凭 `tt.login` 已调用就认定完成实名、防沉迷。

参考：[基础信息、隐私与适龄](https://developer.open-douyin.com/docs/resource/zh-CN/mini-game/guide/minigame/improve-information)、[内容规范](https://developer.open-douyin.com/docs/resource/zh-CN/mini-game/operation1/norms/content-norms-for-mini-game)、[实名系统渠道绑定](https://developer.open-douyin.com/docs/resource/zh-CN/mini-game/guide/minigame/realnameauthentication)。

准备至少 iOS、Android 各一台测试设备。只有业务确有需要时再配置后端、CDN 和对应安全域名；证件、账号密码与 AppSecret 不写入仓库或客户端。

## 5. 功能接入：必接、条件必接与可后置

### 5.1 适用条件

| 能力 | 官方适用条件 | 项目落地重点 |
| --- | --- | --- |
| 侧边栏复访 | 所有小游戏必须接入 | 使用 `tt.navigateToScene`，完整验证前往侧边栏、真实复访识别和配置奖励的领取 |
| 客服 | 内购游戏必须接入 | 有真实可用入口及处理流程；非内购也建议保留问题反馈方式 |
| 敏感词/内容安全 | 存在用户自定义文字输入时必须接入 | 检查昵称、房间名等真实输入场景 |
| 网络安全域名 | 使用对应网络能力时 | 配置 request/socket/uploadFile/downloadFile 白名单及 HTTPS/WSS |

参考：[必接能力](https://developer.open-douyin.com/docs/resource/zh-CN/mini-game/guide/minigame/essential-skills)、[侧边栏接入](https://developer.open-douyin.com/docs/resource/zh-CN/mini-game/operation1/user-ops/-retention/sidebar)、[版本提审指引](https://developer.open-douyin.com/docs/resource/zh-CN/mini-game/guide/minigame/examineguide)。

### 5.2 侧边栏复访：单独安排开发与验收

**完成标准不是“有一个跳转按钮”，而是能正确识别真实复访。**

- [ ] 大厅提供清晰入口和可关闭的引导界面。
- [ ] 通过 `tt.checkScene` 判断宿主能力，再决定入口展示；不硬编码宿主范围。
- [ ] 点击入口调用 `tt.navigateToScene`，处理失败或不支持的情况。
- [ ] 在 `game.js` 运行时机同步监听 `tt.onShow`，保留判断来源所需信息。
- [ ] 同时覆盖冷启动和热启动，按最新官方来源参数判定复访。
- [ ] 若配置复访奖励，真实复访后才允许领取；保存领取状态并防止重复发放。
- [ ] 先用 IDE 或场景参数模拟；上线前完整真机流程按官方指引联系客服申请测试加白。

跳转成功不等于复访完成，也不能只靠自定义 query 冒充真实来源。未上线游戏通常不会直接出现在真实侧边栏中，测试支持应提前安排。

依据：[侧边栏技术与测试指南](https://developer.open-douyin.com/docs/resource/zh-CN/mini-game/develop/guide/open-ability/Introduction-for-tech)。

### 5.3 可以后续接入的能力

云存档、排行榜、联机不是本次查到的普遍上架必接项；是否首发取决于产品范围。若保留入口，必须有真实可用实现。

添加桌面、订阅消息、推荐流直出、达人任务及买量按运营计划后续评估；专项活动可能另有准入要求。参考：[官方文档指引的推荐能力](https://developer.open-douyin.com/docs/resource/zh-CN/mini-game/guide/overview)。

## 6. 当前项目缺口与开发落点

2026-09-30 已复核以下本地代码与配置。这些是实现现状，不代表抖音真机验收通过。

| 项目 | 当前证据 | 后续工作 |
| --- | --- | --- |
| 平台选择 | `PlatformManager.ts` 已有 `BYTEDANCE` 分支 | 使用真实 AppID 构建并验证平台选择 |
| 登录/分享/广告 | `DouyinPlatform.ts` 有对应接口实现 | 逐项核对现行 API 和宿主兼容，验证异常回调与生命周期 |
| 广告位 | `AdConfig.ts` 的抖音值为占位值 | 后台开通并替换真实广告位，检查重复回调及奖励幂等 |
| 玩家数据 | `BackendManager.ts` 统一选择 `MockBackend`，使用本地存储 | 若要求跨设备、排行、公平经济或内购，需建设实际后端及账号绑定 |
| 排行榜 | 抖音实现仍为 TODO/空结果 | 接入实际支持方案，或首版移除未实现入口 |
| 抖音联机 | `NetManager.ts` 只有微信房间实现，其他平台走 `DefaultNetRoom` | 按首版范围决定关闭未实现入口，或另做抖音房间适配与双机同步验收 |
| 侧边栏 | 在 `assets/scripts` 未检出 `navigateToScene`/`checkScene` 调用 | 补完整必接流程，保留宿主启动与复访来源信息 |
| 数据埋点 | 在 `assets/scripts` 未检出 `reportAnalytics`/`reportScene` | 新建统一统计入口并接入下述事件 |
| 分包 | `assets/race.meta` 仅为微信配置 subpackage；构建扩展仅注册 `wechatgame` | 新增并检查抖音 Bundle 配置、字体/音频/3D 资源加载和构建产物 |

现有平台层只抽取启动参数中的 `query`，后续需按官方 API 核对并保留复访判断所需场景信息，不能仅靠自定义 query 冒充真实侧边栏来源。

Cocos 3.8 支持直接构建抖音小游戏。普通分包方案当前默认主包不超过 4MB、整体包不超过 20MB，开通虚拟支付有不同总包额度；本项目先按普通广告游戏预算检查，超过预算再规划远程资源与域名。微信构建产物及其压缩、分包验证不能替代抖音验收。参考：[Cocos 发布教程](https://docs.cocos.com/creator/3.8/manual/zh/editor/publish/publish-bytedance-mini-game.html)、[抖音代码包限制](https://developer.open-douyin.com/docs/resource/zh-CN/mini-game/develop/guide/basic-function/subpackages/introduction)。

## 7. 数据埋点：首期统计什么、如何验证

### 7.1 首期方案

建议首期使用平台看板＋`tt.reportAnalytics` 自定义事件＋`tt.reportScene` 启动场景。这个方案直接使用宿主 API，不需要为这些事件另引入第三方分析 SDK 或自建接收服务器。登录、云存档、订单、联机后端是另外的业务需求。

平台增长分析用于渠道新增用户及后效；自定义事件用于具体玩法和漏斗；广告实际收入以流量主数据为准，不能用“看完广告次数”直接充当收入。参考：[增长分析](https://developer.open-douyin.com/docs/resource/zh-CN/mini-game/operation1/about-data/growth-analysis/game-task-rules)。

只有需要跨微信/抖音统一身份、明细导出、复杂路径/LTV 等能力时，再评估火山引擎等分析服务的支持范围、费用和隐私接入。参考：[火山引擎增长分析能力](https://developer.open-douyin.com/docs/resource/zh-CN/mini-game/operation1/about-data/advanced-analysis/volcengine)。

买量使用的转化回传与游戏内自定义分析分别验收。接了 `tt.reportAnalytics` 不代表巨量引擎的归因、转化优化和回传配置已完成；实际投放时另按投放产品配置和联调，当前不预设接入。

### 7.2 接入与验证步骤

1. 先列明业务问题、事件名、触发时机、字段名、字段类型、去重规则、负责人和版本。
2. 后台进入“数据 → 自定义分析 → 事件管理”，先注册事件和字段。
3. 游戏经统一统计模块调用抖音适配器的 `tt.reportAnalytics(event, data)`；业务代码不散落 `tt.*`。
4. 字段首期统一采用后台明确支持的字符串或数值；例如布尔状态可规范为 0/1。不要上传嵌套对象、角色轨迹、昵称、手机号或登录凭证。
5. 上传测试版本，在后台埋点验证中扫码绑定设备、选择事件，再用该设备触发。
6. 检查事件数量、字段、顺序和失败分支。官方说明验证日志可能延迟 2–3 分钟，IDE 本地预览不支持该验证。
7. 建立事件分析与漏斗，按游戏版本、宿主和测试标记筛选；验证数据不要混入正式运营判断。

参考：[上报 API](https://developer.open-douyin.com/docs/resource/zh-CN/mini-game/develop/api/javascript-api/data-analysis/tt-report-analytics)、[事件管理及验证](https://developer.open-douyin.com/docs/resource/zh-CN/mini-game/operation1/about-data/advanced-analysis/events)。

### 7.3 首批事件字典（建议，尚未接入）

| 事件 | 触发时机与次数 | 主要字段 | 回答的问题 |
| --- | --- | --- | --- |
| `lobby_ready` | 每次冷启动首次可操作大厅一次 | 加载耗时、来源分类 | 进入游戏后有多少人到达大厅 |
| `tutorial_step` | 每个教学步骤首次进入/完成 | 步骤、状态 | 玩家在哪一步不理解或离开 |
| `race_start` | 每局正式开始一次 | 模式、距离、难度、角色、本地/联机 | 什么玩法最受欢迎 |
| `race_end` | 本地玩家完成或明确退出时一次 | 完成/退出、耗时、名次、完成进度 | 完赛率、时长、难度是否合理 |
| `race_again` | 结算页确认再来一局一次 | 上局模式、距离 | 玩家是否愿意继续玩 |
| `rewarded_ad_request` | 玩家主动请求一次 | 广告入口 | 有多少用户愿意看广告 |
| `rewarded_ad_result` | 一次请求的终态一次 | 完成/跳过/错误/不可用、错误分类 | 广告在哪个环节失败 |
| `reward_grant` | 奖励实际写入成功后一次 | 奖励来源、币种、数量 | 看完后是否真正拿到奖励 |
| `progression_change` | 升级、突破或解锁提交成功 | 角色、操作、前后等级、花费 | 养成消耗与推进速度如何 |
| `sidebar_guide_click` | 点击前往侧边栏 | 入口 | 引导是否被使用 |
| `sidebar_return` | 按真实来源判定复访 | 复访来源分类 | 侧边栏是否带来回访 |
| `load_failure` | 一个加载尝试失败时 | 阶段、错误分类、重试次数 | 资源失败是否造成流失 |

公共字段建议：`build_version`、`schema_version`、`is_test`；模式/距离等只在相关事件携带。用户去重优先使用平台已有口径，不额外采集个人身份信息。确需服务端关联的局次 ID 和交易 ID 再单独设计，避免将高基数字段默认配置为分析维度。

### 7.4 统计口径、联机与性能

- 比赛帧更新只累计计数，结算时汇总划水次数、完美率、碰撞次数；不对每帧、每次水花、每个 AI 动作上报。
- 联机中的玩家行为由当前设备只报本地玩家一次；未来整场权威统计另设事件并指定房主/服务端为唯一生产者，避免八名选手或状态重放造成重复。
- `race_end` 的“退出”仅记录可观测的主动退出；杀进程或崩溃可能无终态。未结束局次应标记未知/未完成，不能全部算作主动退出。
- `rewarded_ad_result` 的完成与 `reward_grant` 分开；广告统计成功不应触发发奖，发奖也不应依赖埋点网络成功。
- 上报不可阻塞操作；捕获异常，不影响比赛/广告结算。幂等、防重和必要重试须有上限，禁止在 update 热路径格式化字符串或创建事件对象。
- 启动耗时使用后台配置的 `sceneId` 和 `tt.reportScene`，定义大厅可操作、比赛资源就绪等里程碑。耗时起止口径必须统一，不能用业务事件覆盖代码执行前的下载流失。
- 数据披露、授权与收集范围按实际实现核验，避免把其他“小程序”品类 API 直接套进“小游戏”。

参考：[启动场景 API](https://developer.open-douyin.com/docs/resource/zh-CN/mini-game/develop/api/javascript-api/data-analysis/tt-report-scene)、[小游戏隐私与数据规范](https://developer.open-douyin.com/docs/resource/zh-CN/mini-game/operation1/norms/game-rule)。

首期建立三个漏斗：大厅可操作 → 教学完成 → 首局开始 → 首局完成 → 再来一局；广告请求 → 广告完成 → 奖励到账；侧边栏引导 → 真实复访 → 配置奖励到账。留存与渠道分析使用平台对应看板，阈值先由小样本实测建立，不预设未经验证的行业达标值。

## 8. 执行阶段与验收清单

### 8.1 按交付结果推进

各项初始状态均为待完成或待后台核验，不能将计划列出视作已经接入。

| 阶段 | 交付内容 | 完成标准 |
| --- | --- | --- |
| A：确定材料与范围 | 主体、软著、版号现状及首发功能表 | 认证和授权路径明确；内购、联机等是否首发已决定 |
| B：跑通抖音版本 | AppID、构建产物、资源预算、真机记录 | iOS/Android 可加载并完成一局，未实现入口已按范围处理 |
| C：完成平台接入 | 侧边栏、适用的内容安全/客服、广告及隐私配置 | 必接能力、广告异常分支与奖励防重通过验证 |
| D：验证数据 | 事件字典、后台注册记录、上传版验证记录 | 字段及次数准确，三个漏斗可查看，发奖不依赖上报成功 |
| E：提审与审批 | 资料、自审记录、审核通过版本、备案及核准状态 | 按实际资质路径取得发布所需批准 |
| F：上线与观察 | 发布记录、首批指标、错误监控与发布异常处置预案 | 观察加载、完赛、广告奖励和复访，安排后续更新 |

### 8.2 提审前逐项检查

- [ ] 主体、名称、软著与授权关系核对完成，基础信息符合后台要求。
- [ ] 图标、简介、三张实机截图、更新说明及适龄信息已准备。
- [ ] 版权依据、隐私与用户协议和实际代码行为一致。
- [ ] 侧边栏已按第 5.2 节验证；适用的内容安全和客服已完成。
- [ ] 首发功能真实可用，没有展示尚未实现的联机、排行或支付能力。
- [ ] 广告完成、提前关闭、无填充、失败和重复回调的处理已验证。
- [ ] 上传版本的埋点验证通过，测试数据能与正式数据区分。
- [ ] iOS、Android 及适用合作宿主回归完成，阻断问题已解决。
- [ ] 后台申请状态有记录，区分“已上传、已提审、已通过、已核准、已发布”。

### 8.3 真机与提审注意事项

- 准备三张游戏内截图和更新说明，所有可见功能与实际实现一致。
- iOS、Android 真机检查启动、分包下载、连续游戏、切前后台、弱网与加载失败恢复。
- 广告必须由用户主动触发；检查完整观看、提前关闭、无填充、加载失败及奖励发放。普通玩法不可被强制看广告阻断。
- 检查刘海安全区、音频恢复、全屏左右输入、拒绝头像昵称授权后的游玩。
- 当前版本提审指南自 2026-04-20 起要求对符合条件的合作宿主默认多端回归，不能只测抖音一个 App。
- 官方灰度能力适用于已有线上版本后的更新。首次上线先用上传测试版本做限定测试；上线后的更新再按条件灰度发布。
