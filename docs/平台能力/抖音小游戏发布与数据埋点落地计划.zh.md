若新包仍超限，继续检查实际分包配置、重复或未引用资源，再决定资源优化或远程加载方案。分包有助于控制主包与启动下载，但不会自动降低所有包的总大小。

不要把该包当成已经满足正式上线性能要求。ZIP 会增加首次解压耗时、占用本机缓存；目前仍沿用临时不生成 ASTC 的功能测试资源，需要继续评估正式纹理策略及包体增长空间。恢复 ASTC 或改动任何资源后，都应重新测量压包结果，不沿用 19.73MiB 的估算。

### 1.5 备用方案：远程资源加载

**适用条件：**后续完整资源继续增长、正式纹理策略使本地包超限，或本地 ZIP 的真机启动和缓存表现不合适时，再评估将 `race` 资源包放到 HTTPS 资源托管地址，必要时也迁移 `music`，保留登录启动资源与程序代码在上传包里。图片、模型、场景、动作仍作为完整游戏的一部分，在运行时下载；不是删除娱乐模式。

最新无 ASTC 测试构建中，`assets/race` 约 **23.529MiB**，`assets/music` 约 **0.992MiB**。程序已使用 `assetManager.loadBundle('race')` 和 `assetManager.loadBundle('music')`，可利用 Cocos 的远程 Bundle 配置。是否还需要处理启动依赖、加载失败提示与重试，应以新构建和真机结果验证，不能只把目录移出上传包。

对娱乐资源的专项统计：已单独定位的娱乐界面约 **0.463MiB**，道具模型及贴图约 **0.350MiB**（部分共用），玩具鲨约 **0.213MiB**。这些不含共用资源和合并 JSON 包，不能视为娱乐模式全部成本，但现有证据不支持将超限主要归因于娱乐美术未压缩。相比之下，角色模型及贴图约 **8.125MiB**，角色动作曲线约 **4.959MiB**，其他界面约 **5.854MiB**。

落实顺序：

1. **准备资源地址。**已有 HTTPS 域名、对象存储或 CDN 时，先确认可公开下载静态文件；没有时先准备托管空间。这一步不需要自建登录、比赛或统计服务器。项目客户端不保存对象存储的管理密钥。
2. **配置抖音下载域名。**在应用开发设置中配置实际使用的 `downloadFile` 合法域名；根据实际网络请求补充需要的其他域名类型。使用正式 HTTPS 地址，不能把电脑上的本地目录当作手机可访问的资源服务器。
3. **只调整抖音 Bundle 配置。**将 `race`（需要时包括 `music`）设为远程包，压缩类型采用支持远程的方式，取消其本地小游戏分包属性；保留微信自己的配置。构建面板填写真实资源服务器地址，恢复适当的 GPU 纹理压缩，不再以跳过所有纹理压缩作为最终压包手段。
4. **构建并上传对应版本。**核对 Cocos 生成的 `remote` 资源、客户端远程 Bundle 列表、资源地址和版本信息；按生成目录结构部署资源，保证客户端引用的每个配置、图片和二进制文件可下载。平台允许的程序脚本保留在本地包，不能自行将全部代码放到 CDN。
5. **检查上传目录。**托管用 `remote` 文件夹不应再次被计入小游戏上传包；检查本地包实际小于应用当前 20MB 上限，不能只估算原包减去源文件大小。
6. **真机验收。**手机扫码后先验证资源首次下载，再验证缓存复用、大厅、标准及娱乐比赛、结算、音乐、弱网失败和重试、切前后台恢复。仍需独立接入侧边栏、广告及后台埋点。

当前没有配置或部署远程资源，暂无必要要求用户准备托管地址。若未来采用本节方案，届时再确认用户已有的 HTTPS 域名、对象存储或 CDN；账号、费用和服务商选择依实际需求决定。

依据：[Cocos Asset Bundle 的远程配置与加载](https://docs.cocos.com/creator/3.8/manual/zh/asset/bundle.html)、[抖音下载域名要求](https://developer.open-douyin.com/docs/resource/zh-CN/mini-game/develop/api/javascript-api/media/picture/tt-get-image-info)。

## 2. 上线顺序：哪些步骤必须等前一步

官方提供无版号游戏经小游戏备案后办理 ICP 核准的流程；官方发布指引同时明确，开通内购需要提交版号等完整资质。不能把“广告变现”直接等同于无需审批，也不能把软著、小游戏备案、ICP 核准和版号混为一项。

未上线、无版号项目的主要依赖关系：

```text
主体认证与软著等材料准备
  → 基础信息审核通过＋测试版本审核通过
  → 平台自动申报小游戏备案
  → 小游戏备案通过，开放无版号游戏 ICP 核准入口
  → ICP 核准通过，并满足其余发布条件
  → 发布
```

有版号游戏按官方对应路径处理，不机械套用上面的小游戏备案步骤。参考：[小游戏备案申报](https://developer.open-douyin.com/docs/resource/zh-CN/mini-game/guide/minigame/game-filing-application-works)、[ICP 核准指引](https://developer.open-douyin.com/docs/resource/zh-CN/mini-game/guide/minigame/icp/icp-filings)、[发布与商业能力开通](https://developer.open-douyin.com/docs/resource/zh-CN/mini-game/guide/minigame/release)。

注意：官网最新页面使用“ICP 核准”表述，部分旧链接和后台说明仍保留“ICP备案”。这也不同于自有服务器网站域名的备案，不可用已有网站备案代替小游戏的流程。

## 3. 哪些环节最花时间

**优先防范审批串行等待、反复补件和抖音真机适配。**下表将官方办理口径与项目工作量判断分开列示，不把它们相加当作确定上线日期。

| 环节 | 时效依据或工作量判断 | 提前行动 |
| --- | --- | --- |
| 软著与名称/主体对应 | 以实际申请渠道进度为准，本次未估算软著办理时间 | 申请阶段就核对上线名称、软件简称、权利人与发布主体，减少授权和改名返工 |
| 主体认证 | 官方企业身份约 3 个工作日、个人约 1 个工作日；验证等其他环节另计 | 等软著时先完成账号认证，核查结算主体 |
| 首版 QA | 官方预计 1–3 个工作日；退回修改会增加轮次 | 尽早做完整可提审版本，覆盖实际合作宿主 |
| 小游戏备案 | 主流程文档明确不保证监管处理时间 | 基础信息和版本过审后查看自动申报状态；不可仅拿到软著就认为已进入备案 |
| ICP 核准 | 抖音平台审查 1–3 个工作日；材料齐全准确后，工信部规定管局在 20 个工作日内办理 APP 备案 | 预备负责人、地址、证件及属地附件，收到短信后 24 小时内完成核验 |
| 抖音资源适配与真机排障 | 项目判断：中到高，需先构建验证才能估工期 | 先跑通 iOS/Android 的加载、整局比赛、广告返回及音频/输入恢复 |
| 侧边栏接入 | 项目判断：中；代码外还包括美术、领奖持久化和完整流程测试 | 提前设计入口并申请所需真机测试支持 |
| 联机/实际后端/内购 | 项目判断：若首发必需，可能成为最大的开发工作项 | 明确首发边界，分别估算；云存档不是本次查到的普遍上架必接项 |

时效依据：[主体认证](https://developer.open-douyin.com/docs/resource/zh-CN/developer/join/join-into-developer-platform)、[首版提审](https://developer.open-douyin.com/docs/resource/zh-CN/mini-game/guide/minigame/examineguide)、[小游戏备案 FAQ](https://developer.open-douyin.com/docs/resource/zh-CN/mini-game/guide/minigame/game-filing-application-works)、[ICP 核准步骤](https://developer.open-douyin.com/docs/resource/zh-CN/mini-game/guide/minigame/icp/icp-filings)、[工信部 APP 备案通知第七项](https://www.gov.cn/zhengce/zhengceku/202308/content_6897341.htm?type=mobile-internet)。

20 个工作日指管局收到齐全准确材料后的办理环节，不是从准备软著起计算的整个上线周期；退件、补件、平台审查、前置小游戏备案和节假日另算。抖音个别专项指引对小游戏备案有预估天数，但本项目排期采用主流程的不承诺固定时效口径。

### 5.2 侧边栏复访：单独安排开发与验收

**完成标准不是“有一个跳转按钮”，而是能正确识别真实复访。**

- [ ] 大厅提供清晰入口和可关闭的引导界面。
- [ ] 通过 `tt.checkScene` 判断宿主能力，再决定入口展示；不硬编码宿主范围。
- [ ] 点击入口调用 `tt.navigateToScene`，处理失败或不支持的情况。
- [ ] 在 `game.js` 运行时机同步监听 `tt.onShow`，保留判断来源所需信息。
- [ ] 同时覆盖冷启动和热启动，按最新官方来源参数判定复访。
- [ ] 若配置复访奖励，真实复访后才允许领取；保存领取状态并防止重复发放。
- [ ] 先用 IDE 或场景参数模拟；上线前完整真机流程按官方指引联系客服申请测试加白。

跳转成功不等于复访完成，也不能只靠自定义 query 冒充真实来源。未上线游戏通常不会直接出现在真实侧边栏中，测试支持应提前安排。

依据：[侧边栏技术与测试指南](https://developer.open-douyin.com/docs/resource/zh-CN/mini-game/develop/guide/open-ability/Introduction-for-tech)。

## 7. 数据埋点：首期统计什么、如何验证

### 7.1 首期方案

首期已采用平台看板＋`tt.reportAnalytics` 自定义事件；`tt.reportScene` 启动场景作为后续扩展，当前未接入。直接使用宿主 API，不需要为这些事件另引入第三方分析 SDK 或自建接收服务器。登录、云存档、订单、联机后端是另外的业务需求。

平台增长分析用于渠道新增用户及后效；自定义事件用于具体玩法和漏斗；广告实际收入以流量主数据为准，不能用“看完广告次数”直接充当收入。参考：[增长分析](https://developer.open-douyin.com/docs/resource/zh-CN/mini-game/operation1/about-data/growth-analysis/game-task-rules)。

只有需要跨微信/抖音统一身份、明细导出、复杂路径/LTV 等能力时，再评估火山引擎等分析服务的支持范围、费用和隐私接入。参考：[火山引擎增长分析能力](https://developer.open-douyin.com/docs/resource/zh-CN/mini-game/operation1/about-data/advanced-analysis/volcengine)。

买量使用的转化回传与游戏内自定义分析分别验收。接了 `tt.reportAnalytics` 不代表巨量引擎的归因、转化优化和回传配置已完成；实际投放时另按投放产品配置和联调，当前不预设接入。

### 7.2 接入与验证步骤

1. 先列明业务问题、事件名、触发时机、字段名、字段类型、去重规则、负责人和版本。
2. 后台进入“数据 → 自定义分析 → 事件管理”，先注册事件和字段。
3. 游戏经统一统计模块调用抖音适配器的 `tt.reportAnalytics(event, data)`；业务代码不散落 `tt.*`。
4. 字段首期统一采用后台明确支持的字符串或数值；例如布尔状态可规范为 0/1。不要上传嵌套对象、角色轨迹、昵称、手机号或登录凭证。
5. 上传测试版本，在后台埋点验证中扫码绑定设备、选择事件，再用该设备触发。
6. 检查事件数量、字段、顺序和失败分支。官方说明验证日志可能延迟 2–3 分钟，IDE 本地预览不支持该验证。
7. 建立事件分析与漏斗，按游戏版本、宿主和测试标记筛选；验证数据不要混入正式运营判断。

参考：[上报 API](https://developer.open-douyin.com/docs/resource/zh-CN/mini-game/develop/api/javascript-api/data-analysis/tt-report-analytics)、[事件管理及验证](https://developer.open-douyin.com/docs/resource/zh-CN/mini-game/operation1/about-data/advanced-analysis/events)。

| `sidebar_jump_result` / 137518 | 跳转调用的一次成功/失败终态 | `entry`、`result` 字符串 |
| `sidebar_return` / 137519 | 冷启动或最新展示回调满足真实侧边栏来源 | `source`、`scene` 字符串 |

口径补充：`load_ms` 从入口脚本执行到首次大厅入口建立，不涵盖代码执行前的平台下载耗时；`race_again` 不包含回大厅重新选比赛或生涯下一关。`race_end.outcome` 为 `completed/dnf/eliminated/quit`，杀进程不假报 `quit`；未完赛名次不直接作为完赛名次分析。`test_type=ai_debug` 可过滤调试比赛，不逐个统计 AI。真实来源的 `sidebar_return` 可发生在打开引导之前，不能要求每次复访都有同次引导事件。

### 7.4 后续扩展事件（尚未实现）

| 事件 | 触发时机与次数 | 主要字段 | 回答的问题 |
| --- | --- | --- | --- |
| `tutorial_step` | 每个教学步骤首次进入/完成 | 步骤、状态 | 玩家在哪一步不理解或离开 |
| `rewarded_ad_request` | 玩家主动请求一次 | 广告入口 | 有多少用户愿意看广告 |
| `rewarded_ad_result` | 一次请求的终态一次 | 完成/跳过/错误/不可用、错误分类 | 广告在哪个环节失败 |
| `reward_grant` | 奖励实际写入成功后一次 | 奖励来源、币种、数量 | 看完后是否真正拿到奖励 |
| `progression_change` | 升级、突破或解锁提交成功 | 角色、操作、前后等级、花费 | 养成消耗与推进速度如何 |
| `load_failure` | 一个加载尝试失败时 | 阶段、错误分类、重试次数 | 资源失败是否造成流失 |

公共字段建议：`build_version`、`schema_version`、`is_test`；模式/距离等只在相关事件携带。用户去重优先使用平台已有口径，不额外采集个人身份信息。确需服务端关联的局次 ID 和交易 ID 再单独设计，避免将高基数字段默认配置为分析维度。

### 7.5 统计口径、联机与性能

- 比赛帧更新只累计计数，结算时汇总划水次数、完美率、碰撞次数；不对每帧、每次水花、每个 AI 动作上报。
- 联机中的玩家行为由当前设备只报本地玩家一次；未来整场权威统计另设事件并指定房主/服务端为唯一生产者，避免八名选手或状态重放造成重复。
- `race_end` 的“退出”仅记录可观测的主动退出；杀进程或崩溃可能无终态。未结束局次应标记未知/未完成，不能全部算作主动退出。
- `rewarded_ad_result` 的完成与 `reward_grant` 分开；广告统计成功不应触发发奖，发奖也不应依赖埋点网络成功。
- 上报不可阻塞操作；捕获异常，不影响比赛/广告结算。幂等、防重和必要重试须有上限，禁止在 update 热路径格式化字符串或创建事件对象。
- 启动耗时使用后台配置的 `sceneId` 和 `tt.reportScene`，定义大厅可操作、比赛资源就绪等里程碑。耗时起止口径必须统一，不能用业务事件覆盖代码执行前的下载流失。
- 数据披露、授权与收集范围按实际实现核验，避免把其他“小程序”品类 API 直接套进“小游戏”。

参考：[启动场景 API](https://developer.open-douyin.com/docs/resource/zh-CN/mini-game/develop/api/javascript-api/data-analysis/tt-report-scene)、[小游戏隐私与数据规范](https://developer.open-douyin.com/docs/resource/zh-CN/mini-game/operation1/norms/game-rule)。

本轮入库验证完成后，先建立“大厅 → 比赛开始 → 完赛”及“引导打开 → 跳转成功 → 真实复访”的观察路径；跨会话复访还需结合平台用户和时间窗口口径。教学、广告奖励及养成尚未实现其埋点，不提前声称完整漏斗可用。后续扩展教学完成率与“广告请求 → 完成 → 奖励到账”，如配置复访奖励再增加奖励到账事件。留存与渠道分析使用平台对应看板，阈值先由小样本实测建立。

### 8.3 真机与提审注意事项

- 准备三张游戏内截图和更新说明，所有可见功能与实际实现一致。

- 官方灰度能力适用于已有线上版本后的更新。首次上线先用上传测试版本做限定测试；上线后的更新再按条件灰度发布。
