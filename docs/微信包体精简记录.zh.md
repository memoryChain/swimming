### 动作存储编码

`extensions/wechat-race-subpackage/sampled-motion-storage.js` 在微信 `onAfterBuild` 中处理比赛分包的 Cocos JsonAsset。逐帧重复的字段名与骨骼名只存一份；整段动作保持恒定的旋转只存一份；变化的旋转存为数值数组。源文件 `assets/race/model-actions/tPose/*.json` 不变，`divePrep` 静态姿态不处理。

`RaceBundleLoader.ts` 在单资源和目录加载回调前调用 `SampledMotionStorage.ts`，还原原始结构并写回 JsonAsset 缓存。大厅角色预览、每个角色的动作覆盖和比赛全量加载都使用该入口，因此一份资源仅还原一次，不增加比赛逐帧工作。原格式仍能直接读取。

压缩前逐字段确认构建数据与源数据一致；缺动作或缓存不一致时拒绝构建。沿用 Creator 标准 JSON 序列化语义（源文件中的负零在原构建中同样写为零），不量化、不插值、不删帧。单机和联机读取同一套还原数据，不修改比赛模拟或同步协议。

对现有构建副本的实际处理结果：20 个动作、3,660 帧，20 个导入文件从 5,198,163 字节降至 3,627,046 字节，节省 1,571,117 字节（1.50 MiB）。全部动作逐字段、逐帧比对通过。

## 第三轮：UI 压缩覆盖与无损 PNG 优化

当前 199 张 UI 图片的 `.meta` 压缩配置如下。小图和首包 UI 保留原格式属于既定策略，避免 ASTC 与回退文件双份存储反而增大包体。

| 分类 | 数量 | 当前配置 |
| --- | ---: | --- |
| 分包较大透明 UI | 85 | ASTC 5×5，thorough，保留 PNG 回退 |
| 分包较大不透明 UI | 14 | ASTC 6×6，thorough，保留 JPG 回退 |
| 分包小图 | 95 | 原 PNG/JPG，不生成额外 ASTC |
| 首包 UI | 5 | 原 PNG/JPG，不生成额外 ASTC |

ASTC 属于有损纹理压缩，现有档位不能等同于逐像素无损。本轮不调整 ASTC 档位、回退质量或图片尺寸，只对源 PNG 做无损重编码。

`scripts/optimize-ui-images.py` 默认改为仅优化 PNG，JPG 保持原文件；有损 JPG 重编码必须显式传入 `--allow-lossy-jpeg`。PNG 重编码后逐像素比较 RGBA，并原样保留 ICC、sRGB、gAMA、cHRM、eXIf、pHYs 等非文本附加块，只删除不参与渲染的文本注释。16 位 PNG 与 APNG 保持原文件。

实际优化 **44 张 PNG**，源文件合计减少 **3,159,289 字节（3.01 MiB）**。全部 199 张图片的尺寸、解码像素、非文本附加块及 `.meta` 哈希复核一致，2 张 JPG 原文件哈希不变。原图备份位于 `temp/ui-image-optimizer/backups/20260922-013608/`，本地前后统计位于 `temp/package-audit/ui-images-lossless-result.json`。

此处节省量仅针对源文件，**不能再从第二轮的上传包估算中直接扣除 3.01 MiB**：Creator 会按原配置生成 ASTC 与回退图。需要完成图片重新导入并构建，才能计算上传包收益。当前 `build/wechatgame` 仍是旧构建。

验证命令：`pnpm test:ui-images`（6 项，覆盖像素、透明度、色彩信息及特殊格式）、`pnpm ui:images:check`、`pnpm test:ui-resources`、`pnpm textures:fix`、`pnpm textures:check`。不涉及运行时 UI、动画或联机状态变更。

## 第四轮：修复已构建产物漏执行后处理

01:45 上传仍报 `30935KB` 超限。检查 01:43:52 的最新构建日志发现，Creator 执行的插件仍只输出旧版主包统计，没有 `[motion-storage]` 和总包统计；构建目录中的 20 个动作全部保持未编码格式。源码中的新钩子已存在，但编辑器会话缓存的旧插件没有执行它，因此前面的离线估算不能作为实际包体结果。

该次构建的运行脚本已包含 `SampledMotionStorage` 和接入后的 `RaceBundleLoader`。在补做后处理前，从实际构建加载这两个模块和 Babel 辅助模块，以模拟 JsonAsset 分别验证单资源与目录加载；20 个动作、3,660 帧均逐字段还原一致。

新增独立入口 **`pnpm wechat:finalize`**，默认处理 `build/wechatgame`，也可传入当前工程内的其他构建目录。它检查项目身份、分包入口、实际产物中的解码器与加载器依赖，再核对全部动作与源数据，备份待修改的导入文件，执行原有无损编码并检查包体。重复执行不会重复编码，不需要重启 Creator。原始动作、构建脚本、图片、模型、音频和字体都不修改。

`pnpm wechat:check --build` 继续只读，但现在也会检查解码入口及动作是否已完成后处理，即使包体暂时低于上限，也能识别旧插件漏执行的情况，并提示运行独立入口。
