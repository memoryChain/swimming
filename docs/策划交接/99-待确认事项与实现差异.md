# 99｜待确认事项与实现差异

本文不是设计结论，而是交接时需要产品/策划确认的清单。凡是代码能确定的事实已写入 01–07；本页只列“实现与旧文档/直觉不一致”或“代码无法判断最终意图”的地方。

## 1. 已确认的实现差异

| 事项 | 当前代码事实 | 影响 |
| --- | --- | --- |
| 触控分手 | 正式 HUD 是全屏 `StrokeInput`，`InputRouter` 自动 LEFT/RIGHT 交替 | 不能按左右半屏设计操作说明 |
| 全局与角色时序 | 全局 0.72s 后进入 RACING；角色水下保持 2.00s、上浮 1.35s | 一段时间内已计时但仍不能划手 |
| 连击效果 | PERFECT 会加连击并统计，但没有连击叠速 | 旧字段 `combo bonus` 不应写成现行效果 |
| BAD 推进 | 普通 BAD 仍会走基础划水推进；超时 BAD 只给 0.08 微推进 | “失误=完全不前进”不准确 |
| AI 起步 | AI 可在玩家仍停在 DIVING 时先入水并开始马达 | 玩家等待跳水没有对称等待规则 |
| 结算等待 | 玩家完成后要等所有激活 AI 完赛 | 结果弹窗不是玩家触壁即出 |
| 状态层接入 | `efficiencyModifier` 作用在稳定划水加速；`qualityModifier` 当前未被读取 | 心率/体能设计仍有半接入状态 |

## 2. 请策划确认的设计问题

### Q1｜全屏自动左右交替是否为最终正式方案？

当前运行时已关闭 `InputManager.pointerInputEnabled`，备用左右半屏逻辑只保留给编辑器/调试。若要恢复显式左右操作，需要同时调整 HUD、InputRouter 和交互说明。

### Q2｜是否保留“全局 RACING 早于角色出水”的错位？

当前比赛计时和心率在 0.72s 后已经开始，而角色可能仍处于水下保持/上浮。若设计上希望玩家出水后才进入正式节奏，需要把 `RaceManager` 的状态切换改为读取角色上浮完成，而不是只使用固定 `GLIDE_SECONDS`。

### Q3｜心率/体能的质量修正是否应该真正进入判定？

现在 `qualityModifier` 已算出但不参与甜区或稳定性；`efficiencyModifier` 只乘稳定划水的主要加速。请确认这是刻意的渐进接入，还是待补齐的功能。

### Q4｜冲刺档位是否需要玩家可见、可解释？

当前 85% 进入冲刺，按 effortScore 切换 STEADY/PUSH/GAMBLE，只影响体能倍率；HUD 没有单独档位提示或主动冲刺按钮。请确认是否作为隐藏调试状态，或要做成正式策略操作。

### Q5｜AI 调试模式是否属于交付给玩家的正式功能？

`AI DEBUG`、AI 甜区盘和跟随 AI 镜头会出现在登录页/比赛 HUD，但代码注释把它定义为测试入口。请确认发布版本是否隐藏，或要改名为正式难度选择。

### Q6｜折返是否需要真实转身玩法？

当前 100/200m 只是位置映射和朝向翻转，没有触壁窗口、转身动作或损失。若策划案需要“转身”，需要补充判定、动画和数值规则后再写入正式文档。

### Q7｜体能耗尽是否要有硬代价？

当前耗尽只降低 modifier，不锁输入、不硬直、不直接清空速度。若要加入疲劳失速，应明确是影响轮速、推进、质量还是阻力，避免与现有心率 modifier 重复。

## 3. 交接建议

在上述问题未确认前，后续策划文档应使用“当前实现”措辞，不把未接入的字段写成玩家可感知规则；数值调整应通过 `tuning.json` 和调参面板验证后再更新本文档。
