## 已实施的第一轮优化

1. `GameFlowController` 用直接计数计算镜头名次，移除每帧 `filter/map/spread/sort/findIndex` 和选手包装对象；同距离玩家优先、隐藏对手排除的规则保持不变。镜头快照与名次结果改为实例缓存。
2. `RaceCameraDirector` 的水面转播、冲刺、俯视、海豚跳、转身路径复用向量和取景结果。开场及观战辅助路径仍有部分分配，不能声称整个模块零分配。
3. `Swimmer`/`SwimmerMotor` 复用 motor options 和冻结的空反馈数组；非空事件仍独立取出且消费一次。
4. 玩家水下泡沫有九个粒子系统。初始化时禁用；停发后保留实际存活粒子，待 `getParticleCount()` 归零才暂停并禁用组件。全休眠后停止轮询，下次水下发射重新启用；销毁时清理。
5. `SampledMotionStorage` 解码微信压缩动作时，为每条曲线的恒定骨骼旋转创建一份冻结副本并共享。变化旋转仍逐帧独立，源数据和数字不变。当前 canonical 20 个动作共 3660 个采样帧、84180 个旋转数组；按压缩器识别出的恒定骨骼核算，可减少 9462 个常驻数组。这是数组数量核算，不是实测节省 MB，也不覆盖全部角色专用动作。

这些改动减少热路径分配和空粒子组件工作，尚不能证明已经解决自动化报告中的全部 CPU/内存问题。引擎渲染帧处理仍是本样本最大的累计开销，后续需复测 draw call、相机 pass、材质/模型更新及纹理常驻内存。已有 AI 姿态降频、离屏冻结和 HUD 节流，不应重复当作缺失功能。

- JS Heap 81.2–90.6MB，约每 1–2 秒反复增长和回收。此范围与早前样本不同，不能解释成源码优化使堆变小。

`frameMove → _frameMoveEnd → render → execute → execute → v2 → g2 → finishVertex → visitVertex → rasterPass → record → record → anonymous → record → _updateRenderData → _updateGlobal → J3 → c4 → l`

其中这个 Call Tree 分支的 `_updateRenderData` 为 220.8ms，`_updateGlobal` 为 217.1ms，`J3` 为 216.9ms，`c4` 为 206.1ms，常量循环闭包 `l` 为 153.2ms。通过当前构建 `cocos-js/cc.ac681.js` 的 `J3`、`c4` 实现核实：这里遍历 render data 的 constants、textures、samplers、buffers，比较 uniform 数据并更新相应 buffer/descriptor。构建文件中的 `J3` 约在字符偏移 1232465、`c4` 约在 1233717（仅对应当前构建，非稳定源码行号）。`Array.from(...).find(...)` 出现在常量索引缓存未命中的分支，不能仅凭源码宣称它每帧都会执行。

另一次同阵容赛中只读检查返回 `state=racing`、玩家距离约 11.96m，实际启用相机为：UI `Camera`、`BroadcastCamera3D`、`WaterRefractionCamera`（有 RT）、`SwimmerOverlayCamera`。此前结算时观察到的相机组合已在赛中得到复核。RT 尺度减少像素量，但不能据此推断每台相机的渲染图 CPU 固定开销消失。尚未做关相机 A/B，不能把上述耗时定量分摊给折射或叠加相机。

### 工具限制与下一步优先级

微信工具显示 `Allocation sampling` 且单选状态可切换，但启动按钮仍为 `Take snapshot`；启动后实际生成 Heap Snapshot 2，没有开始/停止分配录制。切回 Heap snapshot 再选 sampling 也未改变该行为。因此本轮没有有效的 Allocation sampling 数据，不能根据此模式宣称找到了每帧分配最多的业务函数。Profile/Snapshot 保存入口也未得到可验证的本地导出文件，本记录保存面板读数、调用链和资源 UUID。

1. CPU 首先验证减少重复相机/pass 与渲染数据准备：对折射、叠加和常规主镜头做受控 A/B，再决定画质策略。不能仅降低 RT 分辨率就认定解决 CPU 问题。
2. 内存首先评估动作数据按阶段加载/缓存生命周期，再针对已证实的高分配路径复用输出。GC 已占脚本约 19.2%，但还没有把 GC 的责任精确分配给相机、姿态或引擎。
3. 模型变换、UBO 与骨骼驱动是下一层 CPU 重点；需要在多泳者近距离镜头下验证姿态降频是否同时减少模型 dirty/UBO 工作。现有离屏冻结和 AI 降频不能重复列作新优化。
4. 纹理、RT、GPU/native 内存必须另取真机口径；当前堆快照不支持判断它们是否是微信自动化总内存偏高的主因。本轮也没有得到内存泄漏证据。

本轮只追加定位记录，没有新增 runtime 修改，也未重跑上一轮已通过的代码检查。临时输入和全局诊断引用在离开工具前清除；原有构建和其他人的工作区修改保留。

- 普通自由泳曲线、蛙泳采样输出、碰撞 scratch vectors、正常 HUD 左右划水 guide 已有输出缓冲；名字／名次投影已有稳定向量与更新频率控制。没有将这些已有措施重复算成本轮改动。
- 展示动作 `sampleDebugActionMotion` 仍创建结果、rotations record、`Object.keys`、逐骨骼旋转数组及接触高度数组。主要发生于开场／领奖展示，不能作为普通自由泳全程 GC 的证据；常驻动作缓存也不能解释短期分配锯齿。
- 划水事件、转身状态返回值和网络编码／快照仍有分配。它们分别受输入、转身区间或网络会话门控，本轮未修改快照的所有权、事件生命周期或报文布局，不能声称整个比赛零分配。
