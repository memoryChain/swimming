# iOS 微信小游戏 DPR 限制

微信构建完成后，`extensions/wechat-race-subpackage/hooks.js` 调用
`wechat-ios-dpr.js`，在生成的 `game.js` 顶部插入初始化代码。
上限集中在 `IOS_MAX_DPR = 2.2`，修改后需重新构建微信小游戏。
不手工修改构建产物，也不修改本机 Cocos 引擎。

仅对微信返回 `platform: ios` 的设备生效：实际 DPR 为 `min(原生 DPR, 2.2)`。
原生 DPR 为 2 的设备保持 2；安卓、微信开发者工具和浏览器预览保持原行为。

Cocos 3.8.8 初始化时复制微信接口，因此必须早于 `web-adapter` 和引擎加载。
同时适配 `getWindowInfo` 和 `getSystemInfoSync` 的 `pixelRatio`，让画布、触摸
和安全区换算一致。若系统信息包含 `devicePixelRatio` 别名，也同步限制。
保留窗口尺寸和安全区原值；每次查询仍调用原接口，支持尺寸变化。

启动时只输出一次 `[DPR]` 日志，例如：

```text
[DPR] 平台=ios 原始=3 生效=2.2 iOS上限=2.2
```

原始值在修改前读取，生效值在修改后重新查询微信接口；安卓也打印但不限制 DPR。
日志不会在窗口查询、场景切换或比赛逐帧更新时重复输出。此值确认的是引擎读取的
像素比，实际画布分辨率仍可通过画布尺寸与窗口尺寸的比例核对。新增日志需重新构建
并上传新包，已发布的旧包不会自动出现此日志。

Creator 会话可能缓存构建插件：2026-09-26 曾出现新构建包仍注入旧版无日志代码。
构建后运行 `pnpm wechat:finalize`，由独立进程读取当前策略，备份并更新入口；
重复运行不会重复注入。上传前运行 `pnpm wechat:check -- --build`，会校验实际
入口是否包含完整最新策略和日志，而不只检查存在 DPR 标记。后处理备份位于
`temp/wechat-finalize-backups/`。重新打开 Creator 可以刷新缓存，但不自动重启编辑器。

此修改仅影响本机渲染分辨率，不改变单机或联机的模拟、输入侧别、帧率和同步协议。
DPR 从 3 降到 2.2 时，渲染像素量约为原来的 53.8%，但发热与总功耗不会同比下降；
模型顶点处理、CPU 逻辑等开销仍然存在，画面和文字锐度也会降低。

运行 `npm run test:wechat` 检查启动顺序、平台隔离、旧基础库回退、低 DPR 保留和重复构建。
发布前在 iOS 真机重新构建后验证：首屏及比赛清晰度、左右半屏划水、海豚按钮、
安全区、切后台恢复和联机比赛；相同亮度、帧率与场景下对比持续游玩发热。
自动化检查不代表已完成真机温度验证。
