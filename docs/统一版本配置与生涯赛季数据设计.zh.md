# 统一版本配置与生涯赛季数据设计

更新：2026-09-28。状态：**配置文件已创建，运行时读取和云端发布尚未实现**。本文统一此前排行榜和生涯提案中的版本口径；不代表当前数据库已有这些配置、集合或管理操作。

## 1. 三种版本独立，集中管理

| 配置字段 | 中文含义 | 由谁决定 | 变化时影响什么 |
|---|---|---|---|
| `clientVersion` | 客户端发布版本 | 发布客户端时填写 | 标识修 Bug、增加功能的安装包，不自动换榜或换季 |
| `quickRankVersion` | 快速比赛排行榜版本 | 负责人手动填写并启用 | 开启这一版本的快速比赛新榜，保留旧榜 |
| `seasonVersion` | 生涯赛季版本 | 负责人手动填写并启用 | 使用该赛季独立规则和独立玩家进度，旧季保留历史 |

三者独立：只升级客户端，两个业务版本都不变；只开新生涯赛季，快速榜不变；只开新快速榜，生涯进度不变。负责人也可以明确选择一次同时更改其中两个或三个。

**系统、开发者和 AI 都不根据数值改动、Bug 类型、日期、安装包或规则差异自动替负责人增加榜版本或赛季版本。** 原先建议的 28 天仅可作为内容时长参考，不是自动创建下一季的计时器。

“统一配置”指统一填写、校验和发布，不指三个编号必须相同或一起递增。

## 2. 一份配置如何管理

### 2.1 唯一编辑源

项目配置已创建于 [`config/game-versions.json`](../config/game-versions.json)，负责人在这里填写版本号。当前文件内容如下；尚未接入客户端构建或腾讯云发布，修改文件不会自动切换线上榜单或赛季：

```json
{
  "clientVersion": "1.0.0",
  "quickRankVersion": "1.0",
  "seasonVersion": "S1"
}
```

三个值都使用字符串，不能用浮点数保存 `1.0`。客户端版本建议三段编号；两个业务版本支持自定字母、数字、点、下划线和短横线，长度 1～32。只校验合法性和是否重复，不比较大小、不自动加一。

按后续实现设计，这份文件是唯一编辑源，腾讯云将保留对应的**已发布配置**，游戏从云端取得当前有效的榜和赛季。不能让项目文件和另一张控制台表各自随意编辑而不知道哪个生效。如后续负责人希望完全在腾讯云填表，可将唯一编辑源整体迁到云端，不并行维护两个可写真源。

生涯 S1 的赛事规则保存在以 S1 为键的规则配置中，发布时验证引用存在。这是规则内容，不要求负责人再管理第四个业务版本号。

### 2.2 填写不等于启用

保存文件只更新草稿，不直接改变线上。统一发布先显示差异，例如：

| 配置项 | 当前生效 | 本次拟启用 | 影响 |
|---|---|---|---|
| 客户端 | 1.2.2 | 1.2.3 | 新客户端发布元数据 |
| 快速榜 | 1.0 | 1.0 | 保留原榜 |
| 生涯赛季 | S1 | S2 | 新季独立进度，S1 停止签发新场 |

负责人发起启用后，服务端在受控管理操作中切换指针，记录操作人与时间。相同配置重复发布不能清空数据、重复初始化或重复发奖励。自动任务可以执行已授权发布/归档，但不能自己决定是否换版本。

安装包发布与云配置切换不是跨平台的单个事务：有新玩法时，先部署兼容服务、发布并验证客户端，再由负责人启用新赛季。准备检查失败则维持原生效配置，不留下指向不存在规则的半完成状态。

### 2.3 区分“实际安装版本”和“服务器已发布版本”

`clientVersion` 构建时固化到实际包中，云端也保留对应发布元数据。玩家装的是 1.2.2，即使云端发布了 1.2.3，这台设备仍是 1.2.2；不能读取云配置就自称已更新。

榜版本和赛季版本由云端签发赛事时确定，客户端包内的旧值只能作构建溯源，不能覆盖云端指针，也不能由玩家指定历史版本参赛。

各客户端还需有玩法/接口兼容信息，由发布流程维护。多个客户端版本可以共用同一榜和赛季；兼容信息不触发新榜/新季，也不是另一个需手填的业务版本号。

## 3. 每个生涯赛季独立保存规则与进度

当前 `profile.career` 只有一套联赛、积分、杯赛和回执。`profile.career.version = 1` 是内部结构标记，**不能改成 S2 来实现新赛季**；`profile.schema`、`revision` 也不能代用。

新模型按“账号＋生涯赛季版本”分别保存：

```text
玩家 10000
├─ 账号资料：昵称、金币、角色等级、外观
├─ S1：城市精英、60 分、蛙妹杯赛记录
└─ S2：新的赛事地图、新的阶段进度、新的领奖记录
```

S1 的 60 分不直接套进 S2。S2 可能没有积分，可能是计时关卡、星级挑战或其他赛制。历史显示必须结合 S1 的规则，不能用 S2 的名字/阶段解释旧数字。

### 3.1 数据归属

| 数据 | 归属 | 换新季默认处理 |
|---|---|---|
| 短 ID、昵称、头像 | 账号 | 保留 |
| 金币、各角色等级、外观选择 | 账号 | 保留，不因换季清空或重新发一份资产 |
| 赛事定义、阶段、AI、距离/规则、晋级及奖励规则 | 赛季 | 使用该季独立定义 |
| 联赛等级/关卡、积分/星级、解锁、杯赛轮次 | 玩家＋赛季 | 按新季规则初始化，不直接复制旧值 |
| 首通、首奖、目标领取记录 | 玩家＋赛季 | 独立防重；新季是否再次发奖由新季规则决定 |
| 赛事凭据、结算证据 | 所属比赛季 | 固定归属，不随当前指针搬家 |
| 历史奖杯/荣誉 | 原季历史＋账号展示摘要 | 保留季节标签，不能将 S1 第三级当作 S2 第三级 |
| 未来跨季累计成就 | 账号 | 仅汇总语义一致的事件，不盲目相加不同赛制的分数 |
| 快速比赛纪录 | 快速榜版本＋模式＋账号 | 生涯换季不影响 |

这替代原提案“六级联赛永久作为所有赛季共同解锁基础”的假设。当前六级路线可以成为 S1；下一季是否继承资格由该季明确配置，不能默认仍有六级、100 分或相同杯赛。

“保留旧进度”是保存为旧季历史，不是让新季继续读旧字段。金币/等级如未来也想按赛季重置，需要负责人另行明确；本设计默认账号养成保留。

### 3.2 每季规则配置

包含：标题说明、客户端已支持的规则类型、稳定赛事 ID、阶段关系、解锁条件、距离与玩法、轮次、AI 配置、胜负/晋级条件、奖励定义、初始进度、历史展示名称及客户端能力要求。

赛事使用稳定 ID，例如 `s1_city_cup`，不只依赖数组下标 `2`。不同季可以有同名赛事，但关联时必须带所属季。

已发布规则保留不可变快照和内部校验摘要，赛事绑定实际快照。摘要用于溯源，不触发自动换季，也不是第四个手填版本。

### 3.3 “完全不一样”的能力边界

如果只是组合已有距离、规则、AI 和赛事条件，可主要通过配置变化，不一定更新客户端。如果新增目前不存在的胜负判定、赛中机关或界面流程，需要先开发客户端/云端支持，再更新 `clientVersion`，最后由负责人启用新 `seasonVersion`。

版本隔离数据，但不会自动创造新玩法。

## 4. 同季调整和新开一季

| 操作 | 处理 |
|---|---|
| 同号修 UI/文案 | 原季进度保留；必要时更新客户端 |
| 同号改奖励/AI/数值 | 不自动建新季；旧场按绑定规则处理，新场按发布规则处理 |
| 同号改变关卡结构 | 发布检查要求兼容/迁移方案；没有方案则拒绝发布，不能擅自改赛季号 |
| 负责人填写新号并启用 | 新季规则和玩家进度独立，旧季历史保留 |
| 只改快速榜版本 | 生涯继续当前季 |
| 玩家自己升级角色 | 三个发布/业务版本均不变 |

负责人可以决定同号更新，但结构变化时仍需完成迁移，不能让旧数据被当成新结构误读。系统的保护动作是阻止损坏性发布，而不是替负责人创建新版本。

## 5. 换季时的比赛、杯赛与网络恢复

### 5.1 凭据固定归属

快速比赛绑定 `quickRankVersion`；生涯比赛绑定 `seasonVersion`、赛事 ID、规则快照及进度记录。两者都记录实际客户端版本供排查，但客户端版本不决定榜单/赛季分组。

结算按原凭据处理，不能到提交时才读取当前指针，把旧比赛记入新季。客户端不能自行改所属季。

### 5.2 默认关闭策略

建议首版：停止签发旧季新场 → 新开生涯比赛进入新季 → 已签发旧场在原有效期内补结算（当前最长 24 小时）→ 旧季归档。

有效旧场更新原季进度，按原规则领取一次奖励；金币进入同一个账号钱包。季内领取标记和账号金币同事务提交，新季不继承这场积分/首通，也不再发一次奖励。

**尚未开始的旧杯赛下一轮默认不再开放。** 保留原轮次，历史显示“赛季结束，未完成”，不伪造为主动放弃或失败，也不把旧半决赛搬到新赛制。截止前已签发的决赛正常有效夺冠，仍可生成旧季冠军记录。

这替代旧提案“共用永久杯赛，跨季随时续打”的默认假设。若负责人希望某一季允许旧杯继续，须在关闭策略中另行明确，并保留旧规则与支持客户端；不是当前默认能力。

换季与返回大厅提示应说明这一区别。若要提前取消尚有效的旧凭据，需要负责人明确发起并设处理方案；不能因切季静默取消所有在途奖励。

### 5.3 旧客户端、双设备和断网

新季需要新客户端时，旧端看到“需要更新”，不能生成假空档或降级本地生涯；已签发的旧场仍保留必要兼容结算。

设备 A 持有 S1 页面、B 已看到 S2 时，服务器决定新开赛所属季，旧页面收到季节变化提示后刷新。仍维持每账号一个未结算赛事约束，拆季不意味着可多设备同时开赛。

读取配置失败不初始化默认新季，保留有标识的旧显示；恢复后原请求重试，进度和奖励只记一次。

## 6. 云端存储与发布

以下为未来数据分类，并非已存在的集合：

| 数据类别 | 内容 | 约束 |
|---|---|---|
| 统一发布配置 | 三个版本、内部修订、启用时间和操作者 | 唯一当前指针，发布检查预期修订，原子切换 |
| 客户端发布记录 | 安装包版本、支持玩法/接口、发行状态 | 实际安装版本与推荐版本区分 |
| 快速榜版本记录 | 手填号、启停历史、开放模式 | 不随客户端或生涯自动更换 |
| 生涯赛季定义 | 手填号、规则快照、状态、支持条件 | 不覆盖历史规则 |
| 玩家赛季档案 | `playerId + seasonVersion`、规则类型、进度、领奖标记、局部版本 | 确定性唯一键，一人一季一份 |
| 赛事/结果 | 来源、业务版本、规则快照、结果与发奖记录 | 不搬迁既有归属，不跨版本重复提交 |

主档保存账号资产和有限摘要，不将无限多季档案塞进一个 `profile.career`。按需读当前季/历史季，允许不同季使用各自支持的数据结构。

主档金币、该季进度/领奖标记、操作回执同事务处理。未来管理回档要指定资产/季节/关联赛事范围，不能只恢复主档而留下已经发奖的季节记录不处理。

运营仍用腾讯云官方控制台查看；发布、迁移、回退通过受控管理操作执行，不给普通客户端修改版本权限，不建设新的本地管理网站。

## 7. 现有档案接入首季

1. 负责人指定首季号，如 S1；这个示例不是本次自动启用。
2. 将当前六级生涯配置固定为该季规则。
3. 将已有 `profile.career` 迁入对应 S1 记录，保留联赛、积分、杯赛、wins、回执以及待结算关联，不默认为空档。
4. 原金币、等级、短 ID 和身份保留；迁移有唯一标记、幂等与校验，不重复发奖励。
5. 旧凭据明确映射到 S1，保留结算兼容窗口；不能只改 schema 就拒绝所有在途请求。
6. 客户端读取“账号资产＋当前季档案”；过渡期以云端迁移状态指定唯一数据源，不让新旧 career 各写各的。旧字段清理由后续独立步骤处理。

以后启用 S2，才按 S2 初始化规则创建新进度。历史缺失的用时、日期或累计次数不在迁移时编造。

## 8. 误切换和回退

负责人可以恢复旧榜/旧季为当前：恢复其原数据继续使用，不是清空后重开。要全新一轮必须填写未用过的编号。

误切 S2 后返回 S1，S2 数据保留、不合并进 S1；已合法发出的账号金币不自动收回，再回 S2 时靠领取标记防重复。恢复前检查旧规则和客户端兼容性，不能只改指针。

启停历史独立记录；已用编号不删除后重用，不允许同一编号暗中代表两份全新赛季。原始规则快照及凭据关联也不回退覆盖。

## 9. 验收清单

- 只改客户端号，两个业务版本和已有数据都延续。
- 只改快速榜号，新榜开始，生涯季/资产不变。
- 只改生涯季号，独立新进度，快速榜不变。
- 三项同时发布，引用不存在或客户端不支持时不半成功切换。
- 修数值/Bug但保持编号，不自动建榜、建季、清档。
- 不同季阶段数和胜负规则不同，历史仍按原季解释。
- 跨季旧场、断网重试、双设备、管理恢复、初季迁移均不重复发奖。
- 恢复旧版本不新建空档，不合并其他版本数据。
- 旧客户端不能读云配置就自称新客户端；有明确更新提示与在途结算处理。
- 配置不进入比赛逐帧请求；好友房协议与保活重赛不受影响。
