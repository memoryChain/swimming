## 明确缺陷

### 1. P1：跳水兜底会提前解除远端真人的娱乐击倒状态

位置：`assets/scripts/core/GameManager.ts:4119`；`assets/scripts/entity/Swimmer.ts:475`、`:666`、`:674`、`:694`。

触发链：

1. 真人在比赛中被娱乐事件击倒，`beginEntertainmentKnockout()` 暂停 motor，`isNetRacing` 变为 false，节点仍活动。
2. 其他设备继续收到该真人大于 1 米的进度；此时其跳水开始时间早已超过兜底超时。
3. `updateNetRaceSync()` 只判断“真人、有进度、未处于 racing”，调用 `remote.forceEnterRace()`。
4. `forceEnterRaceAt()` 进入 `startRace()`，清掉击倒标记并重新启动游泳。

结果：真人本机仍在急救，其他设备上的副本已经恢复。恢复控制器与角色实际状态分离，也可能影响房主后续碰撞和目标选择。重复的同阶段恢复快照不保证重新触发击倒入口。

证据：提取真实 `updateNetRaceSync()` 的兜底分支及 `Swimmer.forceEnterRaceAt()` 执行，倒地样本输出 `forced=1, knocked=false, racing=true`。这是方法级复现；完整双机画面尚未验证。

修复方向：跳水兜底必须排除娱乐击倒/恢复流程，明确它只负责尚未完成的起跳入水。不得通过修改本机正常击倒规则规避。

验收：远端真人分别被鲨鱼、炮火、炸弹、水雷击倒后，各端维持同一急救阶段；持续收到真人位置快照也不能提前恢复；原先丢失跳水事件的兜底仍有效。

### 2. P1：补给快照先到时，真人可能拿不到苏打/冰沙效果

位置：`assets/scripts/core/StimulantBrawlController.ts:298`、`:359`；`assets/scripts/net/NetRaceController.ts:696`；`assets/scripts/core/GameManager.ts:1846`。

`applySnapshotState()` 根据领取位图直接将道具标为 `collected`，但快照没有领取者和待结算收益；随后 `applyPickup()` 一看到该标记就返回 false。状态广播和玩法事件并非共同的严格有序流，因此不能假定领取事件总是先到。

结果：道具消失，但领取者本机未回血、未增加苏打心率负担，或未执行冰沙降温/持续效果。真人本机的这些状态不会靠房主对远端占位角色的修改自动补回；领取广播丢失时同样缺少完整补偿信息。

证据：执行当前控制器源码，先应用 `revision=1,collectedMask=1`，再应用对应领取事件。苏打和冰沙均返回 `accepted=false`，效果与反馈调用次数均为 0。

修复方向：分开记录“世界道具已回收”和“领取者收益已结算”；收益按权威领取记录独立去重。恢复信息需要足以确定领取者和领取身份，不能只同步隐藏位图。

验收：事件先到、快照先到、重复事件、丢一次广播、房主迁移五种情况，领取者效果均恰好结算一次；其他人不能重复领取。

### 3. P1：娱乐返场后，上一轮快照可以污染新一轮子玩法

位置：`assets/scripts/core/GameManager.ts:1656`；`assets/scripts/core/CannonBrawlController.ts:85`、`:93`、`:144`；`assets/scripts/core/EntertainmentModeDirector.ts:552`；`assets/scripts/net/NetRaceController.ts:693`。

导演激活返场炮火时调用 `restart()`，子控制器的 revision 和已完成掩码归零。导演自身会拒绝旧 revision，但拒绝结果没有阻止 `NetRaceController` 继续把同一旧整包中的炮火等子状态灌入。子状态未按导演的 `activationSerial` 隔离。

结果：先收到新一轮激活快照、再收到上一轮尾部快照时，旧炮火的完成掩码和较大 revision 能覆盖新一轮。访客可能认为新炮击已经全部结束，并拒绝新一轮较小 revision 的发射事件。

证据：执行真实炮火控制器：返场安排两次炮击，随后输入上一轮 `revision=4,completedStrikeMask=3`，剩余炮击变成 0；再输入新一轮 revision=1 发射事件，被拒绝。

修复方向：子状态与玩法事件携带并校验激活代次，或使用跨返场单调编号；导演拒绝旧代状态时应同时阻断该包对应的子状态。炸弹、鲨鱼等返场 reset 路径也应一并检查，不能仅修炮火掩码。

验收：将上一轮最后两帧状态延迟到返场之后到达，炮火仍按新排期完整执行；过期事件不能串入新轮；房主迁移恢复代次后仍一致。

### 4. P2：垃圾和水雷的快照会提前占用命中事件编号

位置：`assets/scripts/core/LitterBrawlController.ts:376`、`:412`；`assets/scripts/core/MinefieldBrawlController.ts:232`、`:266`；`assets/scripts/core/GameManager.ts:2801`、`:2672`。

两个控制器均在应用快照时推进 `revision`，命中事件则以 `event.revision <= this.revision` 拒绝。快照更新了垃圾位置或水雷存活状态，却没有重放真人受到的瞬时效果。GameManager 只有在 `applyContact/applyImpact` 成功时才执行命中处理。

结果：垃圾硬碰撞漏掉即时减速和弹开；水雷外围选手漏掉冲击。水雷核心击倒另有恢复快照兜底，不能因此认定所有命中效果都被补回。

证据：垃圾由真实 host 控制器生成碰撞事件，再让 guest 先接收碰撞后的状态快照，事件返回 false；水雷同顺序复现，事件也返回 false。

修复方向：世界物体状态版本与每个选手的瞬时结算去重分开；还需定义迟到效果的时效和补偿方式，避免为了不漏结算而无限补播很久以前的物理冲量。

验收：同一真人按两种消息顺序受到相同的减速/冲击，重复事件不叠加；核心急救仍只启动一次。

### 5. P2：400 米娱乐赛程在存档归一化时变成 200 米

位置：`assets/scripts/backend/PlayerProfile.ts:243`、`:251`。

`quickRule` 已接受 `entertainment`，但距离归一化只为 `standard` 和 `wild` 保留 400 米，娱乐规则落入固定 200 米分支。

结果：400 米娱乐赛设置不能可靠保存。后端读取档案时会再次归一化，因此不限于重启游戏，后续读写档案也可能固化错误值。

证据：真实 `normalizeProfile()` 输入 `{distance:400,rule:'entertainment'}`，输出 `{distance:200,rule:'entertainment'}`。

修复方向：用一致的规则/距离合法性约束处理娱乐赛程，补充存档往返覆盖。

验收：选择 400 米娱乐，执行保存、读取、奖励更新和重新进入准备页，均保持 400 米；非法距离仍正确回退。

### 6. P2：炸弹画中画中的离屏角色会被主镜头冻结姿态

位置：`assets/scripts/core/GameManager.ts:838`；`assets/scripts/entity/CartoonSwimmerRig.ts:1305`；`assets/scripts/core/PerformanceConfig.ts:101`；`assets/scripts/camera/RaceEventPictureInPictureCamera.ts:267`。

主镜头裁剪只有鲨鱼目标的画中画保活例外，没有炸弹携带者。携带者若属于 AI/远端角色且离开主镜头，会被标记为 `splashCulled`。当前配置打开 `freezePoseWhenCulled`，该状态直接跳过姿态更新，但画中画仍在拍摄它。

结果：携带者位置可以继续移动，画中画里的肢体动作却冻结，同时丢失对应水花。该问题也影响单机 AI 携带者。

证据：确认主镜头裁剪与炸弹画中画的调用链；执行真实节流方法，裁剪态返回 `-1`，即跳过姿态更新。尚未在引擎内录制画面，因此不把具体视觉严重程度作为已测结果。

修复方向：让当前活跃画中画目标参与姿态可见性判定；画中画结束后恢复原有裁剪，避免全面取消离屏节流。

验收：主镜头外的 AI 和远端真人携带炸弹时，画中画仍正常划水；传递换人和画中画关闭后保活目标及时切换/释放。
