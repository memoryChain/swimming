# 快速比赛总榜与手动版本管理设计

日期：2026-09-27。状态：设计，未实现。本次只整理文档，不修改游戏、云函数或线上数据。

> 最新统一配置见[统一版本配置与生涯赛季数据设计](统一版本配置与生涯赛季数据设计.zh.md)：`clientVersion`、`quickRankVersion`、`seasonVersion` 三者独立，集中填写并发布。本文“养成榜版本”即 `quickRankVersion`，不另设独立编辑配置。

## 1. 已确认的产品规则

- 先做单人快速比赛的全服总榜，例如「200 米＋狂野」。不限制角色和等级，不考虑养成差异的公平性。
- 每个玩家在每个榜内保留最佳有效完赛时间，越短越靠前。
- 客户端版本与养成榜版本分开。客户端更新、修 Bug、修改数值均不自动换榜。
- **是否开启新榜完全由负责人决定：手动填写养成榜版本号并启用。系统和开发者不能根据改动类型自动替负责人换榜。**
- 同一个养成榜版本下持续累计成绩，不按周、月、生涯赛季或客户端发布次数重置。
- 新榜从无成绩开始，旧榜保留历史。金币、角色等级、生涯进度不随换榜清空。

本文件覆盖此前生涯设计中“先做赛季杯赛榜、统一属性竞速优先”等排行榜建议。赛季、成就仍是单独的后续提案，不是快速比赛总榜的依赖。

## 2. 榜单范围与排名

首个建议开放榜：**快速比赛 · 200 米 · 狂野**。后续可复用相同设计增加 200 米标准、400 米狂野、400 米标准，分别排名；不默认同时开放所有榜。

榜单身份由以下内容确定：

> 正式平台/环境 ＋ 养成榜版本 ＋ 单人快速比赛 ＋ 距离 ＋ 规则

例如：`微信正式 / 1.0 / quick / 200 / wild`。客户端发布号和赛季编号不放入这个标识。内部可使用不可变的版本记录 ID，避免版本显示名改动导致关联失效；负责人填写的版本号在同一环境中唯一，启用后不可改名或复用。

| 项目 | 规则 |
|---|---|
| 比赛来源 | 只收 `quick`，联赛、杯赛、好友房、调试均不混入 |
| 入榜条件 | 云端接受的正常完赛，凭据匹配榜单条件，成绩未被排除 |
| 玩家属性 | 使用本人实际角色和等级，不固定属性、不分等级榜 |
| 角色切换 | 同一玩家仍只占一个名额；换角色创造更快成绩则替换个人最佳 |
| 排序 | 整数毫秒升序；相同毫秒并列，名次为 1、2、2、4 |
| 未完赛 | 不入榜；不把 0 秒作为最佳 |
| 展示字段 | 名次、昵称、头像、短 ID、时间、创纪录角色、当时等级、纪录日期 |
| 个人区 | 本人最佳、名次、版本、刷新时刻；暂无记录显示“完成此模式后上榜” |
| 页面规模 | 首屏 20 条，可分页看前 100 条，并单独查询本人名次 |
| 奖励 | 首版只展示纪录，不新增按名次发奖 |

个人最佳保存创纪录时的角色与等级快照；之后玩家升级或换角色，不能把旧纪录改显示为新等级/新角色。昵称头像可展示当前公开身份，赛事证据保留当时快照。

同分行用稳定键保证翻页一致，但不得把表格先后当作打破并列。前 100 条截断并列时提示存在同分玩家；没在前 100 条内不等于没有名次。

## 3. 版本如何分工

统一管理三个概念：**游戏安装了哪个版本、快速成绩记入哪一期榜、当前使用哪一季生涯**。后两者均由负责人手动启用，互不触发自动切换。

| 概念 | 用途 | 会不会自动开新榜 |
|---|---|---|
| 客户端发布版本，如 `1.2.3` | 识别安装包、修复范围与兼容性 | 不会 |
| 养成榜版本，如负责人填写的 `1.0` | 明确一组持续累计成绩的榜单 | 只有负责人启用新版本时才开新榜 |
| 已有云协议 `version/rulesVersion` | 云接口与经济规则兼容检查 | 不会 |
| 已有联机协议版本 | 控制客户端能否在同一房间比赛 | 不会 |
| 存档 `schema` | 数据结构与迁移 | 不会 |
| 后续生涯赛季 | 赛季任务与荣誉周期 | 不会 |

配置字段统一为 `quickRankVersion`，界面名称“快速比赛榜版本”。它是**运营手动选择的榜单版本**，不是程序自动计算的养成代码版本，也不是玩家自己的角色等级。此前提议名 `activeBoardVersion` 不再作为另一个配置字段。

现有 `CLOUD_PROTOCOL.rulesVersion` 是严格相等检查，不能直接复用为这个字段。仓库 `package.json` 的 `3.8.8` 也不能直接当成新的客户端发布号规则。实现时新增独立的版本配置与发布兼容记录。

### 3.1 例子

| 实际变化 | 负责人是否更换养成榜版本 | 结果 |
|---|---|---|
| 客户端 `1.0.0 → 1.0.1`，修界面 Bug | 否，仍是 `1.0` | 原成绩保留，新成绩继续进入 `1.0` |
| 调整角色成长、技能或比赛速度 | 否，仍是 `1.0` | 仍沿用原榜；系统不得自行拆榜 |
| 修复会影响成绩的 Bug | 否，仍是 `1.0` | 仍沿用原榜；如有异常成绩可另行处理 |
| 负责人决定本次养成更新开新榜 | 是，填写并启用 `2.0` | 新开 `2.0`，`1.0` 转为历史 |
| 客户端没更新，只希望开启新一期 | 是，填写并启用新版本 | 也可以开新榜，无需靠发布客户端触发 |
| 玩家角色升到 30 级 | 无关 | 继续当前榜，不为个人升级新建榜 |

即使改动可能让旧纪录更难打破，也只提供影响说明，由负责人决定是否更换版本；不得以“公平性要求”“检测到配置差异”为由自动操作。

## 4. 负责人怎么操作

继续使用腾讯云官方控制台，不建设本地后台或要求域名。以下为待实现的管理流程，不表示目前已经有这些按钮或集合。

### 4.1 日常更新不换榜

发布新客户端或更新养成数值时，保持当前养成榜版本号即可。负责人可以把新客户端加入当前版本允许的发布列表；多个客户端发布版本可以使用同一养成榜版本。

兼容列表只控制“哪个客户端可以提交”，不会自动创建新榜。普通兼容更新可以沿用当前发布策略；若服务器接口也变了，开发者安排接口迁移，不能用新开榜代替兼容处理。

### 4.2 需要换榜时

1. 在统一版本配置中填写 `quickRankVersion`，如 `2.0`，可附备注“第二轮养成调整”；保持另两个版本不变。
2. 查看启用预览：当前 `1.0`、拟启用 `2.0`、涉及的快速比赛榜、旧榜处理和允许的客户端。
3. 负责人执行“启用此版本”。服务端在一个受控管理操作中切换当前版本、记录启用时间和操作人。
4. 新开比赛进入 `2.0`，旧榜仍可查看；不删除任何玩家档案。

首版建议所有已开放的快速比赛模式共享一个手填版本号，一次启用统一切换；不先增加每种模式各自版本的复杂度。启用后新榜可以没有成绩，不复制旧纪录填充。

版本号用文本保存，例如 `1.0`、`1.1`、`2026.10`，建议只允许字母、数字、点、下划线、短横线，长度 1～32。**不按大小比较、不自动加一、不从提交号/日期生成。** 输入重复版本只显示已有记录，不能借此清空原榜。

“填写草稿”和“启用版本”分开，是为了避免手误立即切换全服。最终启用操作由负责人发起，不需要由开发者批准。实现时可以用腾讯云官方配置记录配合管理云函数完成；控制台直接改当前指针不能被当作完整启用流程，避免旧榜状态与指针不一致。

### 4.3 回退与误操作

未启用的草稿可修改。已启用的版本号不可覆盖、重命名或删除后重用。

若误启用新版本，由负责人明确执行“恢复上一版本接收新比赛”：恢复原榜继续累计，已产生的新版本记录仍保留，二者不合并。回退本身不代表客户端或云规则已经回退，发布兼容列表需要同时核对。每次启停留下独立操作记录，重试同一管理请求不会重复切换。

## 5. 开赛、换榜与补结算

**比赛属于开赛时签发凭据绑定的版本，不属于提交成绩那一刻的当前版本。**

开赛时，云函数读取负责人已启用的版本，检查客户端兼容性，把榜单版本、来源、距离、规则、角色和当时等级写入赛事凭据。客户端不能自行传一个历史版本号来指定上哪张榜。

| 情况 | 处理 |
|---|---|
| `1.0` 开赛，中途启用 `2.0` | 该场仍记 `1.0`，不丢弃正常赛果，不进入 `2.0` |
| 切换后新开赛 | 使用 `2.0` |
| 旧场断网，之后恢复 | 在原凭据有效期内重试，仍写原版本，原请求不重复发奖 |
| 重复提交同一场 | 返回已保存结果，不重复记录或再次发金币 |
| 旧客户端被负责人排除 | 阻止其新开计榜比赛并提示更新，不自动让它进入新榜或另开旧榜 |
| 切换时存在接口/规则升级 | 保留旧凭据的必要校验/结算处理，不能全部按新规则硬算 |

沿用当前凭据最长 24 小时的边界：旧榜停止新开计榜比赛后，允许有效旧凭据补交，界面显示“停止接收新比赛，旧成绩结算中”；最迟在旧签发窗口结束 24 小时后冻结普通写入。普通补结算不会开启新版本。历史纠错走管理员操作，并显示修订记录。

版本恢复后，该版本重新允许签发；冻结判断依据实际最后一次停止签发的记录，而不是只看第一次启用日期。一次比赛仍只归一个版本。

旧客户端也可能通过云端配置看到新指针，因此**仅把 `quickRankVersion` 下载到本机并照填不足以做隔离**。需要服务器维护发布兼容信息，并绑定云端签发凭据。发布号/配置摘要本身也不是防修改客户端的安全证明；这里只解决正常发布流程的版本归属，反作弊另行处理。

## 6. 数据与查询方案

首版可复用现有云函数、事务和管理审计，不依赖生涯赛季集合。建议新增以下少量数据：

| 数据 | 用途 |
|---|---|
| 榜单版本配置 | 当前指针、负责人填写的版本号、启停记录、允许的发布版本、已开放模式 |
| 快速比赛结果 | 凭据 ID、内部玩家 ID、短 ID、榜版本、比赛条件、整数毫秒、校验/排除状态 |
| 玩家榜单最佳 | 每榜每玩家一条；最快时间、对应结果 ID、角色/等级快照 |
| 榜单快照（规模增长后） | 固定生成时刻的分页排行与本人名次，避免每次全表扫描 |

确定性记录键使用“榜 ID＋内部玩家 ID”；结果用赛事凭据去重。结算事务内处理经济回执、有效结果与个人最佳比较，两个并发结算不会用较慢成绩覆盖较快成绩。云端统一将有效用时换算为整数毫秒，显示和排序使用同一精度。

没有更快成绩则不改最佳；同毫秒保留原有效纪录，角色/等级不因同分提交反复变化。旧版本纪录不复制到新版本，也不跨版本比较后覆盖。

查询按榜版本/模式限定，再按用时排序；本人名次为该榜内严格快于自己的有效玩家数＋1。公共榜目标缓存约 1～5 分钟，结算后本人纪录立即更新并提示排名等待刷新；具体索引、查询上限与费用在实现阶段验证。快照生成版本、客户端版本、手填养成榜版本彼此不同。

历史榜明确显示版本号和冻结/结算中状态。客户端默认打开当前榜，历史入口按启用记录排序，不按版本号文本排序。未启用版本和管理字段不对玩家公开。

## 7. 管理与记录边界

按玩家短 ID＋榜版本＋比赛模式查找对应纪录。排除异常成绩保留原记录、原因与审计，重新计算该玩家在同榜的下一条有效最佳，而不是永久移除整个人或改动其他版本。

因此不能只存一条最佳然后丢掉其余所有候选；结果保留/归档策略需支持最佳撤销后的恢复。当前 `career.receipts` 的 32 条奖励摘要没有完整用时，不能据此补出历史榜；总榜从功能正式启用后的有效比赛开始记录。

目前比赛结果仍由客户端上报，云端只有基础合理性检查。首版不发名次奖励，保留异常标记/排除和查询证据。**不以反作弊或修复成绩为由擅自开启新榜**：修一条记录和负责人换一整个版本是两个独立操作。

## 8. 实现前验收清单

- 普通客户端升级而版本号不变：原纪录保留，新旧兼容客户端继续同榜。
- 数值/能力/影响成绩的 Bug 修改而负责人不换号：仍沿用原榜，无隐藏自动重置。
- 负责人手填并启用新号：只新建对应榜，金币、等级、生涯与历史榜不变。
- 输入重复号、启用请求重试、同时两次管理操作：不清空数据、不产生两个当前指针。
- 开赛途中换版本、断网恢复、旧接口在途请求：赛果与奖励各处理一次，归属原榜。
- 同号恢复、暂停后再次启用：保留该榜原成绩；其他版本不并入。
- 同玩家不同角色、升级前后、同毫秒与更慢成绩：只有更快有效成绩替换个人最佳。
- 距离/规则/来源隔离：400 米、标准、联赛、杯赛、好友房都不能写入快速 200 米狂野榜。
- 当前榜/历史榜分页和本人排名一致；公共结果不暴露私有档案或平台身份凭据。
- 单场经济结算、好友房保活、现有生涯规则不因排行榜改动而受影响。

后续实施时先交付“快速 200 米狂野总榜＋手动版本启用＋历史查看＋异常纠错”。不要求先做赛季、成就或统一属性挑战；是否扩展其他快速模式由负责人确定。
